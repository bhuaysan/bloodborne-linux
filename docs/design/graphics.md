# Graphics design (M4)

How the game's GPU work reaches Vulkan: the shader translator (GCN → SPIR-V), how it is tested offline, how shaders are extracted from the game files, and a sketch of the command-buffer side. The first wave of M4 issues builds on this note and runs without the game booting. Change this note in the same PR when an implementation has to deviate.

## Starting point

- **GPU generation.** The base PS4 GPU is GCN 2nd generation ("Sea Islands", gfx7). The game's shader code uses the SI/CI encodings. Three instructions from a game shader show it:
  - `v_interp_p1_f32` (`0xC8080000`), `image_sample` and `exp mrt0 … done compr vm` (`0xF800…`), assembled with LLVM's assembler for `bonaire` (gfx7), give the same bytes as the game.
  - LLVM's gfx8 (`tonga`) decoder rejects them as invalid encodings.
  - `v_cvt_pkrtz_f16_f32` appears as a VOP2 instruction, which gfx8 only has as VOP3.
  
  The corpus test (#121) answered whether the game uses Sea Islands (CI) additions to Southern Islands (SI, gfx6): every distinct instruction of the 3,832 programs with different code, assembled for `tahiti` (SI), gives the words of the game, except 265 distinct SMRD encodings with the 32-bit literal offset (`s_load_dwordx8 s[24:31], s[12:13], 0x100`; the SI offset field has 8 bits). No FLAT, no `flat_scratch` and no other CI instruction occurs. So the game relies on CI only for SMRD offsets of 256 dwords and more, which the decoder handles. References: the AMD documents in [source-policy.md](../source-policy.md#allowed-with-credit).
- **Command buffers** are built by GNM code that is statically linked into the eboot. Only the driver boundary is imported: `libSceGnmDriver` has 50 imported functions, two of them named so far. The game hands us finished PM4 streams at submission time.
- **Shaders live in the game files** (below). Each one can be found again at run time by the hash of its code.
- **The first wave ran offline**, before M3 reached the main loop: extraction, decoding, translation, and execution tests on our own GCN programs. The second wave works on the running game.

## Shader extraction

The 8 archives in `dvdroot_ps4/shader/` hold about 20,300 shader programs:

| Archive | Files | Programs |
|---|---|---|
| `gxflvershader.shaderbnd.dcx` | 14571 | 16265 |
| `gxflvershader.shaderbnddebug.dcx` | 3194 | 3194 |
| `gxffxshader.shaderbnd.dcx` | 301 | 308 |
| `gxdecal.shaderbnd.dcx` | 193 | 193 |
| `gxposteffect.shaderbnd.dcx` | 119 | 119 |
| `gxrenderershader.shaderbnd.dcx` | 111 | 111 |
| `gxshader.shaderbnd.dcx` | 15 | 15 |
| `gxgui.shaderbnd.dcx` | 13 | 13 |

Programs are counted by their `OrbShdr` marker. In every archive that count matches the count of `s_endpgm`.

What a first look shows, to be worked out and documented in `docs/formats/`:

- **DCX** (`docs/formats/dcx.md`): a big-endian header with the sizes (`DCS` chunk) and a `DFLT` method tag, followed by a zlib stream.
- **BND4** (`docs/formats/bnd4.md`): an archive with a file table, names and data offsets. The shader set has no nested archives.
- **Shader program** (`docs/formats/shader-binary.md`): each archive entry starts with a header (tag `Shdr`) that gives the offset of the first program's code. A program is GCN code, then a footer that ends in a 0x1C-byte block starting with the `OrbShdr` marker. The footer, together with the data after the last block, holds the metadata:
  - resource names (`g_Texture0`, `SS_ClampLinear`),
  - input semantics (`IN.tex0`, `TEXCOORD`),
  - the entry point name (only as the name of the outputs, so compute shaders don't carry it; #117).
  
  Some files hold more than one program.

FromSoftware file-format material may be used under the rules in [source-policy.md](../source-policy.md). Everything gets checked against the files.

`tools/shaderbnd` checks each archive's SHA-256 against a pinned table in a new file in `tools/common/`. It refuses other files. It writes to `analysis/shaders/<archive>/`:

- one file per program under `programs/`: code plus footer, as stored. The last program of an entry also holds the data after its footer block;
- every entry as stored under `entries/`, so the entry header and the trailing data stay available;
- `index.json`, with entry name, program index, offset in the entry and size (#114), and the program type, stage, code size and SHA-256 of the code (the **code hash**, #117); per entry, the resource, sampler, input and output names from the metadata (#117).

Nothing it writes is committed.

The code hash is the shader's identity everywhere: in corpus reports, in the translation cache, and later at run time, where the game gives us only the code address (`SPI_SHADER_PGM_LO_*`). Whether the footer follows the code in GPU memory, so the run time can find the code size the same way, is checked once the game boots. Until then the run time decodes as described below.

The eboot may contain shaders of its own, such as GNM's internal clear and copy shaders, or fetch shaders. The extractor also scans the eboot for the `OrbShdr` marker and reports what it finds (`--scan-eboot`, report only): 5,493 footer blocks of PS, VS, ES, LS and CS programs, most of them in the executable segment (`docs/formats/shader-binary.md`).

## Shader translator

```
code ─decode─► instructions ─cfg─► blocks ─analyze─► typed program ─structurize─► SPIR-V
                                                 ▲
                                       ShaderKey (pipeline state)
```

### Decoder and disassembler

- Decoding is table-driven, for every Sea Islands microcode format: SOP2, SOPK, SOP1, SOPC, SOPP, SMRD, VOP2, VOP1, VOPC, VOP3, VINTRP, DS, MUBUF, MTBUF, MIMG, EXP and FLAT. It handles literal constants and inline constants.
- The result is a list of `Instruction` values (opcode, format, operands, modifiers, size).
- A program can end in an early `s_endpgm` before other blocks. Decoding stops at the first `s_endpgm` that lies at or beyond the furthest branch target, or at the code size from the footer when it is known.
- The disassembler prints LLVM's assembly syntax.
- An unknown encoding is an error that names the offset and the word. It is never skipped.
- The opcode tables are written by hand from the ISA manual. They are code, not generated data. Regular families are built in code rather than listed: VOPC names, for example, come from the base (`cmp`, `cmpx`, `cmps`, `cmpsx`) × condition × type. Table rows are kept dense.

### Execution model

**One SPIR-V invocation is one GCN lane.** The registers of the wave become per-invocation variables:

- **VGPRs** are the lane's own values. When the program uses relative indexing (`v_movrel*`, `s_movrel*`, with the index in M0), they become an indexable array.
- **SGPRs** are copied into every lane. They are uniform in the hardware, and every lane computing the same scalar value gives the same result. M0 is an SGPR like the others.
- **Lane masks** (EXEC, VCC, and SGPR pairs that hold compare results or saved masks) are stored per lane as **this lane's bit**, a bool. A type pass decides which SGPRs hold masks and which hold values. An SGPR used as both is reported as an error until a shader needs it.
  - Bitwise operations on masks (`s_and_b64`, `s_or_b64`, `s_andn2_b64`, `s_and_saveexec_b64`, …) become boolean operations on that bit.
  - Mask constants other than 0 and −1, and 32-bit writes to `exec_lo`/`exec_hi`, take the bit at the lane ID.
- **The lane ID** is `LocalInvocationIndex & 63` in compute, and `SubgroupInvocationID` in the graphics stages.
- **Cross-lane operations** need the whole mask and use subgroup operations:

  | Operation | Translation |
  |---|---|
  | SCC after a mask operation; `s_cbranch_execz`/`execnz`/`vccz`/`vccnz` | any or all over the lane bits |
  | `s_bcnt1`, `s_ff1` and the other scalar operations on masks | ballot of the lane bits |
  | `v_readfirstlane_b32` | find the lowest lane whose EXEC bit is set (ballot, then lowest set bit), then broadcast from it with a dynamic lane ID (SPIR-V 1.5) |
  | `v_readlane_b32` | broadcast from lane *n* (ignores EXEC) |
  | `v_writelane_b32` | `lane_id == n ? s : v` (ignores EXEC) |
  | `v_mbcnt_lo_u32_b32`, `v_mbcnt_hi_u32_b32` | count of mask bits below the lane ID |
  | `s_wqm_b64` | any over the quad: two `OpGroupNonUniformQuadSwap` in every stage (#253) |
  | `ds_swizzle_b32` | subgroup shuffle (gfx7 has no `ds_permute`/`ds_bpermute`) |

**Divergence is predication.** A GCN program's control flow is scalar, so the whole wave takes every branch together. Lanes diverge only through EXEC. The translator mirrors that:

- **Branch structure.** It comes from the scalar branches and becomes structured SPIR-V control flow. The branch conditions are uniform per subgroup by construction. The structurizer handles acyclic regions and natural loops. An irreducible graph falls back to a loop around a switch on a block index.
- **Vector results.** A VALU result is written as `select(active, new, old)`. The operation itself runs in every lane.
- **Mask results.** A mask destination is written as `active && result`, not as a select, because GCN clears the bits of inactive lanes. This covers every VALU mask destination: `v_cmp*` into VCC or SGPRs, the implicit VCC of VOP2 `v_add_i32`, `v_sub_i32`, `v_addc_u32` and `v_subb_u32`, VOP3 SGPR destinations, and `v_div_scale_*`. `v_cmpx*` sets EXEC = `active && result`.
- **Vector memory.** Every MUBUF and MTBUF access, load or store, runs only under `if (active && in_range)` (see Resources). An inactive lane may hold any address.
- **Scalar memory** (SMRD) runs in every lane, with no `active` term. The wave executes it even when EXEC is 0, its address is uniform and really used, and skipping it would leave stale SGPRs in some lanes.
- **Other side effects.** Exports, atomics and LDS writes run under `if (active)`.
- **Image operations.** Sampling runs unguarded, so derivatives stay available. Other image loads run unguarded too, with robust image access enabled. `robustImageAccess2` (`VK_EXT_robustness2`) returns 0 out of range like GCN. With only `robustImageAccess`, the value is undefined, which can differ for active lanes with out-of-range coordinates. Image stores and image atomics are side effects and run under `if (active)`.

**Pixel shaders** need four more rules:

- EXEC starts as "this fragment is covered", that is `!HelperInvocation`.
- `s_wqm_b64` (whole quad mode) turns the helper lanes of a quad back on for derivatives, as in the table above.
- At the final `exp … done`, a lane outside the valid mask was discarded. The valid mask is EXEC at the last export with `vm` (all lanes when no export has `vm`; as built in #129, a refinement of "EXEC at `done`"). Such a lane executes `OpDemoteToHelperInvocation` (core in SPIR-V 1.6 and Vulkan 1.3), so the fragment is not written, and it stays a helper invocation for the derivatives of its quad.
- Implicit derivatives are only defined in uniform control flow. The branch conditions are uniform per subgroup, and that works on real drivers. Where `VK_KHR_shader_quad_control` is available, the translator declares `QuadDerivativesKHR` and `RequireFullQuadsKHR`, which make it defined by the spec.

**Execz skips and live-out scalars.** A forward `s_cbranch_execz` that skips a region in which scalars are defined and used afterwards is translated as a fall-through. The compiler emits these skips as an optimization, so executing the region with no active lane gives the same result. Without the fall-through, a subgroup whose lanes are all inactive would skip scalar work that the 64-lane wave runs.

`s_cbranch_vccz` and `s_cbranch_vccnz` are always real branches on any(VCC). On gfx7 they are also how uniform branches on float compares are made (there is no scalar float compare), and the skipped region then runs under full EXEC.

**Wave size.** A GCN wave has 64 lanes, but a Vulkan subgroup may be smaller: 32 on many GPUs, 8 or 16 on lavapipe.

- **Exact mode** requires a subgroup size of 64 (`VK_EXT_subgroup_size_control`, with `requireFullSubgroups`) in the stages listed in `requiredSubgroupSizeStages`. It matters mainly for compute: the PS4 doesn't define which vertices or pixels share a wave either.
- **Lane-local mode** computes cross-lane results over the subgroup instead of the wave.
  - In compute, ballot results keep their wave bit positions, and the bits of lanes in other subgroups read as 0. The wave position of bit *i* is `subgroup_base + i`, with `subgroup_base = lane_id - SubgroupInvocationID`.
  - `v_readfirstlane_b32` and `v_readlane_b32` convert the wave lane back to `lane - subgroup_base` before the broadcast. A lane outside the subgroup reads as 0.
  - This assumes that a subgroup covers consecutive values of `LocalInvocationIndex`. Vulkan doesn't guarantee it, but implementations do it. The execution tests check it once (`subgroup_base` is uniform per subgroup).
  - A device with `maxSubgroupSize` above 64 is not supported.
- **Reconvergence.** Predication puts non-uniform branches into the module (a predicated store is an `if (active)`), and a ballot or broadcast can follow one. Core Vulkan only promises that invocations reconverge after a branch that is uniform in the subgroup, so a module with subgroup operations declares `MaximallyReconvergesKHR` (`SPV_KHR_maximal_reconvergence`), and the backend needs `VK_KHR_shader_maximal_reconvergence` (lavapipe has it).

An analysis pass marks the shaders whose results can depend on the wave width: cross-lane results that are not uniform, and `s_barrier` under control flow that depends on EXEC (a hang risk). The corpus report counts them.

As built (#125, cross-lane part), the analysis is conservative and has no pass of its own: every operation that needs a subgroup operation (a ballot, `v_readfirstlane_b32`, `v_readlane_b32`) sets `wave_size_dependent` when it is translated, whether its source is uniform over the wave or not. A uniformity analysis that keeps the flag clear for uniform sources (a VGPR that only ever holds a scalar) needs EXEC tracking, because a predicated write leaves inactive lanes different; it is left until the corpus report (item 9) shows how many shaders the conservative rule marks. The `s_barrier` case needs no rule of its own: control flow is scalar, so a branch depends on EXEC only through a cross-lane operation (`any` for the SCC of a mask operation and the `execz`/`vccz` branches, a ballot for a mask read as a value), and that already marks the shader. `s_barrier` itself is translated with LDS (item 7c).

### Control flow

The scalar branches split a program into blocks (`build_cfg`), and the structurizer turns the graph into SPIR-V's structured control flow.

- **Blocks** start at the entry, at every branch target, and after every branch and `s_endpgm`. A block ends in a fall-through, an `s_branch`, a conditional `s_cbranch_*` (taken or next) or `s_endpgm`. A conditional branch to the next instruction is a fall-through. A branch that doesn't land on an instruction, control that runs off the end, and the unsupported branches (`s_cbranch_*fork`, `s_cbranch_join`, `s_setpc_b64`, the `s_cbranch_cdbg*` debug branches) are errors. `s_swappc_b64` is not a branch here: the fetch subroutine it calls is inlined.
- **Execz skips** (see above) become a fall-through when the skipped region, the blocks between the branch and its target, is entered only from the branch's block, is left only to the target, doesn't end the program, and writes scalars. "Writes scalars" means a scalar ALU or SMRD instruction (they all write SCC or a destination), or a scalar destination operand in another format. Whether the scalars are also used after the region isn't checked: that needs the implicit operands of every opcode, which the translator's passes know. A fall-through is correct either way, since running the region with no active lane gives the same result; it only costs the skip. The order in which skips are checked doesn't matter: a nested skip only branches within the outer region or to its target, and two overlapping skips block each other. `vccz` and `vccnz` stay branches.
- **Analysis** (`analyze`): reverse postorder of the reachable blocks, immediate dominators with the iterative algorithm of Cooper, Harvey and Kennedy, loop headers (the targets of back edges that dominate their source), merge nodes (more than one forward edge in), and whether the graph is reducible.
- **Structurizer** (reducible graphs). The nesting follows Ramsey's "Beyond Relooper": every block is emitted exactly once, either inline where its only forward predecessor branches to it, or, as a merge node, right after a scope opened in the code of its immediate dominator. A block's merge nodes nest by reverse postorder, the last one outermost. In SPIR-V:
  - A **scope** is a loop construct that runs once, its continue block unreachable. A branch to its merge node is a break, valid from any depth of selections inside it.
  - A **natural loop** is a loop construct around its header and the scopes that the header opens. All back edges continue to one continue block that branches to the header. Nothing breaks it: an exit continues inline inside the construct (an exit block with one predecessor), returns, or branches to an enclosing scope. Its merge block is unreachable unless a stored branch leaves through it.
  - A **conditional block** is a selection whose merge block is unreachable. Each arm is a break, a continue, a return, or the inlined successor.
  - A **branch out of several constructs** stores the depth of its target (plus 1) in a function variable and breaks the innermost construct. The merge block of each construct it leaves checks the variable: 0 continues with the merge node, otherwise the branch moves one construct out, and the target clears the variable. SPIR-V only allows breaks and continues to the innermost loop, so there is no shorter form.
  - The caller's prologue block is the function's entry block, so a loop header is never the entry.
- **Irreducible graphs** (a loop with more than one entry) have no such nesting. The whole program becomes one loop construct around an `OpSwitch` on the index of the next block, held in a function variable that starts at the entry's index. Each reachable block is a case: it returns at `s_endpgm`, or stores its successor's index (an `OpSelect` on the condition for a conditional exit) and continues the loop. The switch's default is its merge block, which ends in `OpUnreachable`: no other index is ever stored. Every block is still emitted once. The fallback covers the whole program rather than only the irreducible region: irreducible flow from a compiler is expected to be rare, so the simpler form is worth the lost nesting. If the shader corpus shows otherwise, node splitting or a fallback limited to the region can replace it.

### Per-draw data

Each stage of a draw or dispatch reads one push constant: a buffer device address pointing to its **draw block**. `ShaderKey::push_offset` says where: compute at 0, and in a graphics pipeline the VS at 0 and the PS at 8 (`vertex_push_offset`, `pixel_push_offset`), so each graphics stage reads its own block from one 16-byte push-constant range (`graphics_push_size`) that the pipeline layout declares for both stages (#281). The block holds:

- `user_data[16]`, the stage's `SPI_SHADER_USER_DATA_*` or `COMPUTE_USER_DATA_*` values, which the program finds in its first SGPRs;
- `address_bias`, so that device address = guest GPU address + bias;
- `code_address`, the guest address of the program, for `s_getpc_b64`.

The layout is `user_data` at offset 0, `address_bias` at 64 and `code_address` at 72, 80 bytes in all (constants in `src/gpu/gcn/translate.hpp`, which the compute runner uses). The shader reads it through `PhysicalStorageBuffer` pointers.

For the first wave, the guest's GPU-visible memory was **one contiguous imported range**, so a single bias was enough. The second wave's memory mirror replaced the single bias with a table of 16, one per 2 GiB of the window: the field at offset 64 holds the table's device address, and device address = guest address + `bias[(guest address >> 31) & 15]` (`bias_entries` and `bias_shift` in `translate.hpp`; see "GPU memory mirror" under "Command buffers to the first frame"). Every guest access of the translated code (scalar loads, MUBUF, MTBUF, atomics, `flat_store_dword`) loads its entry from the table. The execution tests allocate one buffer and write a table whose 16 entries all hold its bias (`DrawBlock::bias_table` passes another table, the mirror's).

### Resources and memory

GCN shaders get their resources as descriptors in SGPRs:

| Descriptor | Meaning |
|---|---|
| V# | buffer |
| T# | image |
| S# | sampler |

The descriptors come from user data directly, or through `s_load_*` from a pointer that itself comes from user data. A dataflow pass records the **source** of every descriptor that a memory instruction uses: user-data slot *k*, or a load at offset *o* through the pointer in slot *k*, nested as deep as needed. The list of sources is part of the shader's interface.

- **Buffers and scalar memory** are read and written through buffer device addresses (`VK_KHR_buffer_device_address`, `PhysicalStorageBuffer` in SPIR-V).
  - The base address and the other V# fields are data, read at run time.
  - MUBUF, MTBUF and `s_buffer_load_*` check the range the way the hardware does: from `num_records`, the stride, and the `idxen`/`offen`/`addr64` modes. Out-of-range reads return 0, and out-of-range writes are dropped. The game may rely on that. `s_load_*` without a V# has no range check.
  - Typed formats (MTBUF, or the format of a V#) are converted in the shader from raw dwords.
- **Vertex fetch** is ordinary buffer loading. PS4 vertex shaders load their attributes themselves, through a fetch subroutine called with `s_swappc_b64`. The translator inlines the fetch subroutine, which it receives as a second code input, so Vulkan's vertex input state stays empty. The eboot generates the fetch code at run time and puts its address into user-data dwords 0–1 of the vertex stage (VS, ES or LS), so the run time reads it from there at draw time and decodes it up to its `s_setpc_b64`. Offline, the harness can call the eboot's generator to get real fetch shaders ([gnm.md](../formats/gnm.md#fetch-shaders)).
- **Images and samplers** need bindings (as built: "Image sampling" under "Interface"). Each T# and S# source gets a binding of its own (not an element of a descriptor array): image i is binding i and sampler j is binding (number of images) + j, in a descriptor set per hardware stage. The SPIR-V image type needs dim, arrayed, multisample and the sampled type at compile time, but these come from T# memory, not from registers. They are therefore part of the ShaderKey and checked at draw time. A mismatch means a new translation.
- **Scratch** (private memory: swizzled MUBUF accesses through the scratch descriptor) becomes a per-invocation array. Its size comes from `SPI_TMPRING_SIZE` or `COMPUTE_TMPRING_SIZE` through the ShaderKey, because the array size is fixed at compile time. A size above a fixed limit is reported as unsupported.
- **FLAT** (CI): `flat_store_dword` writes guest memory at its 64-bit VGPR address plus the bias, under `if (active)`, with no range check (FLAT has no descriptor). The LDS and scratch apertures of the flat address space are not handled. The execution tests use it to write their results, as it needs no descriptor (#125). Loads and the other sizes come when a test or the corpus needs them.
- **LDS** becomes a `Workgroup` array of dwords. That storage class exists only in compute. Its size is `LDS_SIZE` of `COMPUTE_PGM_RSRC2` (bits 15-23) times 128 dwords (the granularity of `LDS_SIZE` is 128 dwords, 512 bytes, as shadPS4's `regs_shader.h` says, see `references.md`). A DS instruction in a shader with no LDS or more than 64 KB is an error. Done in `translate.cpp` (`ds_*` methods) and `lds.cpp` (which opcodes, by name), #128:
  - Reads and writes of 8 to 128 bits, and the `read2`, `write2` and `st64` forms. A sub-dword write merges its bits into the dword with one compare-and-swap update, because other lanes write the other bytes of the same dword, or the same byte, at the same time. Each lane's write is then whole, and one of the lanes that write the same byte wins, as on the hardware.
  - The 32-bit atomics: add, sub, min and max (signed and unsigned), and, or, xor, exchange, compare-swap and, with a return value, all of them. The ones without a SPIR-V atomic (rsub, inc, dec, mskor) update the dword in a compare-and-swap loop.
  - An access outside the LDS reads 0 and is dropped, as on the hardware, but at the end of the declared LDS. The translator ignores the clamp that M0 sets.
  - `s_barrier` is `OpControlBarrier` on the workgroup with acquire-release semantics on workgroup memory. That needs control flow that is uniform in the workgroup. SCC is per wave, so the branches on it only make the flow uniform within a wave. The translator assumes the rest: source compilers place barriers only where the whole workgroup arrives, and it does not check that.
  - Inside one wave there is no barrier on the hardware: the DS instructions of a wave reach the LDS in program order, so a lane reads what another lane of the wave wrote with an earlier instruction. Compilers drop `s_barrier` for workgroups of 64 threads, so this is common. SPIR-V gives no ordering or visibility between the invocations' non-atomic `Workgroup` accesses without a barrier: the driver may move lane i's load of `LDS[i ^ 1]` above its store to `LDS[i]`. Every DS instruction therefore starts with an `OpControlBarrier` of subgroup execution scope, acquire-release on workgroup memory (it orders the instruction after the earlier DS instructions of the subgroup, which is what the hardware's in-order LDS queue does). Branches depend only on SCC, which is per wave, so the control flow is uniform in a wave, and in a subgroup in exact mode. The guarded store of a write (`if (active)` and in range) is the exception: the next barrier needs the whole subgroup at its merge, so a shader with DS instructions also declares `MaximallyReconvergesKHR` (see "Reconvergence" above). A subgroup is the wave only in exact mode. In lane-local mode two lanes of a wave can be in different subgroups and see no order, so a shader that uses the LDS sets `ShaderInterface::wave_size_dependent` and the run time picks exact mode for it. The execution tests cover both a barrier between two waves and a lane reading its neighbour without one. Lavapipe runs a subgroup in lockstep, so the second passes without the subgroup barriers too, and `GcnTranslate.DsInstructionsWaitForTheSubgroup` checks that the module has them.
  - Not yet: the 64-bit and float atomics, the `src2` forms and `ds_wrxchg2`. They are reported as unsupported instructions.
  - `ds_swizzle_b32` is not an LDS access: it is a subgroup shuffle, translated with the cross-lane operations (#239, see "Cross-lane table and `subgroup_base`" below). It needs no `LDS_SIZE` and no DS ordering barrier.

  **GDS and ordered append** are reported as unsupported until a shader needs them.
- **Fork and join.** `s_cbranch_*fork` and `s_cbranch_join` (SI/CI) are reported as unsupported.

### Stage interfaces and ShaderKey

The register state a program starts with depends on pipeline registers, and so do the stage's inputs and outputs:

| Stage | Inputs | Outputs |
|---|---|---|
| VS | user data in SGPRs; vertex and instance index in VGPRs, per `SPI_SHADER_PGM_RSRC*` (`VGPR_COMP_CNT`) | `exp pos0` → `Position`, `exp param<n>` → `Location n` |
| PS | `SPI_PS_INPUT_ENA/ADDR` decide which VGPRs are set; `v_interp_p1`/`p2` pairs on attribute *n* → an interpolated input at the location from `SPI_PS_INPUT_CNTL_n`, its qualifier taken from the barycentrics it reads; `v_interp_mov` → `Flat` | `exp mrt<n>` → output *n*, converted per `SPI_SHADER_COL_FORMAT`; `exp mrtz` → `FragDepth`, plus stencil and sample mask per `SPI_SHADER_Z_FORMAT` |
| CS | user data; thread and group IDs per `COMPUTE_PGM_RSRC2` and `COMPUTE_NUM_THREAD_*` | memory only |

`ShaderKey` holds everything the generated SPIR-V depends on besides the code:

- the stage and the register values above;
- the float mode bits from `SPI_SHADER_PGM_RSRC1_*` or `COMPUTE_PGM_RSRC1` (`FLOAT_MODE`, `DX10_CLAMP`, `IEEE_MODE`), which change min/max, NaN and denormal behavior;
- the image type class of each T# source (above);
- the scratch size (`SPI_TMPRING_SIZE`, `COMPUTE_TMPRING_SIZE`);
- the push-constant offset of the stage's draw block ("Per-draw data");
- in the pixel stage, `SPI_SHADER_Z_FORMAT` and `DB_SHADER_CONTROL`, which decide what `exp mrtz` writes (see "Depth" under the graphics stages below);
- device-feature flags, which are not register values: `quad_control` says the device has `VK_KHR_shader_quad_control` (see "Quad control" under the graphics stages below).

The translation cache key is code hash + fetch code hash + ShaderKey + translator version. The cache lives in `$XDG_CACHE_HOME/bloodborne-linux/shaders/`. Offline, keys come from the footer metadata where it carries them, otherwise from test defaults.

Other stages (LS, HS, ES, GS for tessellation and geometry shaders) come later. The corpus uses all of them: 850 LS, 404 HS, 1,699 ES and 1,701 GS programs (with their copy shaders) of 20,218, plus 469 domain shaders that run as VS (`docs/formats/shader-binary.md`).

### SPIR-V builder

`bbgcn` has its own small module builder that emits the word stream directly, with the enum values from the Khronos SPIR-V headers. The baseline is Vulkan 1.3 (demote to helper invocation, `robustImageAccess`, subgroup size control are core there), and the target is SPIR-V 1.6. Every translated module must pass `spirv-val --target-env vulkan1.3` in the tests. Lavapipe supports all of it. Beyond the baseline, a module with subgroup operations needs `VK_KHR_shader_maximal_reconvergence` (see "Reconvergence" under Wave size). An optimizer (`spirv-opt`) can come later, behind the cache.

### Interface

```cpp
namespace bb::gcn {

enum class Stage { vertex, pixel, compute };

class GcnError : public std::runtime_error { /* offset() and word() of the failing instruction */ };

enum class Until { program_end, code_end, subroutine_end };  // the stop rule above, every
                                                     // word, or the first s_setpc_b64

                                Until until = Until::program_end);

std::optional<std::uint32_t> branch_target(const Instruction& inst);   // byte offset

    std::vector<ResourceSource> buffers;              // V# sources, in order of first use
    std::vector<ResourceSource> images, samplers;     // binding index = position

struct Translation { std::vector<std::uint32_t> spirv; ShaderInterface interface; };

                      std::span<const std::uint32_t> fetch,
```

Errors are exceptions, as in the loader and hooks (C++20, no `std::expected`). The exact members are settled by the decoder and translator issues, and recorded here when they are.

Decoder (`src/gpu/gcn/gcn.hpp`, #115):

- An `Instruction` holds its byte offset, its size in dwords (with the literal), the format, the format's opcode field, LLVM's mnemonic, and up to 2 destination and 4 source `Operand`s in the order of LLVM's syntax.
- An `Operand` has a kind, its size in dwords, the 8-bit operand code and a 32-bit value. The kinds so far: scalar register (by operand code, so the special registers keep their codes), inline constant (with its 32-bit pattern; on a 2-dword operand an integer constant sign-extends it, and a float constant means the f64 of the same number, so `value` holds the f64's high dword and the low dword is 0), literal, and the immediates of SOPK, SOPP and SMRD (hex value, count, branch offset, hardware register, wait counters, message, dword offset). The vector formats add their kinds and modifiers.
- The opcode tables are in `opcodes.cpp`, one per format, indexed by opcode.
- Register ranges of more than one dword must be aligned, to 2 dwords for pairs and to 4 above, as LLVM requires. A misaligned range is a `GcnError`, as is a reserved operand code or an operand code that the instruction can't use (a 64-bit `m0`, a constant or condition bit as SMRD offset register). Choices that LLVM restricts per instruction but the operand field allows, such as `m0` or `exec` as an SMRD destination, are decoded. The condition bits `src_vccz`, `src_execz` and `src_scc` (codes 251–253) are valid SOP sources of either size: the manual's operand-code table gives them no size limit, unlike the register pairs, and LLVM accepts them as 64-bit sources (`s_mov_b64 s[0:1], src_vccz` is `0xbe8004fb`), except for the instructions it takes only a register for (see the known differences below). The translator reads them as the bit zero-extended to the operand's size. As the SMRD offset register they are a `GcnError`, like every code from 128 except the literal, because the manual allows only a scalar register (code below 128) there, although LLVM accepts them (`s_load_dword s0, s[8:9], src_vccz` is `0xc00008fb`).
- An SMRD offset field of 255 with the immediate bit clear is a 32-bit literal offset (CI).
- `Until::subroutine_end` (#129) decodes up to and including the first `s_setpc_b64` (`is_setpc`), for the fetch subroutine, whose code is followed by a data dword. Running out of code before it is an error.
- DS (`src/gpu/gcn/ds_flat.cpp`, #119) is 2 dwords long and has its own opcode table, built from the operation families (with return, 64-bit, `src2`). A VGPR operand has the kind `vector`, with the register number as `code`. VGPR ranges need no alignment, but a range past `v255` is a `GcnError`. `Instruction::mem_offset` holds the 16-bit offset field (offset1 in the high byte, offset0 in the low byte), and `Instruction::flags` the modifier bits (`flag::gds`). The value of `ds_gws_init`, `ds_gws_sema_br` and `ds_gws_barrier` is read from the ADDR field, where LLVM encodes it.
- FLAT (CI, also in `ds_flat.cpp`; second part of #119) is 2 dwords long, with its own opcode table. Its address is always a VGPR pair (CI has no offset or `saddr`). The `glc`, `slc` and `tfe` bits go to `Instruction::flags` (shared with MUBUF). An atomic has a destination only with `glc` set, when it returns the old value, and `tfe` makes the destination one dword longer. The reserved bits (25 and 15-0 of the first dword, 22-16 of the second) are ignored. The loads (opcodes 8-15), stores (24-31) and atomics (48-64 and 80-96, without 52 and 84, the `rsub` that LLVM rejects for gfx7) decode; any other opcode is a `GcnError`.

Vector memory formats (`src/gpu/gcn/memory.cpp`, #120; MUBUF, MTBUF, MIMG and EXP):

- VGPR ranges have the kind `vector` (as in DS), whose `code` is the first register (0 to 255, also for the 9-bit source fields of the vector ALU formats). They add the kind `off`, an absent address. A VGPR range past `v255` is a `GcnError`.
- The fields that aren't operands go to `Instruction::mem_offset` (the offset) and `Instruction::flags` (as in DS): the address modes, `glc`, `slc`, `lds`, `tfe`.
- MUBUF operands in LLVM's order: vdata (the destination of a load, a source of a store or atomic; none for a load into LDS), the address (`off` without `idxen`/`offen`/`addr64`, one VGPR for either of `idxen` and `offen`, two for both or for `addr64`), the resource descriptor (4 SGPRs) and soffset (an SGPR, a special register or an inline constant; no literal). `tfe` adds a status VGPR to a load. An atomic with `glc` returns the old value into the first registers of vdata.
- MTBUF (opcodes 0 to 7, `tbuffer_load_format_x` to `xyzw` and the stores) decodes like MUBUF, except that bit 16 belongs to the opcode, so there is no `lds`. The data format (bits 19–22) and the numeric format (bits 23–25) go to `Instruction::dfmt` and `::nfmt`. LLVM prints them as `format:[BUF_DATA_FORMAT_X,BUF_NUM_FORMAT_Y]` right after soffset and before `idxen`. It leaves out the data format `8` (1) and the numeric format `UNORM` (0), and the whole field when both are left out. Data format 15 is `RESERVED_15` and numeric format 6 `SNORM_OGL`; the decoder accepts every value. LLVM rejects `tfe` on a typed load.
- EXP has `Format::exp`, the name `exp`, the target in `mem_offset` (mrt0 to mrt7 are 0 to 7, mrtz 8, null 9, pos0 to pos3 12 to 15, param0 to param31 32 to 63; 10, 11 and 16 to 31 are a `GcnError`), `flag::done`, `flag::compr` and `flag::vm`, and four sources in the order of the text: a VGPR, or `off` where its enable bit is clear. With `compr` each VGPR holds two 16-bit values, and the source at position N is vsrc[N / 2] (so `exp mrt0 v0, v0, v1, v1 done compr vm`). LLVM sets the enable bits in pairs under `compr`; an `en` with a single bit of a pair (`0x1`) decodes and prints but LLVM encodes the text differently. `disassemble()` prints an export as one line (`detail::export_text()`), as the target comes before the operands.
- MIMG (opcodes 0 to 111, 93 defined: the loads, stores, `get_resinfo`, atomics, `sample*`, `gather4*`, `get_lod` and the `sample_cd*` family) is built from the operation families in loops. The instruction does not say how many coordinates the address has, as that depends on the dimension of the image descriptor. The decoder gives the address the shortest range LLVM's assembler accepts (1 dword plus one each for the compare value `_c`, the offset `_o` and, for `_d`, `_b` and `_cd`, the derivatives or bias, where the LOD and clamp forms add none), so the text round-trips; the translator must take the real count from the descriptor type. Operands in LLVM's order: vdata (the destination of a load, sample or gather; a source of a store or atomic), vaddr, the image descriptor (always 8 SGPRs, also with `r128`, which uses the first 4) and, for `sample*`, `gather4*` and `get_lod`, the sampler (4 SGPRs). vdata is one register per `dmask` bit (at least one) and four for a gather, plus one status register under `tfe`. The hardware writes that status register under `lwe` alone as well, but LLVM's assembler counts only `tfe` (it accepts `image_sample v0, v4, s[8:15], s[12:15] dmask:0x1 lwe` and rejects `v[0:1]`), so `dst` follows LLVM for the round trip. Translator rule: the range of vdata is `dst` for loads, samples and gathers and `src[0]` for stores and atomics (an atomic with `glc` returns its old value there, and with `tfe` or `lwe` the status too). With `tfe` the status register is the last one of that range; with `lwe` and no `tfe` it is the register right after it. `dmask` goes to `Instruction::mem_offset` and prints as `dmask:0x…` unless it is 0; `unorm`, `r128`, `lwe` and `da` are new flags, `glc`, `slc` and `tfe` are shared, and they print in the order `unorm glc slc r128 tfe lwe da`. LLVM rejects a `gather4` whose `dmask` does not have exactly one bit, and an atomic whose `dmask` is not 1 or 3 (`image_atomic_cmpswap` and `image_atomic_fcmpswap` take 3 or 15 instead); the decoder accepts all of them. `image_atomic_rsub` exists here (opcode 19), unlike `buffer_atomic_rsub`. Bits marked reserved are ignored.
- `lds` on a store or atomic is a `GcnError`. `buffer_atomic_rsub` (opcode 52) and its 64-bit form (84) are left out, because LLVM rejects them for gfx7. Bits marked reserved are ignored.

Disassembler (`src/gpu/gcn/disassemble.cpp`, #115):

- `disassemble()` prints one line in LLVM's gfx7 syntax, checked by assembling it with `llvm-mc`. Literals, SOPK immediates and SMRD offsets print in hex, branch offsets as signed dwords. SOPP counts and the literal of `s_setreg_imm32_b32` print as LLVM prints them: in decimal from −16 to 64 (counts are unsigned, so 0 to 64), otherwise in hex.
- A SOP2, SOP1 or SOPC literal whose value LLVM would encode as an inline constant prints as `lit(0x…)`: 0 to 64, −16 to −1 and the float constants on 32-bit operands, and only 0 to 64 on 64-bit operands, where LLVM reads the literal as a 64-bit integer.
- `hwreg()`, `sendmsg()` and the `s_waitcnt` counters print in LLVM's named form where it has one. Other values print as the raw number, which LLVM accepts: `s_waitcnt` with bit 7 or bits 12–15 set (gfx7 has a 4-bit lgkmcnt), and messages LLVM has no name for, such as `MSG_GS` with `GS_OP_NOP`.
- Known differences, for the corpus round trip's list: LLVM rejects `m0` and `exec` (or either half) as an SMRD destination, it takes only a register (no inline constant or literal) as the source of `s_setpc_b64`, `s_rfe_b64`, `s_cbranch_join`, `s_movrels_b32` and `s_movrels_b64`, nor a condition bit (`src_vccz`, `src_execz`, `src_scc`) as the 64-bit source of `s_setpc_b64`, `s_rfe_b64` and `s_movrels_b64` (the other three take them), and no literal as either source of `s_cbranch_g_fork`, it encodes an SMRD literal offset of 255 or less in the immediate form (also with `lit()`), it accepts a condition bit as SMRD offset register, which we reject, it has no gfx7 syntax for `s_mov_regrd_b32`, `s_mov_fed_b32` and `s_getreg_regrd_b32`, and fields that an instruction doesn't use (the immediate of `s_endpgm`, the base of `s_memtime`, every field of `buffer_wbinvl1` and `buffer_wbinvl1_vol`, the vdata field of a MUBUF load into LDS, reserved bits) don't appear in the text. In MUBUF, LLVM rejects `tfe` on stores, atomics and loads into LDS, `addr64` together with `idxen` or `offen`, and `lds` on loads other than `buffer_load_format_x`, `buffer_load_dword` and the byte and short loads. Where only LLVM's printed text differs: it prints raw `s_waitcnt` and `s_sendmsg` values in its field syntax (for `s_waitcnt` without the bits outside the fields), and an `s_setreg_imm32_b32` value with a float constant's pattern as that float, which its assembler reads back as a different value, so ours stays in hex.
- The round-trip tests (`tests/gpu/gcn/roundtrip_test.cpp`) assemble our text with `llvm-mc` and compare both the words and LLVM's printed text, for every scalar opcode of the tables except the three LLVM has no syntax for (checked by hand), every operand code that decodes as a 32- or 64-bit source and destination, the SMRD offset forms and the SOPP and SOPK immediates.
- DS offsets print in decimal as `offset:N`, or `offset0:N offset1:M` for the two-address instructions, and are left out when 0. The `ds_swizzle_b32` pattern prints in hex (LLVM prints its `swizzle()` form and accepts the number). Known differences: LLVM rejects GWS instructions and `ds_ordered_count` without `gds` and `ds_nop` with it, it has no gfx7 syntax for `ds_condxchg32_rtn_b128`, it has no gfx7 syntax for TFE on FLAT, and fields that an instruction doesn't use (unused register fields, the offset of `ds_nop`, which LLVM's `ds_nop` doesn't take, and the VDST of a FLAT atomic without `glc`) and the reserved bits of DS and FLAT don't appear in the text. FLAT prints its operands in LLVM's order (destination, address pair, data), then `glc`, `slc`, `tfe`.
- MUBUF prints the operands, then the fields that are set in LLVM's order: `idxen`, `offen`, `addr64`, `offset:` (decimal), `glc`, `slc`, `lds`, `tfe`.
- `bb-gcn disasm [--all] FILE` prints the program at the start of a file up to its final `s_endpgm`, or with `--all` every whole dword. Each line has the text, then the byte offset and the words as a comment.

Vector ALU formats (`src/gpu/gcn/vop.hpp`, `vop_opcodes.cpp`, `vop_decode.cpp`, #118). VOP1, VOP2, VOPC, VOP3 and VINTRP are decoded (VOP3 and VINTRP in `vop3_decode.cpp`).

- `decode.cpp` hands every word with bit 31 clear to `detail::decode_vop()`, and words with bits 26-31 `0x34` and `0x32` to `decode_vop3()` and `decode_vintrp()`. The first tells VOP1 (bits 25-31 are `0x3f`), VOPC (`0x3e`) and VOP2 (any other value) apart. Scalar operand fields are decoded by `detail::scalar_operand()`, the same code as in the scalar formats.
- A VGPR operand has the kind `vector`, with the register number as `code` as in DS (the 9-bit source field holds 256 + the register number). VGPR ranges need no alignment, but must end at `v255`.
- Operand code 254 (LDS_DIRECT) is valid only in src0 of a vector ALU instruction and only as a 32-bit source, as in LLVM. It has the kind `scalar` with its code, like the other special sources, and prints as `src_lds_direct`. The scalar formats still reject it.
- The mnemonic carries LLVM's `_e32` suffix, except for `v_nop`, `v_clrexcp` and `v_readfirstlane_b32`, which LLVM prints without one. `v_readfirstlane_b32` takes an SGPR operand code in the vdst field; a constant there is an error.
- Literals with an inline value print as `lit(0x…)`, with the 32-bit rule of the scalar formats. On a 64-bit operand llvm-mc reads a literal as the f64's high dword, so 0 to 64 and the high dwords of the float constants get `lit()` there. On an f16 source (src0 of `v_cvt_f32_f16`, marked in the opcode table) llvm-mc reads a literal as 16 bits, so 0 to 64, `0xfff0` to `0xffff` (−16 to −1) and the f16 patterns of the float constants (`0x3800`, `0x3c00`, `0x4000`, `0x4400` and their negatives) get `lit()` there.
- VOP2 has opcodes 0 to 49. The implicit VCC of `v_cndmask_b32`, `v_add_i32`, `v_sub_i32`, `v_subrev_i32`, `v_addc_u32`, `v_subb_u32` and `v_subbrev_u32` is an explicit operand (kind `scalar`, code `vcc`, 2 dwords): the destination pair (`v_add_i32_e32 v1, vcc, v2, v3`), and for `v_cndmask_b32`, `v_addc_u32`, `v_subb_u32` and `v_subbrev_u32` the last source. `v_readlane_b32` has an SGPR destination in the vdst field, and both it and `v_writelane_b32` take the lane select as an 8-bit scalar operand in the vsrc1 field (SGPR, special register or inline constant; code 255 is an error, because the manual defines a trailing literal only for src0 and K). `v_madmk_f32` and `v_madak_f32` always have a literal K (after src0, or after vsrc1), printed in hex without `lit()`. `v_readlane_b32`, `v_writelane_b32`, `v_madmk_f32` and `v_madak_f32` print without `_e32`.
- VOPC has 196 opcodes, all with VCC as the destination. The float compares are at the base of the family (`cmp` 0x00, `cmpx` 0x10, `cmps` 0x40, `cmpsx` 0x50) plus 0x20 for f64 plus one of 16 conditions (`f lt eq le gt lg ge o u nge nlg ngt nle neq nlt tru`). The integer compares are at 0x80, plus 0x40 for unsigned, 0x20 for 64-bit and 0x10 for `cmpx`, plus one of 8 conditions (`f lt eq le gt ne ge t`). The class compares are at 0x88, plus 0x20 for f64 and 0x10 for `cmpx`; their mask in vsrc1 is one dword. The 64-bit compares take a VGPR pair in vsrc1.
- VOP3 (2 dwords, opcode in bits 17-25) has one table: the `_e64` forms of VOPC at 0, of VOP2 at 0x100 and of VOP1 at 0x180 (all of them except `v_madmk_f32` and `v_madak_f32`, which have no VOP3 form), and the 56 VOP3-only opcodes at 0x140 to 0x177 (`v_mad_*`, `v_fma_*`, `v_bfe_*`, `v_min3_*`, the 64-bit float and shift instructions, `v_div_*`, `v_mad_u64_u32`, `v_mqsad_u32_u8` and the like). Operand sizes come from the table, not the encoding. The `_e32` operands that are implicit become real ones: VCC of the compares and of `v_cndmask_b32`, `v_add_i32` and the carry instructions is an SGPR pair, in vdst for the compares (8 bits, VOP3a), in bits 8-14 for the carry instructions, `v_div_scale_*` and `v_mad_u64_u32`/`v_mad_i64_i32` (VOP3b), and in src2 for the mask of `v_cndmask_b32` and the carry in of `v_addc_u32`, `v_subb_u32` and `v_subbrev_u32` (scalar operands only, no VGPR). `v_div_fmas_*` keeps its implicit VCC.
- Modifiers: `Instruction::neg` and `abs` have bit i set for source i, `omod` is the output modifier (1 `mul:2`, 2 `mul:4`, 3 `div:2`) and `flag::clamp` the clamp bit. They print as `-x`, `|x|`, `-|x|`, then ` clamp` and ` mul:2`. An inline constant with `neg` prints `neg(1.0)`, because `-1.0` is another constant. VOP3b has no abs and no clamp. The decoder rejects a modifier on a mask, carry in or lane select, or on a source that the instruction doesn't have, reserved bits (12-16 in VOP3a, 15-16 in VOP3b), a literal (VOP3 has no slot for one), `src_lds_direct` other than as a 32-bit src0, and a VGPR where a scalar operand is required. The unused source fields of an instruction are ignored (LLVM writes 0). `v_nop_e64` and `v_clrexcp_e64` use no fields: their modifier and source fields are ignored, but the reserved bits are still rejected.
- VINTRP (1 dword) has `v_interp_p1_f32`, `v_interp_p2_f32` (a VGPR source) and `v_interp_mov_f32` (a parameter instead: 0 `p10`, 1 `p20`, 2 `p0`; 3 to 255 are errors). The attribute operand (kind `interp_attr`) holds attribute * 4 + channel and prints as `attr3.y`. Attributes 0 to 32 are valid, as in LLVM.
- Known differences of VOP3, the modifiers by operand and result type (checked by a sweep of every opcode with `llvm-mc -mcpu=bonaire`; the cases in the test are examples of each group): LLVM rejects `neg` and `abs` on a source that isn't a float: the sources of integer instructions, src0 of the integer-to-float conversions (`v_cvt_f32_i32`, `v_cvt_f32_u32`, `v_cvt_f32_ubyte0` to `3`, `v_cvt_f64_i32`, `v_cvt_f64_u32`, `v_cvt_off_f32_i4`), src1 of `v_ldexp_f32`, `v_ldexp_f64`, `v_trig_preop_f64`, `v_cvt_pkaccum_u8_f32` and the mask of the class compares, and src1 and src2 of `v_cvt_pk_u8_f32` (the float sources of those take them, as do those of the float-to-integer conversions). It rejects `clamp` unless the result is a float, so not on compares, integer instructions, the float-to-integer conversions (`v_cvt_i32_f32`, `v_cvt_flr_i32_f32`, `v_cvt_u32_f64`, `v_frexp_exp_i32_f32` and the like), `v_cvt_pknorm_i16_f32`, `v_cvt_pknorm_u16_f32`, `v_cvt_pkaccum_u8_f32`, `v_cvt_pk_u8_f32` and `v_cndmask_b32`. It rejects `omod` unless the result is a float, except on `v_cvt_i32_f32`, `v_cvt_u32_f32`, `v_cvt_i32_f64`, `v_cvt_u32_f64` and `v_frexp_exp_i32_f64`, which take it with `neg` and `abs`: `v_cvt_i32_f32_e64 v1, -v2 mul:2` assembles and `v_cvt_i32_f32_e64 v1, v2 clamp` doesn't. So `omod` is also rejected on `v_cvt_flr_i32_f32`, `v_cvt_rpi_i32_f32`, `v_frexp_exp_i32_f32`, `v_cvt_pknorm_i16_f32`, `v_cvt_pknorm_u16_f32`, `v_cvt_pkaccum_u8_f32`, `v_cvt_pk_u8_f32`, the compares and `v_cndmask_b32`. LLVM also rejects more than one distinct SGPR among the sources of one instruction (the constant bus; also an SGPR next to the implicit VCC of `v_div_fmas_*`, and an SGPR source next to the mask or carry in of `v_cndmask_b32`, `v_addc_u32`, `v_subb_u32` and `v_subbrev_u32`), and an inline constant as that mask or carry in (`v_cndmask_b32_e64 v1, v2, v3, 0`). LLVM has no VOP3 form of `v_readlane_b32`, `v_writelane_b32`, `v_readfirstlane_b32` and `v_mov_fed_b32`, which the decoder accepts and prints with `_e64`. It writes `v_nop` and `v_clrexcp` for the VOP3 form of those, but only the `_e64` spelling assembles to it, which is what the disassembler prints.
- Known differences: LLVM rejects `m0` as the destination of `v_readlane_b32`, two different SGPRs (or an SGPR and a literal, or an SGPR and VCC) among the sources of one VOP2 instruction, and an SGPR, constant or literal as src0 of `v_readlane_b32` or a VGPR as src0 of `v_writelane_b32`; its constant bus allows one scalar value. `v_mov_fed_b32` has no gfx7 syntax in LLVM, LLVM rejects `m0` as the destination of `v_readfirstlane_b32` and takes only a VGPR or `src_lds_direct` as its source, it rejects a literal above `0xffff` on an f16 source (also with `lit()`), and the unused fields of `v_nop` and `v_clrexcp` don't appear in the text.

SPIR-V builder (`src/gpu/gcn/spirv_builder.hpp`, #122):

- `SpirvBuilder` collects one module and returns its words. Each call appends to the section of the logical layout it belongs to, so callers may declare a type or a decoration in the middle of a function.
- Types and constants are shared by value: asking twice gives the same id. Arrays, runtime arrays and structs get a new id on every call, because their layout decorations belong to one use: a laid-out array in a buffer block and a plain one for registers or LDS must stay distinct types. Capabilities, extensions and extended-instruction imports are recorded once each.
- `variable` declares a global in any storage class but `Function`. `local_variable` may be called anywhere in a function, and its `OpVariable` goes to the start of the first block, where SPIR-V requires it.
- `op` takes an optional result id from `id()`, for an instruction that an earlier `OpPhi` already names (a loop's back-edge value).
- `op` and `op_void` emit any instruction inside a block, with enum operands through `spirv_word`. Misuse (an instruction outside a block, a block without a terminator, nested functions, a parameter after the first block) throws `std::logic_error`. Validity is checked by `spirv-val`, not by the builder.
- Enum values come from `spirv/unified1/spirv.hpp11`.
- It has the module sections, capabilities, extensions, extended-instruction imports, memory model, entry points, execution modes, names, decorations and member decorations, the scalar, vector, array, runtime-array, struct, pointer and function types, scalar constants (`constant` for any type, helpers for bool, u32, i32 and f32), composite and null constants, global and local variables, functions and blocks.
- Tests: `tests/gpu/gcn/spirv_val.*` pipes a module to `spirv-val --target-env vulkan1.3 -` and returns its messages. The tests skip without the tool. A validated compute module covers what the translator needs there: the draw block through a push constant and a `PhysicalStorageBuffer64` address, subgroup ballot, broadcast with a dynamic lane and shuffle, a `Workgroup` array, a `GLSL.std.450` instruction, float and signed constants, an extension, a function call with a parameter, a selection and a loop with a phi. A negative test checks that a module without a needed capability is rejected. The word-encoding tests build fragments that `spirv-val` would reject (no capability, undefined ids), so they compare words only; every builder call they make also appears in the validated module.
- Image types (#129): `type_image(sampled_type, dim, depth, arrayed, multisampled, sampled, format)` (the `OpTypeImage` operands in order, the format `Unknown` by default), `type_sampler()` and `type_sampled_image(image)`, shared by value like the other types. `SpirvBuilder.FragmentModuleValidates` builds a fragment module that `spirv-val` accepts: an interpolated `NoPerspective` input, two render target outputs, a texture sampled through a separate image and sampler, and `OpDemoteToHelperInvocation` under a condition. The vertex modules come from the translator (`tests/gpu/gcn/stages_test.cpp`).
- The `SPV_KHR_quad_control` names (`QuadControlKHR`, `QuadDerivativesKHR`, `RequireFullQuadsKHR`) are newer than some distributions' headers (Ubuntu 24.04's in CI), so `src/gpu/gcn/stages.cpp` and its test spell out their values (5087, 5088, 5089) instead of taking them from the headers (see "Quad control" under the graphics stages below).

Translator (`src/gpu/gcn/translate.hpp`, #125, first part):

- `translate()` decodes the program, builds the CFG and emits one entry point `main` through the structurizer: `GLCompute` with a `LocalSize` in compute, and the stage's execution model otherwise (`Vertex`, with no `LocalSize`, see "Graphics stages" below). `fetch` is inlined in the vertex stage ("Fetch subroutine" under "Graphics stages" below) and ignored elsewhere. Everything that isn't supported yet throws `GcnError` with a message that names it (`unsupported instruction v_cmp_lt_u32_e32`), at the instruction's offset and first word; key errors have offset and word 0.
- `ShaderKey` so far: `stage` (`compute`, and `vertex` since #129, see "Graphics stages" below), `pgm_rsrc1` (the raw `COMPUTE_PGM_RSRC1`; only the float mode matters, see the float part below), `pgm_rsrc2` (the raw `COMPUTE_PGM_RSRC2`: `USER_SGPR`, at most 16, sets the user SGPRs; the fields that would add initial registers, `SCRATCH_EN`, `TGID_*_EN`, `TG_SIZE_EN` and `TIDIG_COMP_CNT`, are rejected; `LDS_SIZE` sizes the LDS array and a DS instruction in a shader with none is an error; the others, `TRAP_PRESENT`, `EXCP_EN_MSB` and `EXCP_EN`, don't change the initial registers and are ignored) and `num_threads` (`NUM_THREAD_FULL` of `COMPUTE_NUM_THREAD_X/Y/Z`, the `LocalSize`). The key holds raw register values, so the PM4 side copies them. `ShaderInterface` has `wave_size_dependent`, true for the cross-lane operations and for any DS instruction (the LDS shares data across lanes, see the LDS part), and `mask_round_trip` (see the cross-lane part below).
- The prologue reads the draw block through the push constant: `user_data[0..USER_SGPR-1]` into s0 and up, and `address_bias`. v0 is `LocalInvocationId.x` (the thread ID in X), and the lane ID is `LocalInvocationIndex & 63`.
- Registers are function variables, declared on first use: a u32 per SGPR, M0 and VGPR, and a bool each for EXEC (this lane's bit, starting true) and SCC. The dwords of EXEC, VCC and the mask pairs are read as values through a ballot and written as values bit by bit (cross-lane part below); other special registers and the condition bits are unsupported operands.
- EXEC takes `s_mov_b64` of a constant or of itself (0 and −1 are constant bits, any other constant gives the bit at the lane ID; an integer constant sign-extends, a float constant is the f64's pattern) and 32-bit writes to `exec_lo`/`exec_hi` (the lanes of that half take their bit of the value).
- Scalar: `s_mov_b32`, `s_mov_b64` (values), `s_add_u32` and `s_sub_u32` (SCC is the carry or borrow), branches on SCC. Vector (VOP1, VOP2, VOP3 without modifiers): `v_mov_b32`, `v_and_b32`, `v_or_b32`, `v_xor_b32`, `v_lshlrev_b32`, each written as `select(active, new, old)`. `s_nop` and `s_waitcnt` emit nothing.
- Tests: `tests/gpu/gcn/translate_test.cpp` translates every program in `tests/gpu/programs/` and an inline program (scalar ALU, a loop on SCC, VOP1, VOP2 and VOP3 encodings) with 16 user SGPRs (5 since the masks part) and runs `spirv-val` on them, and checks the error messages. `tests/gpu/runner/translate_exec_test.cpp` runs `exec_lanes` (lane bits of EXEC from both halves and from a constant, predicated VALU results and stores), `exec_writes` (`s_mov_b64` of EXEC to itself, with the constants 0 and -1, with a float constant, and by a 32-bit `s_add_u32` on one half), and `scalar_loop` (a loop on SCC, branches on the SCC of an `s_add_u32` with and without carry, a 64-bit scalar move, and `v_xor_b32_e64` with an SGPR as src1) as one workgroup of 64 lanes on lavapipe.
- Masks, VALU, SALU and branches (#125, as built):
  - **Type pass** (`collect_masks`, before the prologue). VCC and EXEC are masks. An SGPR pair is a mask when it is a mask operand of a `v_cmp*`/`v_cmpx*` (destination), `v_cndmask_b32` (the select), a carry op (`v_add_i32`, `v_sub_i32`, `v_subrev_i32`: the carry out; `v_addc_u32`, `v_subb_u32`, `v_subbrev_u32`: carry out and carry in), `s_<op>_b64` or `s_<op>_saveexec_b64` of the bitwise family, or when an `s_mov_b64` copies it to or from a mask (repeated until nothing changes). Mask pairs are bool function variables keyed by the pair's first SGPR, like EXEC. These pairs have one type for the whole program. The initial registers (user data, `TGID_X`, the PS primitive mask; a pair that starts in them counts as a whole) have one per instruction instead, from a forward dataflow over the CFG (`StartState`): the prologue fills them as values, and a dword holds a mask from the instruction that writes one to it until a value overwrites it, so a pair can serve as a mask register after its last read as a value. Two errors, both about reading an initial register: `user data s<n> is used as a mask` (a mask operand, or the source of an `s_mov_b64` into a mask, that still holds the value) and `initial s<n> is a value or a mask, depending on the path` (a read where paths that disagree meet). Until the cross-lane part, a mask dword used as a value was an error too (`s<n> is used as both a mask and a value`); it is now a ballot, and a value that passes through a mask pair sets `mask_round_trip` (cross-lane part below).
  - **VALU mask results** are written as `active && result`: `v_cmp_<cond>_<i32|u32>` and `v_cmpx_...` (conditions f, lt, eq, le, gt, ne, ge, t; the VOP2 form writes VCC, the VOP3 form its SGPR pair; `v_cmpx` also sets EXEC), and the carry out of the carry ops. Carry and borrow outs are computed from the unsigned wrap (`r < a` for an add, `a < b` for a subtract), the carry ins by a second step on the intermediate, `v_subrev_i32` and `v_subbrev_u32` swap the sources. `v_cndmask_b32` selects src1 where the mask bit is set. The modifiers rejection of the vector ALU applies to all of them. Float compares are in the float part below; 64-bit compares are still unsupported.
  - **SALU**: `s_<op>_b32` of the family (and, or, xor, andn2, orn2, nand, nor, xnor) on values, with SCC = result != 0. `s_<op>_b64` on lane bits (`bool` operations on this lane's bit, with no `active` term, since the SALU ignores EXEC) with SCC = `any` of the result. `s_<op>_saveexec_b64 sdst, ssrc`: sdst = old EXEC, EXEC = op(ssrc, old EXEC), SCC = `any` of the new EXEC. `any` is `OpGroupNonUniformAny` over the subgroup (capability `GroupNonUniformVote`) and sets `wave_size_dependent`: it equals the wave's value only when the subgroup is the wave.
  - **SOPC and branches**: `s_cmp_<cond>_<i32|u32>` sets SCC. The six SOPC conditions are eq, lg, gt, ge, lt and le (not equal is spelled `lg`, where the VALU compares say `ne`), and there is no f, t or `cmpx` form. `s_cbranch_vccz`/`vccnz` test `any` of VCC and `s_cbranch_execz`/`execnz` `any` of EXEC over the subgroup (`condition()` in the structurizer callback), so these four set `wave_size_dependent` through `cross_lane()`; the branches on SCC don't. The SCC branches and the mask branches go through the same CFG and structurizer. A loop that each lane leaves at its own time (`s_and_b64 exec, exec, vcc` then `s_cbranch_execz`) exits when no lane of the subgroup is left, and the lanes that are done sit out the remaining rounds through EXEC.
  - **Tests**: `mask_alu` (compares into VCC and into SGPR pairs, signed and unsigned, `v_cndmask_b32` from VCC and a pair, carry in and out through VOP2 and VOP3b, a compare under a partial EXEC, `v_cmpx_e64` into a pair, and the carry and borrow outs with a carry in, `v_subrev_i32` and `v_subbrev_u32`, over every combination of carry in and operand), `mask_cmp` (all 16 conditions with a negative operand, each as one bit accumulated with `v_addc_u32 v, vcc, v, v, vcc`), `mask_branch` (the EXEC loop with `s_cbranch_execz`, branches on VCC with and without lanes, on SCC after `s_cmp_lt_i32` and `s_cmp_lt_u32` with a negative operand, and on EXEC; lane 3 of every 8 has the bit, so every subgroup of 8 or more agrees), `mask_exec` (nested predication with `s_and_saveexec_b64`, `s_mov_b64` to EXEC from a saved mask, `v_cmpx`, the eight bitwise operations on two masks over every combination of bits, `s_or_b64` and `s_nor_b64` under a partial EXEC with result bits outside EXEC, and `s_andn2_saveexec_b64` and `s_orn2_saveexec_b64` with the saved and the new EXEC checked per lane), `mask_sopc` (all 12 `s_cmp_*` opcodes, one SCC bit each, on -2 against 1 and on equal operands) and `mask_scc` (branches on the SCC of `s_and_b64`, `s_andn2_b64`, `s_orn2_b64`, `s_nor_b64`, `s_and_saveexec_b64` and `s_xor_saveexec_b64`, with data that is the same in every lane and run both ways, the SCC of two `s_<op>_b32` whose result is 0 and all ones, and a chain of the eight operations on values), plus translator error tests. The execution tests use 5 user SGPRs, so that the masks sit above the user data.
- Cross-lane table and `subgroup_base` (#125, as built; stacked on the VALU part of the masks):
  - **Ballot.** A mask read as a value (a dword of EXEC, VCC or a mask pair, as a 32-bit source, or the whole pair as the 64-bit source of a scalar count) is `OpGroupNonUniformBallot` of this lane's bit, its low two words as a u64 shifted left by `subgroup_base`. So bit *i* of the subgroup lands on wave lane `subgroup_base + i`, and the bits of other subgroups are 0. `subgroup_base` is `lane_id - SubgroupLocalInvocationId`, computed where it is used. A 32-bit value written to a mask dword (`s_mov_b32 s8, s2` where `s[8:9]` is a mask, `exec_lo`, `vcc_hi`) sets the lanes of that half to their bit, as for EXEC before.
  - **Values in mask pairs.** The type pass is flow-insensitive, so this applies to any value, not only to lane masks: a compiler that reuses an SGPR pair for a `v_cmp` result in one place and for an address or a constant in another stores the address as lane bits and reads it back through a ballot. That round trip is exact only when the subgroup has all 64 lanes. In a smaller subgroup (8 lanes on lavapipe, 32 on many GPUs, or a workgroup that isn't a multiple of 64) the bits of the other subgroups' lanes read as 0, without an error. `ShaderInterface::mask_round_trip` marks these shaders: a value written to VCC or an SGPR mask pair (a 32-bit write to one of its dwords, or an `s_mov_b64` or `s_<op>_b64` with a constant source other than 0 and -1) that is read as a value somewhere, from that pair or from a pair it moves to, directly or through other pairs. A move is an `s_mov_b64` copy, either source of an `s_<op>_b64` into its destination, and `s_<op>_saveexec_b64`, whose source goes into EXEC and whose destination takes EXEC. EXEC is left out as a source and a reader (a value can only pass through it to another pair), because its value is a lane mask by definition and its bits outside the subgroup belong to the other subgroups like those of any ballot. The corpus report (item 9) counts the marked shaders; if real shaders reuse pairs this way, the fix is a flow-sensitive type pass that gives each definition of a pair its own representation.
  - **Scalar counts** (SOP1, 32- and 64-bit sources, values or masks): `s_bcnt0`/`s_bcnt1` (SCC: the count isn't 0), `s_ff0`/`s_ff1` (first clear or set bit from the LSB), `s_flbit_i32_b32`/`_b64` (first set bit from the MSB) and the signed `s_flbit_i32`/`s_flbit_i32_i64` (first bit from the MSB that differs from the sign); a search that finds nothing gives -1. Vulkan allows `OpBitCount` and the `GLSL.std.450` `FindILsb`/`FindUMsb` only on 32 bits, so a 64-bit source is handled as two dwords.
  - **Lanes.** `v_readlane_b32` broadcasts from wave lane `src1 & 63`, `v_readfirstlane_b32` from the lowest set bit of the EXEC ballot (lane 0 when there is none). Both convert the wave lane to `lane - subgroup_base` and use `OpGroupNonUniformBroadcast` with that id when it lies below `SubgroupSize`, and give 0 otherwise. `v_writelane_b32` is lane-local: `lane_id == (src1 & 63) ? src0 : old`, ignoring EXEC. `v_mbcnt_lo_u32_b32`/`_hi` are lane-local too: `src1` plus the bits of `src0` below the lane (all 32 for `_lo` above lane 31, none for `_hi` below lane 32), predicated like other VALU results. Only a mask read as `src0` (`exec_lo`, a mask pair's dword) takes a ballot; the usual `v_mbcnt_lo_u32_b32 v, -1, 0` takes none.
  - **`ds_swizzle_b32`** (#239, `ds_swizzle` in `translate.cpp`). Lane *i* takes the VGPR of wave lane *j* of its wave, or 0 when that lane is inactive (the rule is from the GPUOpen cross-lane article, as `thread_valid[j] ? thread_in[j] : 0`; the Sea Islands manual only names the instruction, and shadPS4's plain shuffle does not model it). The 16-bit pattern is offset1:offset0. Bit 15 set is a quad permutation: *j* is the aligned quad of *i* with the lane picked by bits 2k+1:2k, *k* being *i* mod 4. Otherwise it is a bit mask on the lane within its group of 32: *j* = ((*i* & and) | or) ^ xor, with and in bits 4:0, or in bits 9:5 and xor in bits 14:10, and the group number kept. The FFT and rotate modes are GFX9 and later and do not exist in the encoding here. The pattern is a constant, so the translator builds *j* from the lane ID with a few bit operations (no special case per pattern), zeroes the value in inactive lanes first (`select(active, v, 0)`), and shuffles it with `OpGroupNonUniformShuffle` (capability `GroupNonUniformShuffle`) through the same wave-lane-to-subgroup-lane conversion as `v_readlane_b32` (`subgroup_lane`): a source in another subgroup gives 0 in lane-local mode. A source that does not exist also gives 0: a subgroup is not full when the workgroup size is not a multiple of the subgroup size, and a shuffle from a missing invocation is undefined, so `shuffle` also tests the source's bit in `OpGroupNonUniformBallot(true)` (`OpGroupNonUniformBallotBitExtract`). The result is written under EXEC like any VALU result. It sets `wave_size_dependent` through `cross_lane()`, and the module declares maximal reconvergence. The GPUOpen article and shadPS4's `data_share.cpp` agree on the layout (`docs/references.md`). Test: `ds_swizzle` (exec test, run with 64 lanes and with a workgroup of 42 whose last subgroup is not full; at subgroup sizes 4 and 8 (lavapipe's is 8) the quad patterns 0x801b and 0x80aa send lanes 40 and 41 to the missing lanes 42 and 43 of their own subgroup, so that run reaches the source-exists check. Stages: quad permutations, including a broadcast and one that repeats a lane, and bit masks with xor 1, 16 and 31, with and 0, with or, and with all three, over 64 lanes, with the expected values worked out per subgroup size; two stages with the lane 3 of each quad inactive, where the lane that reads an inactive lane gets 0 and the inactive lane keeps its value) and `GcnTranslate` (`WaveSizeDependence`, the error cases). GcnCoverage with it: the opcodes that translate alone go from 120 to 121 of 208 probed, and the instructions whose opcode translates from 1,307,483 to 1,309,324 of 1,512,771 (86.4% to 86.6%; the 1,841 `ds_swizzle_b32` instructions of 192 distinct programs). No whole program translates yet, other gaps stop them first.
  - **Wave size**: every ballot, broadcast and `any` sets `wave_size_dependent` (see "Wave size" above for why the analysis is conservative), adds the `GroupNonUniform` and `GroupNonUniformBallot` capabilities (`any` also adds `GroupNonUniformVote`) and makes the module declare `MaximallyReconvergesKHR` (see "Reconvergence" above).
  - **Tests**: `cross_lane` (`v_readfirstlane_b32` of the thread ID, which checks that `subgroup_base` is uniform and a multiple of the subgroup size, the subgroup size counted from `exec_lo` and `exec_hi`, `v_mbcnt` with -1 and with a mask's dwords, the 64-bit counts of a mask pair written as two values, `s_ff1_i32_b32` of its high dword, `s_bcnt1_i32_b32` of `vcc_lo` with a branch on its SCC, the signed `s_flbit` on values, `v_readlane_b32` with a lane select above 63, and `v_readfirstlane_b32` and `v_writelane_b32` under a partial EXEC, including subgroups with no active lane). The expected values are worked out for the subgroup size the program counts, which must be a power of two in the device's range (8 on lavapipe). `GcnTranslate.WaveSizeDependence` checks which instructions set the flag and that the modules with it declare maximal reconvergence; `GcnTranslate.MaskRoundTrip` checks `mask_round_trip` (set for `cross_lane`, whose `s[8:9]` holds the input mask as values, and for none of the other programs; also through `s_mov_b64` copies, the SALU bitwise family and constants).
- Descriptor sources and untyped buffer memory (#126, first part; the V# modes and the narrow MUBUF forms #247, first part; the MUBUF atomics #247, second part; scratch is not done yet):
  - **Sources** (`src/gpu/gcn/descriptors.*`). A forward dataflow over the CFG gives each SGPR dword either nothing or a *path*: `[k]` for user-data slot *k*, and for a dword loaded by `s_load_*` with an immediate offset *o* from the pointer in the pair at path *P*, `P + [o + j]` for result dword *j*. `s_mov_b32`/`s_mov_b64` copy paths, every other scalar write forgets the dwords it writes, and a join keeps the entries that agree. A V# used by a MUBUF instruction or `s_buffer_load_*` is a source when its four dwords are consecutive dwords of one path; `ShaderInterface::buffers` lists each source once, in order of first use, and leaves out one that can't be followed. Only slots below `USER_SGPR` start with a path.
  - **SMRD** runs in every lane (`scalar_memory`). `s_load_dword*` reads at the 64-bit address in the SGPR pair plus 4 * the offset (an immediate or a literal in dwords, or an SGPR in bytes with the low 2 bits ignored), with no range check. `s_buffer_load_dword*` reads through the V# and gives 0 for each dword that is not inside the buffer, checked per dword: dword *d* of an access at byte offset *o* is inside when `o + 4d < size`, with `size = num_records` bytes for a stride of 0 and `num_records * stride` otherwise (Sea Islands ISA 7.2.2, p. 7-2, and the buffer size in the footnote of Table 8.5, p. 8-9). The manual's clamp for a stride is `offset > size`, which would let the dword at byte `size` read from outside the buffer; `scalar_in_range` uses `>=` for both cases (a difference from the manual's text, as for the MUBUF check below). Only the base, stride and `num_records` count; the manual says the other V# fields are ignored.
  - **V# fields**: dword 0 and the low 8 bits of dword 1 are the 40-bit base (the ISA manual disagrees with itself: Table 8.5 gives 48 bits and the address pseudocode of 8.1.5 `const_base[39:0]`. The game's V#s have 0x80 or 0xb0 in bits 40-47 and PS4 guest addresses end below 2^40, #385. What those bits mean is not known, and no hardware confirmed that they are ignored: shadPS4 declares them as padding), bits 16 to 29 of dword 1 the stride, dword 2 `num_records`. The modes are run-time values too, read from the V# by every MUBUF and MTBUF access (#247): `swizzle_enable` (dword 1 bit 31) with `element_size` (dword 3 bits 19-20: 2, 4, 8 or 16 bytes) and `index_stride` (bits 21-22: 8, 16, 32 or 64 indices), `add_tid_enable` (dword 3 bit 23) and `heap` (dword 3 bit 26, bit 122 of Table 8.5). See the range rule below. `s_buffer_load_*` ignores them, as the manual says (7.2.2). The check that rejected them at run time (`check_buffer_descriptor`) is gone with them. The formats are ignored by the untyped accesses.
  - **MUBUF** (`buffer_memory`) handles the untyped dword loads and stores (`buffer_load_dword` and `x2` to `x4`, `buffer_store_dword` and the same sizes) under `active && in_range`, per dword, and the narrow forms (#247): `buffer_load_ubyte`, `_sbyte`, `_ushort` and `_sshort` (zero- or sign-extended to 32 bits) and `buffer_store_byte` and `_short` (the low bits of the VGPR). A narrow access is one component: it is checked at its first byte and read or written whole, byte by byte from any address (a short may cross a dword), and a narrow store merges its bytes into each dword it touches with the compare-and-swap loop of the typed stores (`store_bytes`), as adjacent lanes write the other bytes. The format forms go to `typed_memory` (#265, see "Typed buffer formats"); `tfe` and `lds` on the untyped forms and on the atomics are errors for now.
  - **Atomics** (`buffer_atomic`, #247): every MUBUF atomic of Sea Islands ISA Table 12.8 (p. 12-150 and 12-151), 32-bit and `_x2` (64-bit), in active lanes. The address is the one of the loads and stores, and the range check is **all or nothing** (8.1.5.3: "atomics are either completely in-range or completely discarded"), taken at the first byte as for a format access (`inside(m, 0)`), so a qword that starts inside the buffer and ends past it is updated whole (our reading: the check of 8.1.5.3 is on `buffer_offset`, the first byte). An atomic outside the buffer is dropped and returns 0. With `glc` the old value returns into the first VGPR (two for `_x2`) of vdata, the hardware's VDST being VDATA (Table 8.2); without it vdata is left alone. The compare-and-swaps take src from the first data VGPR(s) and cmp from the next (`dst = (dst == cmp) ? src : dst`). The operations with a SPIR-V atomic (swap, cmpswap, add, sub, the signed and unsigned min and max, and, or, xor) use it, on a `PhysicalStorageBuffer` pointer at device scope with relaxed semantics; inc, dec and the float ones (fcmpswap, fmin, fmax) update the memory in the compare-and-swap loop of the LDS atomics (`atomic` and `updated` are shared with them, typed by the width). `_x2` declares `Int64Atomics`, so bbvk's device now requires `shaderBufferInt64Atomics`. The float operations compare the bits as IEEE values, so denormals count whatever the shader's float mode (the manual: "handles NaN/INF/denorm"); our reading, unverified: fmin and fmax give the other operand when one is NaN (the memory when both are) and order -0 below +0, and fcmpswap takes +0 and -0 as equal and a NaN as equal to nothing. Like the dword accesses, the translator relies on aligned addresses (8 bytes for `_x2`). The only atomic of the corpus is `buffer_atomic_add`. Corpus (`GcnCoverage`, default keys, on top of 8abcf40): 178 opcodes translate alone before, 179 after (`buffer_atomic_add`), and 1,409,607 of 1,512,771 instructions instead of 1,409,599; still 863 distinct programs (5,261 files) translate, as the two compute programs with the atomic stop at a later instruction.
  - **Range rule.** Source: Sea Islands ISA, 8.1.5 (p. 8-6 to 8-8: the address in 8.1.5.1 and 8.1.5.4, the swizzled form in 8.1.5.2, the check in 8.1.5.3) and Table 8.2 (p. 8-4, `addr64`). A load outside the buffer returns 0 and a store is dropped. `x2` to `x4` accesses are checked dword by dword ("range-checked per component", 8.1.5.3), not all or nothing. The address is `base + soffset + buffer_offset` (8.1.5.4), with `offset` the instruction's 12-bit offset plus the VGPR under `offen`, and `index` the VGPR under `idxen` (0 without it) plus the lane (`thread_id[5:0]`) under `add_tid_enable` (8.1.5). `buffer_offset` is `index * stride + offset` (8.1.5.1), or under `swizzle_enable` (8.1.5.2) `((index / index_stride) * stride + (offset / element_size) * element_size) * index_stride + (index % index_stride) * element_size + offset % element_size`. soffset stays outside the swizzle: the manual adds it to the base (shadPS4 adds it to the offset). Each dword of a wider access has its own `buffer_offset` from its own offset (`+ 4d`), so with an `element_size` of 4 the dwords of a pair or of a 32_32 typed element are `index_stride` elements apart; a narrow access or a narrow typed element (8, 16, 8_8) takes its bytes contiguously from the address of its first byte (our choice: the compilers keep them inside an element; unverified for one that crosses it). The lane of `add_tid_enable` is the lane ID of the "Execution model": exact in compute, the subgroup's in the graphics stages, which is the wave lane only for a subgroup of 64 (the translator can't see the bit, so the shader is not marked `wave_size_dependent`; a known difference until the graphics stages need it). `inside` checks dword *d* with `offset` taken as the offset of that dword (`+ 4d`):
    - **Stride 0** (`num_records` is a size in bytes): out of range when `buffer_offset + soffset >= num_records` (`buffer_offset` is `offset` unless swizzled). The manual writes `buffer_offset >= num_records - soffset`; the sum is computed in 64 bits, which equals it without the 32-bit wrap of the subtraction, so a soffset beyond the size is out of range for every offset (a hardware that wrapped would let it in; the manual doesn't say). `idxen` adds nothing to the address and is not checked (the index times 0).
    - **Stride != 0** (`num_records` counts records): out of range when `index >= num_records`, or, with `idxen` or `add_tid_enable`, when `offset >= stride`. soffset is not part of the check, only of the address.
    - **Stride != 0 without `idxen` or `add_tid_enable`**: the manual defines it: the index is 0, so only `0 >= num_records` applies, and the offset is not checked at all. The size is not `num_records * stride` here. This holds for a stride of 1 as well; the manual's "raw" (`stride <= 1`) is only about coalescing.
    - **`heap`** adds to either check (Table 8.5: "out-of-range if offset = 0 or >= num_records"): out of range when the offset of the dword (`offset + 4d`, the manual's `offset`, without soffset) is 0 or not below `num_records`. Which offset the manual means, and whether `num_records` counts bytes there with a stride, is our reading, unverified; no game shader is known to use it.
    - **`addr64`** adds its 64-bit VGPR address to the base, soffset and the instruction's offset, ignores the stride and is not range-checked (Table 8.2). The manual requires `idxen` and `offen` to be 0 with it (and LLVM rejects them), so the translator gives a `GcnError` for them. It also ignores `swizzle_enable`, `add_tid_enable` and `heap` (the manual makes `add_tid_enable` with `addr64` illegal).
    - **`s_buffer_load_*`** has its own clamp, see SMRD above.
    - Difference from shadPS4: its `GetSize()` (`num_records` for a stride of 0, `stride * num_records` otherwise) is a size for all accesses; here it applies to `s_buffer_load_*` only, and MUBUF follows the checks above.
    - The hardware ignores the two low bits of a dword address (8.1.6); the translator does not mask them and relies on aligned addresses, as the compilers emit them.

  - **Layouts** (`src/gpu/gcn/buffer_format.*`). The data formats 8, 16, 8_8, 32, 16_16, 2_10_10_10 (10, 10, 10 and 2 bits from bit 0), 8_8_8_8, 32_32, 16_16_16_16, 32_32_32 and 32_32_32_32 (components from the lowest bits and dwords, X first). 10_11_11 (6) is X and Y in 11 bits from bits 0 and 11 and Z in 10 bits from bit 22, in FLOAT only (the unsigned small floats, next items); its other number formats are errors. Not supported: 0 (invalid), 7 (11_11_10), 8 (10_10_10_2) and 15. The manual gives 11_11_10 and 10_10_10_2 only by name (Sea Islands ISA Table 8.13, p. 8-20, the DFMT list of Table 8.2, p. 8-3, and Table 12.11), with no bit positions; reading the names from the high bits down, as 2_10_10_10 and 10_11_11 are, would put X in the 10 low bits of 11_11_10 and in the 2 low bits of 10_10_10_2, but that is a guess, so they stay errors until a source or a game shader shows the layout. The unsupported pairs are errors at translation time, like a number format that has no conversion on the format's width: FLOAT on 8 or 10 bits (outside 10_11_11), and UNORM, SNORM, USCALED, SSCALED and SNORM_OGL on 32 bits.
  - **Conversion** (`FormatEmitter::decode`, per component of *w* bits): UNORM *c* / (2^*w* - 1), SNORM max(*s* / (2^(*w*-1) - 1), -1) with *s* the sign-extended field, USCALED and SSCALED the integer as a float, UINT and SINT the zero- or sign-extended integer, SNORM_OGL (2*s* + 1) / (2^*w* - 1) (the number format 6; its formula is shadPS4's `SnormNz`, unverified against the manual), and FLOAT the half float (`UnpackHalf2x16`) on 16 bits, the bits on 32, and on 11 and 10 bits (10_11_11) the unsigned small float with 5 exponent bits (bias 15) and 6 or 5 mantissa bits, converted exactly in integer operations (`from_small_float`): exponent 0 is a denormal (the mantissa times 2^-(14 + m), through an exact `OpConvertUToF`), exponent 31 is +Inf, or with a mantissa a NaN, which reads as the quiet f32 NaN 0x7fc00000. The layout and the conversions are those of Vulkan's `B10G11R11_UFLOAT_PACK32` ("Unsigned 11-Bit" and "10-Bit Floating-Point Numbers"), which shadPS4 also uses for this format. A result is a u32 holding the float's bit pattern or the integer.
  - **MTBUF** (`typed_memory`): `tbuffer_load_format_x` to `xyzw`, the format from the instruction's `dfmt` and `nfmt`. The address and the range check are `buffer_memory`'s (both use `buffer_access` and `inside`). Per the ISA manual (8.1.5.3) a format load is **all-or-nothing**, so one check covers the element, at its first byte: an element that starts outside reads 0 in every component (the zero is selected after the conversion, as zero bits are not a zero component in SNORM_OGL), and one that starts inside is read whole, past the end of the buffer if it has to. An element of 4 bytes or more is read from **aligned dwords**: the manual (8.1.6) says the two low bits of the address of a dword or larger access are ignored, so the element at byte 1 of a table reads the dwords at byte 0. (Which behaviour a PS4 has may depend on `SH_MEM_CONFIG`'s alignment mode, unverified; the manual's is the one implemented.) A narrower element (8, 8_8, 16) is read byte by byte from any address, as the manual says nothing about it. The components are the format's X to W, and those it lacks are 0: the manual's **dst_sel is the identity for MTBUF** (Table 8.4: X000, XY00, XYZ0 or XYZW by the number of components) and comes from the V# only for the formatted MUBUF loads and stores (`buffer_load_format_*`), so the V#'s dword 3 is ignored here. shadPS4 does the same. The formatted MUBUF forms apply the V#'s dst_sel (next items).
  - **MTBUF stores** (`typed_memory` and `FormatEmitter::encode`): `tbuffer_store_format_x` to `xyzw`, with the address, range check and alignment of the loads: an element whose first byte is inside the V# is written whole (8.1.5.3: format stores are completely in range or completely dropped), one that starts outside is not written, and an element of 4 bytes or more goes to the aligned dwords. The components the instruction lacks are stored as 0 (shadPS4 does the same; the manual doesn't say). Per component of *w* bits: UNORM clamps to [0, 1] and SNORM to [-1, 1] (a NaN becomes 0), multiplies by 2^*w* - 1 or 2^(*w*-1) - 1 in f32 and rounds to the nearest integer, ties to even (`RoundEven`); UINT saturates to 2^*w* - 1 and SINT to the signed range; FLOAT keeps the 32 bits or rounds to a half float, to nearest even, in integer operations (so no float mode reaches it): 65520 and above become infinities, magnitudes below 2^-14 denormals, and a NaN the quiet half NaN of its sign (0x7e00 with the sign bit; the payload is not kept). USCALED, SSCALED and SNORM_OGL can't be written by the buffer unit (Sea Islands ISA Table 8.13, "buffer w": no) and are errors at translation time (`format_error(..., store = true)`), as are the pairs that loads reject. The fields are put together in the element's dwords. An element of 1 or 2 bytes (8, 16, 8_8) is written byte-exact: adjacent lanes may write other bytes of the same dword, so each dword it touches is updated by a compare-and-swap loop at device scope (`store_bytes`, the loop of the LDS's sub-dword writes, `atomic_update`, which now takes the scope), and an element at byte 3 also updates the next dword. Stores in UNORM and SNORM count as float uses like the loads (next item): the clamp, the product and `RoundEven` are float operations, and the rounding mode does reach the product (*v* × 255 is inexact for most *v*), the same known difference as the loads' divisions. Stores in FLOAT don't: they copy the 32 bits or round to a half float in integer operations, so a shader whose only float-format access is a FLOAT store gets no float modes and translates under any `FP_ROUND_32` and `FP_DENORM_32`. **Known difference, unverified:** the manual (8.1.5.3, Table 8.13) gives no conversion rules for stores, and these are our choice: UINT and SINT saturate, as #265 asks, where shadPS4 (`StoreBufferFormat`, whose `Pack4x8` and `Pack2x16` insert the low bits) truncates; UNORM and SNORM round ties to even (Vulkan only says implementations should round to nearest); and a NaN in FLOAT becomes 0x7e00 with its sign, in UNORM and SNORM 0. Check all three against the hardware or the game's shaders. The small floats of 10_11_11 (`to_small_float`, the half float's rounding with 6 or 5 mantissa bits, ties to even, in integer operations, so no float mode reaches it either): a negative value, -0 and -Inf become 0, a finite value above the largest finite one (65024 for 11 bits, 64512 for 10) becomes that one, +Inf stays +Inf, a NaN of either sign becomes the quiet NaN (exponent 31 with the mantissa's top bit), and magnitudes below 2^-14 denormals. **Known difference, unverified:** these are our choices (the manual gives no conversion rules, and an unsigned format has no sign to keep, so the clamps go to its nearest values); shadPS4 (`DefineFloat32ToUfloatM5`) makes a negative NaN 0 and a NaN `31 << m | 1`, and does not clamp a value too large for the exponent.
  - **Float modes**: every MTBUF load whose number format is not UINT or SINT counts as a float use (`note_float`), because it converts through f32 or unpacks a half float, and half floats have infinities, NaNs and -0 that the conversion must keep. Such a shader gets the execution modes of the float VALU (next item): `SignedZeroInfNanPreserve`, the rounding mode and the denormal mode of `COMPUTE_PGM_RSRC1`, and it fails to translate for the half-flushing denormal modes or the roundings toward the infinities (modes 1 and 2), even if it has no float instruction. A load in UINT or SINT converts nothing and needs none of them. No conversion makes an f32 denormal, and the 16-bit integers and half floats convert exactly, so the denormal mode and the signed-zero, Inf and NaN modes change nothing but the half float cases above. The rounding mode is different: it applies to the divisions of UNORM, SNORM and SNORM_OGL (*c* / (2^*w* - 1) is inexact for most *c*), so with `FP_ROUND_32` = 3 (toward zero) the shader's `RoundingModeRTZ` can make the result 1 ulp closer to zero than round-to-nearest (RTZ rounds a negative quotient toward zero, so it is the magnitude that drops). **Known difference, unverified:** on the hardware these conversions happen in the buffer unit, which probably does not follow the shader's `MODE` register and always rounds to nearest; if so, these divisions should round to nearest whatever the mode. The execution mode covers the whole shader, so that would need the quotient corrected in the translator; left open until the hardware behavior is known. The execution tests run with the default mode (round to nearest). **Known difference, driver-dependent:** Vulkan lets `OpFDiv` be off by up to 2.5 ULP, so the bit-exact expectations of `TypedBuffer` hold on lavapipe, whose division is correctly rounded, but not necessarily on a GPU driver, whose result for UNORM, SNORM and SNORM_OGL may differ from the correctly rounded quotient. The translation does not correct for it, so the shader's rounding mode is not the only source of a difference from round-to-nearest.

The vertex key therefore means a real VS or a copy shader with the primitive ID off. Both registers must join the key, or be rejected, before a VS with the primitive ID or a domain shader translates; until then the translator can't tell and would read the wrong inputs.
- **Initial registers.** User data in s0 and up, as in compute. v0 is `VertexIndex`; with `VGPR_COMP_CNT` 1 or more v1 is `InstanceIndex` divided by step rate 0, with 2 or more v2 the same with step rate 1, and with 3 v3 is `InstanceIndex`; a step rate of 0 gives 0 (the layout and the rate-0 rule as shadPS4 has them, see `docs/references.md`). `VertexIndex` and `InstanceIndex` include the draw's vertex offset and first instance, so the backend issues draws that match GNM's indices (decided with the backend).
- **Lane ID.** `SubgroupLocalInvocationId`, so `subgroup_base` is 0 and a graphics module always declares `GroupNonUniform`.
- **LDS.** A DS instruction other than `ds_nop`, and `s_barrier`, are errors in a graphics stage so far: the VS has no LDS of its own (`SPI_SHADER_PGM_RSRC2_VS` has no `LDS_SIZE`), and a Vulkan module may use the `Workgroup` storage class and workgroup-scope barriers in none of the graphics stages translated so far (`spirv-val` rejects both in a vertex module; sources in `docs/references.md`).
- **Exports** run under `if (active)`. `pos0` writes `Position`, `param<n>` the output at `Location n` (a float vec4; both start as 0, so the channels an export leaves out are defined), each enabled channel as the float with the VGPR's bits. `null` writes nothing. In the VS, `pos1` to `pos3`, the render targets and compressed exports are errors so far, and `exp` in compute is an error.
- **Pixel key.** `ps_input_addr` (`SPI_PS_INPUT_ADDR`) places the input VGPRs and `ps_input_ena` (`SPI_PS_INPUT_ENA`) says which are loaded; an enabled bit that ADDR doesn't place is an error. `ps_input_cntl[n]` is `SPI_PS_INPUT_CNTL_<n>` (`OFFSET` bits 0-5, `DEFAULT_VAL` bits 8-9, `FLAT_SHADE` bit 10; its other fields, `CYL_WRAP` in bits 13-16 and `PT_SPRITE_TEX` in bit 17, which replaces the attribute with the point sprite coordinate, are rejected) and `col_format` is `SPI_SHADER_COL_FORMAT`. `z_format` (`SPI_SHADER_Z_FORMAT`) and `db_shader_control` (`DB_SHADER_CONTROL`) are for `mrtz` (see "Depth"), and `quad_control` is a device flag, not a register (see "Quad control"). In `SPI_SHADER_PGM_RSRC2_PS`, `SCRATCH_EN` is rejected.
- **Pixel: not in the key yet.** `SPI_BARYC_CNTL` changes what `POS_*_FLOAT` hold: `POS_FLOAT_LOCATION` moves the position from the pixel center to the centroid or the sample, and `POS_FLOAT_ULC` gives the pixel's upper-left corner (without the +0.5). The translation reads `FragCoord`, which is at the pixel center only while the shader runs once per pixel, so the pixel key means `POS_FLOAT_LOCATION` at the center and `POS_FLOAT_ULC` off. An enabled sample barycentric pair (`PERSP_SAMPLE`, `LINEAR_SAMPLE`) gives a `Sample` input, which makes the shader run per sample and moves `FragCoord` to the sample (Vulkan, "Sample Shading"), so `POS_*_FLOAT` together with a sample pair is an error until the register is in the key. The register must join the key, or be rejected, before a PS that reads `POS_*_FLOAT` with another setting translates; until then the translator can't tell and would give the wrong position (sources in `docs/references.md`).
- **Pixel initial registers.** The SGPR after the user data is the primitive mask, which programs move to M0 for `v_interp`; the translation doesn't need it, so it holds 0. EXEC starts as `!HelperInvocation` (decorated `Volatile`, as demote changes it). The VGPRs follow the ADDR bits in order: 2 each for the I/J barycentrics of the perspective sample, center and centroid, 3 for the pull model, 2 each for the linear sample, center and centroid, then one each for `LINE_STIPPLE_TEX`, `POS_X/Y/Z/W_FLOAT`, `FRONT_FACE`, `ANCILLARY`, `SAMPLE_COVERAGE` and `POS_FIXED_PT` (shadPS4's order, see `docs/references.md`). A placed input that ENA doesn't enable holds 0. Supported so far: the six barycentric pairs, which hold 0 and are only read by `v_interp` to choose the interpolation, and `POS_*_FLOAT` from `FragCoord` (W as 1/`FragCoord.w`). The pull model, `LINE_STIPPLE_TEX`, `FRONT_FACE`, `ANCILLARY`, `SAMPLE_COVERAGE` and `POS_FIXED_PT` are errors when enabled. A program that reads a barycentric VGPR other than through `v_interp` reads 0 without an error.
- **Interpolation.** `v_interp_p1_f32` and `v_interp_p2_f32` both write the interpolated channel: the input variable does the interpolation. Its qualifier comes from the barycentric VGPR they read, which must be an I register for `p1` and a J register for `p2`: linear pairs give `NoPerspective`, centroid pairs `Centroid`, sample pairs `Sample` (with `SampleRateShading`). The input is a float vec4 at the `OFFSET` of `SPI_PS_INPUT_CNTL_<n>`. `FLAT_SHADE` and `v_interp_mov_f32` with `p0` read a `Flat` input; `p10` and `p20` (which need the vertices' values) are errors. An `OFFSET` of 0x20 and above gives the `DEFAULT_VAL` constant (0000, 0001, 1110 or 1111 in XYZW); there `p10` and `p20` give 0, since the value is P0 + P10 * I + P20 * J and a constant is the same at the three vertices. Two reads of one location with different qualifiers are an error. Integer built-in inputs of the fragment stage (`SubgroupLocalInvocationId`, `SubgroupSize`) are decorated `Flat`, as Vulkan requires.
- **Render targets.** `mrt<n>` converts per its 4 bits of `SPI_SHADER_COL_FORMAT`: `ZERO` writes nothing; `32_R`, `32_GR`, `32_AR` and `32_ABGR` write the channels they name as floats; `FP16_ABGR`, `UNORM16_ABGR` and `SNORM16_ABGR` take compressed exports (two 16-bit values per VGPR, the low half first) unpacked with `UnpackHalf2x16`, `UnpackUnorm2x16` and `UnpackSnorm2x16`; `UINT16_ABGR` and `SINT16_ABGR` write a uint or int vec4 output with the halves zero- or sign-extended. A compressed export to a 32-bit format or an uncompressed one to a 16-bit format is an error. The output at `Location n` starts as 0. Open: a 32-bit format whose color buffer is an integer format needs a uint or int output, which the key can't tell yet (`CB_COLOR<n>_INFO`, later). `pos*` and `param*` exports are errors in the PS.
- **Depth.** `mrtz`'s x is the depth, y the stencil, z the sample mask and w the alpha for alpha to mask, as far as `SPI_SHADER_Z_FORMAT` carries them (`32_R` x; `32_GR` x and y; `32_AR` x and w; `32_ABGR` all four) and `DB_SHADER_CONTROL` enables them (shadPS4's `ExportDepth` and `mrtz_mask`, see `docs/references.md`). With `Z_EXPORT_ENABLE` (bit 0), x is stored into `FragDepth` in the active lanes and the module declares `DepthReplacing`; with `ZERO`, without `Z_EXPORT_ENABLE`, or with x `off`, the export writes no depth and the depth stays the rasterized one. The formats with 16-bit channels and compressed `mrtz` exports are errors, and so is an export whose format carries a channel that `DB_SHADER_CONTROL` enables: the stencil (`STENCIL_TEST_VAL_EXPORT_ENABLE`, `STENCIL_OP_VAL_EXPORT_ENABLE`, bits 1-2), the sample mask (`MASK_EXPORT_ENABLE`, bit 8) or alpha to mask (`COVERAGE_TO_MASK_ENABLE`, bit 7). `FragStencilRefEXT` and `SampleMask` come with a shader that needs them. The other fields of `DB_SHADER_CONTROL` are ignored here; two of them could become execution modes later: `CONSERVATIVE_Z_EXPORT` (bits 13-14) as `DepthGreater` or `DepthLess`, and `DEPTH_BEFORE_SHADER` (bit 12) as `EarlyFragmentTests`. Open: `FragDepth` starts as 0 (outputs have a null initializer), so a lane that is outside EXEC at every `mrtz` export and isn't discarded writes the depth 0; what the hardware writes there isn't known.
- **Quad control.** `quad_control` says that the device has `VK_KHR_shader_quad_control` and the backend enabled `shaderQuadControl`. A pixel shader then declares the `SPV_KHR_quad_control` extension, the `QuadControlKHR` capability (5087) and the execution modes `QuadDerivativesKHR` (5088) and `RequireFullQuadsKHR` (5089). The numbers are spelled out in `stages.cpp`, because Ubuntu 24.04's SPIR-V headers in CI don't have them (the installed headers have them with these values). GCN runs every 2x2 quad with a covered pixel as a whole, its other pixels as helper lanes, and takes the implicit derivatives of a lane from its quad; `RequireFullQuadsKHR` asks Vulkan for the same whole quads, and `QuadDerivativesKHR` defines the derivatives wherever the control flow is uniform in the quad rather than in the whole draw. The other stages ignore the flag, and `s_wqm_b64` keeps its quad swaps (`OpGroupNonUniformQuadAnyKHR` could replace them in a pixel shader with the flag, a later optimization). Without the flag the module doesn't change: derivatives in control flow that isn't uniform are then up to the driver. `GcnStages.QuadControl` checks the declarations and `spirv-val` (it skips when `spirv-val` doesn't know the capability). `bbvk`'s `Device` enables `VK_KHR_shader_quad_control` with `shaderQuadControl` where the device has it, as an optional extension next to the required ones, and says so with `quad_control()` (and in its log line), the value the backend is to put into the pixel key. The compute runner's `DeviceInfo` reports it as `quad_control`, and `Render.QuadControl` renders the pair of `Render.VertexPixelWithDiscard` with the flag and checks the same pixels (it skips without the feature; lavapipe from Mesa 26.2 has it).
- **Valid mask and demote.** An export with `vm` stores EXEC into a valid-mask variable (initially true), and `done` runs `OpDemoteToHelperInvocation` where it is false (see "Pixel shaders" above). The fragment entry point declares `OriginUpperLeft`.
- **Interface.** The outputs follow from the key and the code (`param<n>` is location n, and the pixel shader's input locations come from `SPI_PS_INPUT_CNTL_<n>`), so `ShaderInterface` gets no `inputs` and `outputs` lists yet. They come when the backend needs them.
- **Tests.** `tests/gpu/gcn/stages_test.cpp` translates `vs_attrs` (two vertex attributes loaded by index through a V#, exported as `pos0` and `param0`, and the instance index as `param1`) with step rates 1 and 2, 0, and with `VGPR_COMP_CNT` 0, and `ps_attrs` (perspective, linear centroid, flat and default attributes, a discard by `v_cmpx`, exports to a 32_ABGR, a 32_GR and an FP16 render target, and the 16-bit formats on its compressed export; then again with the perspective sample pair, a 32_AR target and the default value 0001, and with `POS_Z/W_FLOAT`; its `mrtz` export writes the Y position as the depth), through `spirv-val`, checks that `param<n>` is at `Location n` and that each export stores only its enabled channels (four for `pos0` and `param0`, x for `param1`; four for 32_ABGR, x and y for 32_GR, x and w for 32_AR), that each pixel input has the interpolation decorations of its barycentric pair or `Flat`, that the default values give 1.0 where they should, that only loaded positions read `FragCoord`, that `POS_W_FLOAT` divides by `FragCoord.w` and that the fragment entry point declares `OriginUpperLeft`, that a VS takes its float mode from the same `pgm_rsrc1` as `VGPR_COMP_CNT` (`VertexFloatMode`), and checks the error messages. `GcnStages.PixelDepth` translates `ps_attrs` with each 32-bit `SPI_SHADER_Z_FORMAT`, with `ZERO` and without `Z_EXPORT_ENABLE`, and checks `FragDepth` and `DepthReplacing`. The graphics programs (`vs_*`, `ps_*`) are left out of the compute loop of `translate_test.cpp`.
- **Fetch subroutine** (`src/gpu/gcn/fetch.*`, #129, part 5). The translator inlines it before building the CFG, so the later passes (the mask types, the V# sources, the CFG) see one program:
  - `inline_fetch` decodes the fetch code with `Until::subroutine_end` and puts its instructions, without the `s_setpc_b64`, after the program's `s_swappc_b64`. The inlined instructions take the call's byte offset, so the offsets stay in order for the branch targets, and `FetchSite` keeps their offsets in the fetch code for errors.
  - The call stays: its destination gets the return address, the draw block's `code_address` plus the call's offset plus 4, as on the hardware, low dword first, so a shader that reads the pair after the call sees the right value.
  - Errors are at the call's offset (so the coverage report counts them at `s_swappc_b64`) and say "fetch subroutine". Rejected: a call whose source isn't `s[0:1]` (the run time reads the fetch code from user-data dwords 0-1), a second call, a call without fetch code, a fetch subroutine without `s_setpc_b64`, one that returns through another pair than the call's destination, and one that branches, ends the program, uses `s_getpc_b64` (its address would be in the fetch code), `s_swappc_b64`, `s_rfe_b64`, fork or join, or writes the return pair. An inlined instruction that the translator doesn't support names its offset in the fetch code.
  - That `s[0:1]` still holds the user data at the call isn't checked; every call in the corpus's VS programs is `s_swappc_b64 s[0:1], s[0:1]`, once per program.
  - Only the vertex stage inlines. In compute (and so far for the ES and LS programs, which get the compute key), `s_swappc_b64` stays an unsupported instruction. ES and LS inline the same way once they have keys.
  - The generator's loads are `buffer_load_format_*`, the formatted MUBUF loads, translated since #265 with the V#'s format at run time, but only for the pairs of `formatted_pairs` (see "Typed buffer formats" under "Resources and memory"): a vertex attribute in another format reads 0 until its pair is added. The error test for an inlined unsupported instruction now uses `buffer_atomic_add`. `tests/gpu/gcn/fetch_test.cpp` uses a synthetic one in the generator's pattern with `buffer_load_dwordx4`, and checks the inlined program, `spirv-val`, the V# source found through the fetch code, the return address and the errors. The return address is followed through the module's ids, from the 64-bit constant added to `code_address` to the stores of its dwords into the variables the prologue gave the destination pair's user data; running a vertex shader waits for the graphics runner.

Image sampling (`src/gpu/gcn/image.*`, #130: the translator, then the render test on lavapipe):

- **Code layout.** As with the stages, the image code is in `detail::ImageOps` apart from `translate.cpp`, which only dispatches `Format::mimg` to it and adds its variables to the entry point. It reaches the registers through `StageRegisters`.
- **Sources** (`find_image_sources` in `descriptors.*`). The SGPR dataflow of the V# sources (now shared through one walk) gives each MIMG instruction's T# (the first 8-SGPR operand; 4 dwords with `r128`) and S# (the 4 SGPRs after it) a `ResourceSource`. `ShaderInterface::images` and `samplers` list them in order of first use, and `ImageSources::uses` maps the instruction to their positions. An instruction whose T# or S# can't be followed is an error ("can't be followed"), as the binding must be known at compile time.
- **Key** (an interface other issues build on). `ShaderKey::images[i]` is the `ImageClass` of image i: the T#'s type field (dword 3 bits 28-31) and its number class (UINT and SINT sample integers, every other number format floats, from dword 1 bits 26-29). `image_class(tsharp)` computes it from the T#'s first four dwords; the run time compares it at draw time with the key a translation was made with and translates again on a mismatch. An image without an entry is 2D float, so the first translation of a shader can be made before the T#s are read.
- **Bindings.** One descriptor set per hardware stage, so that two stages of a pipeline never collide: set 0 for VS (also a domain shader on the VS stage and a GS's copy shader) and for CS, set 1 for PS, and, once those stages are translated, set 2 for ES or LS and set 3 for GS or HS. Tessellation and geometry shaders are never combined in the game ("Open questions"), so a pipeline (LS+HS+VS+PS or ES+GS+VS+PS) needs at most four sets, Vulkan's minimum `maxBoundDescriptorSets`. `descriptor_set(stage)` returns this; today the translator knows only VS, PS and CS, so it returns 0 or 1, and the pipeline layout of a VS/PS pair has both sets. The stages that come later extend the function, never renumber it. Image i is binding i, a `SampledImage`-compatible image (`OpTypeImage`, `Sampled` 1, format `Unknown`); sampler j is binding `images.size()` + j. The image and the sampler stay separate descriptors, as T# and S# are separate on the hardware, and meet in `OpSampledImage` at each use.
- **Classes so far.** 2D (9), 2D array (13) and cube (11); 1D, 3D and MSAA are errors until a shader needs them. A cube is bound as a 2D array of its faces, as shadPS4 does (`FixImageCoords`): the shader has already done the cube math, so x and y are in [1, 2] on the face and `face_id` is slice × 8 + face (Sea Islands ISA 8.2.3); the coordinates become (x − 1, y − 1, `face_id` − 2 × floor(`face_id` / 8)), the layer of that face. Filtering then doesn't cross the faces' edges. The run time must create cube T#s as 2D arrays of 6 × slices layers (or views of that type).
- **Address** (ISA 8.2.4): the derivatives for `_d` (dx/dh, dy/dh, dx/dv, dy/dv: `Grad` with (n, n+1) and (n+2, n+3)), then x and y, then the slice (only with `da`) or the cube's `face_id` (always), then the LOD for `_l`. The decoded range of vaddr is only the shortest form; the translator reads as many VGPRs as the class needs. Without `da` an array reads layer 0 (the hardware sends no index, 8.2.5); with `da` a 2D image reads and ignores the slice VGPR.
- **Instructions so far:** `image_sample` (`OpImageSampleImplicitLod`, pixel stage only: elsewhere it is an error, as SPIR-V has no derivatives there), `image_sample_l` (`Lod`), `image_sample_lz` (`Lod` 0) and `image_sample_d` (`Grad`). These are the first, second, fourth and sixth most used MIMG opcodes of the corpus (12,328, 2,054, 514 and 252 instructions). The sample is not predicated: every invocation samples, so the implicit LOD sees the whole quad, and EXEC predicates only the VGPR writes. The coordinates come from VGPR writes that EXEC predicates, so, as on the hardware, a shader must enter whole quad mode (`s_wqm_b64`) before it computes them, or the helper lanes keep stale values and the LOD is wrong in partly covered quads (the render test showed it along the diagonal where lavapipe splits the clipped full-screen triangle). `dmask` picks the result components into consecutive VGPRs (integer results as their bits); with `dmask` 0 the one VGPR gets 0 (8.2.1, Table 8.7). `tfe`, `lwe` and `unorm` are errors so far (`unorm` needs an unnormalized sampler, which Vulkan restricts to explicit LOD 0 and no arrays). `glc` and `slc` are ignored.
- **Not yet** (item 8c, which owns all of them; the render test below covers only the four forms above; `image_load_mip` and `image_store` are done, see "Image loads and stores" below): the compare forms (`image_sample_c_lz` is the third most used, 1,090 instructions; the compare function is the sampler's), the offsets (`image_sample_lz_o`), `_b` and `_cl` (unused in the corpus), `image_get_lod`, gather, other loads and stores, and atomics. The T#'s `dst_sel`, base level, base array and min LOD, and the S#, are the run time's: they become the image view and the `VkSampler` (item 28).
- **Image loads and stores** (`image_load_mip` and `image_store`, #131). `image_load_mip` has no S# and its address is integers (ISA 8.2.2): x and y, the slice with `da` (only an array uses it, as for sampling), then the level. 2D and 2D array T#s are translated; other types are errors, like `tfe` and `lwe`; the instruction's `unorm` bit is ignored, as no-sampler addresses are always integers. It reads the same sampled binding as sampling with `OpImageFetch` and the level as `Lod`, in every lane: a coordinate or level out of range relies on robust image access, which is required (`robustImageAccess`, core in 1.3) and tightened to `robustImageAccess2` where the device has it (`VK_KHR_robustness2` or the older `VK_EXT_robustness2`, reported by `Device::robust_image_access2()`). With it the out-of-range load reads 0, as on GCN; without it the value is undefined. `dmask` picks the components into consecutive VGPRs like sampling (with `dmask` 0 the one VGPR gets 0), and the writes follow EXEC. The render test (`tests/gpu/runner/image_render_test.cpp`, `ps_load_mip`) reads levels 1 and 3 of a 16x16 five-level image, 2D and 2D array, and checks that everything out of range reads 0: the part of the 2x2 level 3 beyond (1, 1), a level past the five, and a slice past the array's layers. It requires `robustImageAccess2` on the runner's lavapipe, so the check can't disappear unnoticed. The T#'s `dst_sel`, base level and format are the run time's, as for sampling, so the view has to carry them (item 28). `image_store` has the same address and no sampler or result. A program's written images are storage images (`Sampled` 2, no format, so the device needs `shaderStorageImageWriteWithoutFormat`) and `ShaderInterface::stored_images` says which for the run time; a program that both reads and writes one image is an error, since one binding can't be both kinds. The store runs under EXEC (`OpImageWrite` in the `if (active)` of the lane); the enabled components come from consecutive VGPRs and the missing ones are written as 0 (ISA 8.2.4), and `dmask` 0 is an error. The execution test (`mem_image_store`) stores a float texel with `dmask` 0x9 and, with `da`, one with `dmask` 0x7, on a 4x4 image, with a lane inactive and four lanes out of range (robust access drops those), for 2D and 2D array float and 2D uint and sint. `GcnCoverage` is unchanged by the two instructions: 1,260 of 3,832 programs translate before and after, 3 probes, 179 of 208 opcodes alone. The 7 programs that stop at `image_load_mip` (6 CS, 1 VS) and the 3 that stop at `image_store` (3 CS) go from "unsupported instruction" to "the image descriptor of ... can't be followed": the report translates them with the stand-in key without user SGPRs, so their T# has no source. Only the game's own programs, whose keys carry the user SGPRs, can show the gain.
- **Force unnormalized S#** (S# dword 0 bit 15, ISA Table 8.12) does not fit a `VkSampler` for most of these forms: Vulkan's `unnormalizedCoordinates` forbids implicit LOD, array and cube images and any LOD but 0, the same reason the instruction's `unorm` bit is rejected. Until the translator supports it (a key bit and coordinate scaling by the image size), the run time (item 28) rejects a draw whose S# sets the bit, naming it, instead of dropping it.
- **Tests.** `tests/gpu/gcn/image_test.cpp`: `image_class` of three T#s; a program with `image_sample` (all of `dmask`), `image_sample_l` and `image_sample_d` with `da` (`dmask` 3 and 0) and `image_sample_lz`, translated for 2D, 2D array and cube of float, 2D of UINT and 2D array of SINT, passes `spirv-val`, with its image at user data 0 and its sampler at 8; and the errors.
- **Render test** (#130, second part). `GraphicsRunner::render` takes `Texture`s (R32G32B32A32_SFLOAT, levels and layers, a 2D or 2D array view, texels copied from the guest memory) and a sampler count; it builds the two descriptor sets of a VS/PS pair per render, as `descriptor_set` numbers them ("Bindings" above): set 0, the vertex stage's, is empty, as the runner's vertex shaders sample nothing, and set 1, the pixel stage's, holds the textures, then the samplers (nearest filtering and mip level, clamp to edge). `tests/gpu/runner/image_render_test.cpp` draws `vs_attrs` over an 8x8 target with `ps_sample` (whole quad mode, then `image_sample`, `image_sample_l` with `da`, `image_sample_d` with `da` and `image_sample_lz`, one component each) and a 16x16 image of five levels whose texels encode channel, level, layer and position, and checks every pixel: the implicit LOD reads level 1, LOD 2 level 2, derivatives of 0.5 level 3 and `_lz` level 0, for a 2D image (its slice VGPR ignored), a 2D array (layer 0 without `da`, the slice with it) and a cube array (`face_id` 10, layer 8 of 12, coordinates in [1, 2]). The coordinates are a quarter texel of level 0 away from the texel edges.

Control flow graph (`src/gpu/gcn/cfg.hpp`, #124):

- `build_cfg` returns the blocks in program order, block 0 first. A `Block` holds the byte offset and index of its first instruction, its instruction count (the branch included), its `Exit` (`next`, `jump`, `conditional`, `end`) and the block indices `taken` and `next`. `successors` lists `taken` before `next`. The translator emits nothing for a block's branch instruction: its effect is the exit, so a skip that became a fall-through simply ends the block.
- `analyze` returns a `CfgAnalysis`: `rpo`, `order` (each block's position in `rpo`), `idom`, `loop_header`, `merge_node`, `reducible`, and `dominates(a, b)`. Unreachable blocks have position and dominator `CfgAnalysis::none`.
- Tests: synthetic programs of SOPP branches and `s_nop` placeholders, decoded from words encoded by hand. SOP1 is decoded in parallel (#115), so a scalar write is a placeholder turned into an `s_mov_b32` with a scalar destination.

Structurizer (`src/gpu/gcn/structurize.hpp`, #124):

- `structurize(cfg, builder, emitter)` emits into the current function. A caller block must be open (the prologue); the structurizer ends it with a branch and returns with no block open.
- `BlockEmitter` has two callbacks: `body(block)` emits the block's instructions into the current SPIR-V block, and `condition(block)`, for a conditional exit, emits the branch condition after the body and returns its bool id (true takes the branch). Each is called once per reachable block.
- Tests: synthetic programs pass `spirv-val`, and a small interpreter for the instructions the structurizer emits runs each module with scripted branch outcomes. The blocks it visits must match a walk over the graph. The cases are if/else, nested loops, early returns and breaks out of a loop to an outer merge node, a continue from inside a scope, exits from an inner loop that continue the outer one or leave both, and two irreducible graphs (a loop with two entries, alone and inside a natural loop). A randomized test runs the same checks on 500 random programs of nops, `s_endpgm`, forward `s_branch` and conditional branches to anywhere, with random scripts; about one in seven of them is irreducible.

## Offline test strategy

Four levels. The first three need neither a running game nor a GPU.

1. **Unit tests** (CI): the decoder per microcode format, with words encoded by hand from the ISA manual; the disassembler text; the SPIR-V builder through `spirv-val`. The extractor gets synthetic DCX and BND4 files, so CI covers it too.
2. **Corpus tests** (local, need the game). They skip without `BB_GAME_DIR`, and with "run `tools/shaderbnd`" when `analysis/shaders/` is missing. Over every extracted program:
   - It decodes completely, has exactly one final `s_endpgm`, and its size matches the footer.
   - **Round trip through LLVM:** our disassembly of each instruction, assembled by `llvm-mc -triple=amdgcn -mcpu=bonaire -show-encoding`, gives the original words. LLVM's disassembler doesn't support gfx6/7, so the round trip goes through its assembler. Instructions whose LLVM syntax can't express an encoding exactly (unused fields, alternative encodings) go on a short, reviewed list of known differences.
   - It translates with the default key, and the module passes `spirv-val`.
   - A report counts opcodes, untranslated instructions and wave-size-dependent shaders. It goes to `analysis/`, not into the repo.
   - **Corpus test as built** (`tests/gpu/gcn/corpus_test.cpp`, #121; needs the game, `analysis/shaders/` and `llvm-mc`). It reads the program files one at a time and takes the code from the footer block (the first `OrbShdr` marker; code size in bits 8 to 31 of the u32 at +8). A program whose code hash (SHA-256) was seen before is skipped: 3,832 of the 20,218 programs have different code, with 1.51 million instructions. The decoder runs with `Until::program_end`, and the program must end exactly at the footer's size with one `s_endpgm`, the last instruction. Each distinct encoding (313,295) goes into a batch of 50,000 lines, which `assemble_each` (in `llvm_mc.cpp`) gives to `llvm-mc` for `bonaire`; the words and LLVM's printed text must equal ours. `assemble_each` takes the rejected lines from llvm-mc's error output (kept apart from stdout, because the interleaving of the two pipes cuts lines), so one rejected line does not stop the batch. The test then assembles the same lines for `tahiti` to find the CI features (above). Memory is the set of distinct encodings plus one batch (about 0.5 GB resident in the debug build with sanitizers), and the run takes about 20 s.
   - The known differences in the test are the ones the corpus hits. Of those documented above (scalar, DS, VOP3 and so on) it hits one: `ds_swizzle_b32`, where LLVM prints the offset as `swizzle(QUAD_PERM,…)` and we print the number (703 distinct encodings; the words are equal). Everything else the game uses assembles to the original words with the same text. An entry that the corpus no longer hits fails the test.
   - The opcode histogram goes to `analysis/gcn-opcode-histogram.tsv` (format, opcode, name, instructions and programs, most used first). Counts are over the programs with different code. The 208 opcodes in use are, by instructions: VOP2 49%, VOP1 13%, VOP3 12%, SOPP 7%, SMRD 6%, VINTRP 3.5%, SOP1 2%, VOPC, MTBUF, EXP and MIMG 1 to 2% each, SOP2, MUBUF and DS under 1%; 55 opcodes cover 95% of the instructions and 89 cover 99%.
   - **Translation coverage as built** (`tests/gpu/gcn/coverage_test.cpp`, #132; needs the game, `analysis/shaders/` and `spirv-val`). It runs every distinct program (by code hash, as above) through `translate` and counts what comes out, so it works with whatever the translator supports: a `GcnError` is a gap, counted by the instruction it stops at (decoded at the error's offset) and by its message with the mnemonic and the numbers replaced, which groups one kind of gap in one row. Any other exception, or a module that `spirv-val --target-env vulkan1.3` rejects, fails the test. The program-reading helpers moved into `tests/gpu/gcn/corpus.*` (shared with the round-trip test).
     - **Key.** `default_key(type)` in the test gives the key, from test defaults, as the footer carries no register values. Vertex and copy shaders (types 1 and 6) get the vertex key with `VGPR_COMP_CNT` 3 and no user SGPRs (#129). Domain shaders (type 8) also run on the VS stage, but with other inputs ("Not in the key yet" under "Graphics stages"), so like the other programs they get the default compute key, whatever their stage, and are probes that count the instructions the translator lacks, not translations. Each opcode probe (below) is translated with the key of the program type its first occurrence comes from.
     - **Probes.** A program stops at its first gap, and almost all programs begin with the same instruction, so the per-program counts hide the rest. The report therefore also translates each opcode of the corpus alone (its first occurrence followed by `s_endpgm`; a branch gets the offset of the next instruction) and lists the result per opcode with its instruction and program counts. The headline number is the share of the corpus's instructions whose opcode translates alone. It says an opcode is accepted, not that every operand form is.
     - **Report.** `analysis/gcn-translation-coverage.txt`: totals (programs, translated, wave-size-dependent, opcodes that translate alone, instruction share), a stage table (program files and how many translate), the gap tables by instruction, by stage and instruction, and by message, the probe results, and the probe result per opcode, most used first. The run takes about 15 s. Later items extend it when they land: a stage key replaces the default one, and a new counter goes into the totals.
3. **Execution tests** (CI with lavapipe):
   - Small GCN programs are written in assembly by us under `tests/gpu/programs/`. `llvm-mc` assembles them, and the words are committed next to the source as hex text (`.hex`, one instruction per line). That way CI doesn't need LLVM, and the hooks don't mistake the files for game binaries. When `llvm-mc` is installed, a test checks that the hex matches the source. The programs stay small, because they count toward the PR line limit.
     - Format (#123): `<name>.s` is LLVM assembly for `bonaire`, with `;` comments. `<name>.hex` has one line per instruction, each word as 8 lower-case hex digits, the words of a line separated by one space (2 words for a literal or a 64-bit encoding; gfx7 has nothing longer), and a final newline. `smov_literal` is the example.
     - Branches take numeric offsets, not labels: `llvm-mc -show-encoding` leaves a label's fixup unresolved in the encoding it prints, so `assemble_file` rejects a source that uses one.
     - `tests/gpu/gcn/programs.*` (in `bbgcntest`) reads the words. `GcnPrograms.WordsMatchSource` assembles each source with `assemble_file` and compares, and skips without `llvm-mc`.
   - Each program is translated and run on lavapipe with input buffers. Its output is compared with values worked out by hand from the ISA manual. Cross-lane results are worked out for the device's subgroup size, not for 64.
   - They cover ALU semantics (output modifiers, clamping, 24-bit multiplies), EXEC predication and loops, scalar and buffer memory with range checks, and LDS.
   - Denormal tests run only where the driver's float-controls properties allow GCN's mode, otherwise they skip. Transcendental results are compared with a tolerance in ULPs.
   - A graphics test renders a VS and PS pair into an offscreen image.
   - **Graphics runner** (`tests/gpu/runner/graphics_runner.*`, in `bbcomputerunner`, #129 part 4). `GraphicsRunner` derives from `ComputeRunner` and shares its setup: `bbvk`'s device and scheduler on lavapipe, the guest memory and the draw block, which the compute runner offers its subclass through protected accessors (`device()`, `scheduler()`, `guest_buffer()`, `guest_size()`, `draw_block()`). The guest memory's buffer is also a transfer source and destination (the runner uploads textures from it and reads the render target back into it).
     - `render(vs, ps, draw, vertices, target)` builds a pipeline with dynamic rendering (entry points `main`, one `R32G32B32A32_SFLOAT` color attachment, a triangle list without vertex buffers, no culling, blending or depth, the viewport and scissor over the target), clears the image to the target's color, draws, and copies the image to the start of the guest memory (16 bytes per pixel, row after row). The barriers are `synchronization2`'s; the scheduler's submission ends with the barrier to host reads. The image, view, modules and pipeline go through `defer()`, as in the compute runner. Before `guest_memory`, or when the image doesn't fit into it, it throws `std::logic_error`.
     - **One draw block for both stages.** The runner's keys leave `push_offset` at 0, so the vertex and pixel shaders of a draw share one block and one `user_data`, and the test gives the PS no user SGPRs. The backend gives each stage its own block (VS at push offset 0, PS at 8; "Per-draw data"); the runner can follow when a test needs user data in both stages.
     - **Render test** (`tests/gpu/runner/render_test.cpp`): `vs_attrs` (with its key from `stages_test.cpp`) draws the triangle (-1,-1), (3,-1), (-1,3), which covers a 16x8 target, with the attribute (x, y, 0.25, 1) at 0 at the first vertex and 2 in x and y at the others, so at a pixel center it is the center over the target size. `ps_discard` (`tests/gpu/programs/ps_discard.s`) enters whole quad mode with `s_wqm_b64` (quad swaps in a fragment shader), interpolates the attribute, restores EXEC, keeps the pixels whose x is at least 0.5 with `v_cmpx_le_f32` and exports to `mrt0` with `done vm`. The test checks every pixel: the left half keeps the clear color (the lanes outside the valid mask are demoted, so they write nothing), the right half holds the attribute within 1e-5. Both modules also go through `spirv-val`.
     - A translated pixel shader discards with `OpDemoteToHelperInvocation`, so `bbvk` now requires `shaderDemoteToHelperInvocation` (see "bbvk device core").
     - Lavapipe lists no vertex stage in `subgroupSupportedStages` (fragment, compute, task and mesh). The vertex module declares `GroupNonUniform` and reads `SubgroupLocalInvocationId`, which works; a VS with subgroup operations needs that stage on the device (see "Open questions").
     - The graphics pipeline's threads in lavapipe allocate state that Mesa keeps reachable only from the driver's globals, which LeakSanitizer reports once the loader has unloaded the driver. `ComputeRunner::create` therefore pins the loaded driver with `dlopen("libvulkan_lvp.so", RTLD_NOLOAD | RTLD_NODELETE)`, so it stays loaded until the process exits; the `leak:pthread_once` suppression stays for the binaries without the runner.
   - **Compute runner** (`tests/gpu/runner/`, the static library `bbcomputerunner`, #123). `tests/gpu/CMakeLists.txt` builds it only when `find_package(Vulkan)` finds Vulkan, so CI without the packages still builds everything else.
     - `ComputeRunner::create(why)` makes `bbvk`'s instance and device on lavapipe (the selector `"llvmpipe"`, see "bbvk device core", part 3). It sets `VK_LOADER_DRIVERS_SELECT=*lvp*` first, unless the environment already sets it, so the loader doesn't load and initialize the other installed drivers. The translator needs `shaderInt64`, `bufferDeviceAddress`, `subgroupBroadcastDynamicId` (a broadcast from a lane computed at run time), `subgroupSizeControl` and `computeFullSubgroups`, `shaderMaximalReconvergence` (`VK_KHR_shader_maximal_reconvergence`, for the modules with subgroup operations), and the basic, vote, ballot and shuffle subgroup operations in compute; `bbvk`'s device requires and enables them with the backend's own.
     - Without an instance, without lavapipe or without one of these, it returns nothing and `why` names what is missing; the tests then skip with that text. While the filter is `*lvp*`, the loader fails `vkCreateInstance` when lavapipe is missing, even with other drivers installed, so that failure is reported as a missing lavapipe driver; under another filter from the environment it is reported as a missing Vulkan instance. Two tests point `VK_DRIVER_FILES` at a missing file to check both wordings.
     - `info()` reports the device and driver names, the subgroup size with its range, and the 32-bit float controls (denormals preserved or flushed, RTE and RTZ rounding, signed zero, Inf and NaN preserved). Lavapipe from Mesa 26.2 (LLVM 22, 256 bits) reports subgroup size 8 (8 to 8), and neither denormal mode, so the denormal tests will always skip there.
     - Mesa allocates one-time state under `pthread_once` and never frees it, and the loader unloads the driver before LeakSanitizer runs, so the frames have no module name. The object library `bbvktest` defines `__lsan_default_suppressions()` with `leak:pthread_once` for the Vulkan test binaries.
     - `guest_memory(base, size)` allocates the guest's GPU-visible memory: one zeroed, host-visible and host-coherent buffer with a device address, at guest address `base`, replacing the previous one. It returns the mapped bytes. A size of 0 throws `std::invalid_argument`.
     - `run(spirv, draw, groups)` writes the draw block into a buffer of its own, with `address_bias` = device address of the guest memory − `base` (modulo 2^64). Its device address is the only push constant, 8 bytes, and there are no descriptor sets. It builds the pipeline (entry point `main`), records the dispatch into the scheduler's command buffer and waits for its value (30 s); the submission's barrier makes the shader's writes visible to the host. Called before `guest_memory`, it throws `std::logic_error`.
     - The test module is written with `SpirvBuilder` and checked with `spirv-val` when it is installed. It reads the draw block like a translated program: the guest addresses of its output and input come from user data, it adds a user-data value to every input word, and invocation 0 writes `SubgroupSize` and `code_address`. The guest addresses lie above 2^32, so the high words count. The test runs it twice, the second time on new guest memory at another base, so the reuse of the scheduler's command buffer is covered. The pipeline asks for no subgroup size, so the test accepts any power of two in the device's range.
   - The exact wave-64 mode runs locally on an AMD GPU.
4. **Replays** (later wave, after M3):
   - Captures of real frames, as PM4 streams plus the memory they reference, go to `analysis/captures/`. They come from our runtime, or as reference frames from an emulator run on the game.
   - The captures are replayed through `bbpm4` and `bbvk`, and the images are compared.

Committed test data is only our own: assembly sources, their assembled words, and expected values. Nothing extracted from the game is committed.

## Command buffers to the first frame (second wave)

The game reaches its main loop (M3). On the render thread it binds shaders, builds command buffers, submits them and flips three video-out buffers, all into logging stubs (a 60 s run on 2026-11-06). The second wave turns those submissions into Vulkan work up to the first presented frame. shadPS4 (GPL-2.0-or-later, like us) solves the same problem; its structure is summarised below and its code may be adapted where that is faster, file by file with the notices `docs/source-policy.md` asks for.

### Decisions

- **One GPU thread.** The submit imports only queue work. One thread (`bb::pm4::GpuThread`) runs the graphics queue, its constant engine and the compute rings. Each stream is a parser state that can stop at a wait (`WAIT_REG_MEM`, `WAIT_ON_CE_COUNTER`, `WAIT_ON_DE_COUNTER_DIFF`, `MEM_SEMAPHORE`, an unset `REWIND` bit) and resume later; the thread round-robins over the runnable streams. shadPS4 does the same with C++20 coroutines (`video_core/amdgpu/liverpool.cpp`); a plain resumable cursor is enough for us.
- **Register mirror.** `bbpm4` keeps the four register spaces as arrays indexed by dword offset (config 0x2000, SH 0x2C00, context 0xA000, uconfig 0xC000), with typed accessors for the registers the backend reads. Offsets and opcode numbers come from AMD's MIT headers `si_ci_vi_merged_offset.h` and `si_ci_vi_merged_pm4_it_opcodes.h`, copied unchanged into `third_party/amd-gcn/` (they also settle the packet names that [gnm.md](../formats/gnm.md#open-questions-and-next-steps) left unverified). Field layouts may be adapted from shadPS4's `amdgpu/regs*.h` and `pm4_cmds.h`.
- **CPU-side packets run on the GPU thread in stream order**: `WRITE_DATA`, `COPY_DATA`, `DMA_DATA` (fill and copy), the memory write of `EVENT_WRITE_EOP`, `EVENT_WRITE_EOS` and `RELEASE_MEM`. Before such a write the thread waits for the Vulkan work recorded so far (a timeline semaphore value), so a label never claims work that hasn't finished. A stream that stops at `WAIT_REG_MEM` or `MEM_SEMAPHORE` first submits the work it has recorded, or a wait on a value that GPU work writes would never end. Interrupt selects trigger the equeue events the game registered with `sceGnmAddEqEvent`. `ACQUIRE_MEM` and `PFP_SYNC_ME` are no-ops while guest memory is host memory (below).
- **Stage register imports** (`sceGnmSetVsShader` and the others, [gnm.md](../formats/gnm.md#shader-objects-and-the-stage-writers), `src/hle/video/gnm_shader.*`, #271; VS, PS and CS are implemented, ES, GS, HS and LS follow in a second part) write the standard `SET_SH_REG`/`SET_CONTEXT_REG` packets for their register block and fill the rest of their fixed size with one `NOP` whose payload is zero. Block layouts (from shadPS4's `gnmdriver.cpp`, checked against the game's shader files below), with the dwords the import writes:

  | Stage | Dwords | Register block | Extra argument |
  |---|---|---|---|
  | VS | 29 | `PGM_LO, PGM_HI, RSRC1, RSRC2, SPI_VS_OUT_CONFIG, SPI_SHADER_POS_FORMAT, PA_CL_VS_OUT_CNTL` | modifier |
  | PS | 40 | `PGM_LO, PGM_HI, RSRC1, RSRC2, SPI_SHADER_Z_FORMAT, SPI_SHADER_COL_FORMAT, SPI_PS_INPUT_ENA, SPI_PS_INPUT_ADDR, SPI_PS_IN_CONTROL, SPI_BARYC_CNTL, DB_SHADER_CONTROL, CB_SHADER_MASK`; NULL unbinds (program address and `DB_SHADER_CONTROL` 0) | – |
  | CS | 25 | `COMPUTE_PGM_LO, COMPUTE_PGM_HI, RSRC1, RSRC2, COMPUTE_NUM_THREAD_X, Y, Z` | – |
  | ES | 20 | `PGM_LO, PGM_HI, RSRC1, RSRC2` | modifier |
  | GS | 29 | `PGM_LO, PGM_HI, RSRC1, RSRC2, VGT_STRMOUT_CONFIG, VGT_GS_OUT_PRIM_TYPE, VGT_GS_INSTANCE_CNT` | – |
  | HS | 30 | `PGM_LO, PGM_HI, RSRC1, RSRC2, VGT_TF_PARAM, VGT_HOS_MAX_TESS_LEVEL, VGT_HOS_MIN_TESS_LEVEL` | `VGT_LS_HS_CONFIG` |
  | LS | 23 | `PGM_LO, PGM_HI, RSRC1, RSRC2` | modifier |

  `PGM_HI` must be 0 (code below 1 TiB, which the guest window keeps), and a non-zero modifier may set only `SGPRS` and `VGPR_COMP_CNT` (the RSRC1 bits outside `0xfcfffc3f`); otherwise the import fails and writes nothing. For VS and ES a non-zero modifier replaces both fields; for LS it will replace `VGPR_COMP_CNT` only when it sets a bit there (shadPS4's mask choice). The game's CS import is `sceGnmSetCsShader`, which takes no modifier (`0xfffffc3f` belongs to `sceGnmSetCsShaderWithModifier`, not imported). shadPS4 writes the context registers of the "unchanged" variants (`sceGnmUpdate*Shader`) inside `NOP`s with payload `0xc01exxxx`, and LS's `RSRC2` twice; we register the same functions for the "unchanged" variants. That is equivalent where the callers pick them only when the context-register dwords are unchanged: the VS (0x108fbb0), PS (0x108fdd0) and HS (0x1090380) binders compare exactly those dwords (object +0x18..+0x20, block dwords 4–6; +0x18..+0x34, dwords 4–11; dwords 4–6 and the `VGT_LS_HS_CONFIG` value), and the parser skips `0xc01e` tags like other `NOP`s. The GS binder (0x1090b30) instead compares the three context dwords of the copy shader's VS object, which follows the GS object's input-usage table (+0x50 + 4 × usage count). So where the GS's own context registers change while the copy shader's don't, the update variant writes the new values; that is the state the bound object asks for, and the copy shader's registers come from the VS binder anyway.

  **Checked against the shader files** (`GnmShaderGame.LayoutsAgreeWithTheShaderFiles`): the entry header of every shader file holds the shader object from 0x34 (so the register block from 0x3c, with the code offset from 0x34 as `PGM_LO` and 0xffffffff as `PGM_HI`, which the game replaces with the address). Each VS, PS and CS block (13,863 of the 18,517 entries) goes through its stage's import, and the registers written agree with the program: RSRC1's `VGPRS` and `SGPRS` cover every register the code uses; VS `SPI_SHADER_POS_FORMAT` has a format exactly for the exported positions, `VS_EXPORT_COUNT` + 1 is the number of parameter exports, and `PA_CL_VS_OUT_CNTL` is non-zero exactly when `pos1` is exported (0x400003, clip distances); PS `SPI_SHADER_COL_FORMAT` and `CB_SHADER_MASK` are set exactly for the exported render targets, `SPI_SHADER_Z_FORMAT` and `Z_EXPORT_ENABLE` exactly with an `mrtz` export, `SPI_PS_INPUT_ENA` equals `SPI_PS_INPUT_ADDR`, and `NUM_INTERP` covers the interpolated attributes; CS `NUM_THREAD_X/Y/Z` equal the three u16 at entry 0x18. Moving any of the checked dwords in the writers fails the test. For the second part, a survey script (not part of the test) found the GS and HS layouts in the files too: GS `VGT_STRMOUT_CONFIG` is non-zero exactly in the 10 entries with stream-out records and the primitive type is 0–2; HS `VGT_TF_PARAM`'s `TYPE` equals entry byte 0x18 and `VGT_HOS_MAX_TESS_LEVEL` the float at entry 0x20 in all 404 entries. The objects also hold dwords the imports don't write (from the same survey): VS +0x24 (two small counts), PS +0x38 (equal to `NUM_INTERP`), CS +0x24 (0), ES +0x14 (in 1,695 of 1,699 four times the output count, so `VGT_ESGS_RING_ITEMSIZE`, which the eboot writes itself at 0x1075a90) and +0x10, LS +0x10 and +0x14 (a multiple of 16), GS +0x24..+0x34 (+0x34 the maximum output vertex count, equal to the u16 at entry 0x1a), HS +0x24..+0x3c. Their meaning is for the items that need them (#281).
- **GPU memory mirror.** Guest addresses are host addresses (the guest window, m3-core-os.md). The backend mirrors the first *N* GiB of the guest window (default 32 GiB; the window places mappings from its start) in sparse `VkBuffer`s of 2 GiB and binds each GPU-visible guest mapping into them at its window offset. The GPU then reads what the CPU wrote with no copies and no write tracking, and labels written by the CPU are seen by `WAIT_REG_MEM` directly. The spike (#268) settled how, with `MemoryMirror.*` in `tests/gpu/runner/memory_mirror_test.cpp`: a translated program (`mem_mirror`) reads what the CPU wrote and writes back through the bias, in mappings bound into two different sparse buffers, on lavapipe (Mesa 26.2.6, LLVM 22.1.8) and on RADV (Radeon RX 7800 XT, Mesa 26.2.6, kernel 7.2). `VK_LOADER_DRIVERS_SELECT='*radeon*'` with `BB_TEST_VK_DEVICE=radv` runs the tests on RADV; they print the limits below.
  - **Imports are dma-bufs of the direct memory memfd, not host pointers.** Direct memory is a memfd and its mappings are `MAP_SHARED` views of it (m3-core-os.md). RADV refuses a host pointer into such a view: `vkAllocateMemory` returns `VK_ERROR_INVALID_EXTERNAL_HANDLE`, while anonymous private memory imports and binds fine. Lavapipe accepts the import, but binding host-pointer memory into a sparse buffer maps nothing there (the bind returns success, and the shader then faults on the address). `/dev/udmabuf` turns a memfd range into a dma-buf, which both drivers import (`VK_KHR_external_memory_fd` with `VK_EXT_external_memory_dma_buf`) and bind into sparse buffers created with that handle type. The spec allows that only when `vkGetPhysicalDeviceExternalBufferProperties`, asked with the sparse binding and sparse residency flags and the mirror's usage (storage buffer, shader device address), reports the handle type importable (VUID-VkBufferCreateInfo-pNext-00920). Both drivers do: dma-buf reports features 0x6 (exportable, importable) and host allocation 0x4 (importable), checked by a separate probe, not by the tests. Item 14 checks it at device choice and rejects a device without it. Binding then follows direct-memory offsets rather than host addresses. What it needs:
    - The memfd is created with `MFD_ALLOW_SEALING` and sealed with `F_SEAL_SHRINK` (not `F_SEAL_WRITE`) after its `ftruncate` (`dmem.cpp`, since #276).
    - `/dev/udmabuf` must open. On the reference machine (Fedora 44, systemd 259) udev tags it `uaccess`, so the logged-in user gets an ACL. Other distributions are unchecked. Without it the backend has no mirror and says why. The tests skip.
    - One udmabuf holds at most the module's `size_limit_mb`, 64 MiB by default, so a longer range is imported and bound in pieces of up to 64 MiB.
    - udmabuf pins the pages of its range. The mirror therefore imports only GPU-visible mappings (block-rounded, below), when they are mapped, and frees the import at unmap. A release punches holes into the memfd (`dmem.cpp`), and pinned pages would live on in an import, so the import must be gone first. The eboot unmaps before it releases (0x20826fd), except on one clean-up path that drops the mapping's address (0x26d3f70, `dmem.cpp`); there the release has to drop the import of a still-mapped range itself.
    - The imported memory is system memory. RADV offers it as host-visible, coherent and cached (memory type 5, flags 0xe), lavapipe as type 0 (0xf).
  - **Buffers of 2 GiB and a bias table.** `maxBufferSize` is 0xfffffffc on RADV and 0xffffffff on lavapipe, so 2 GiB is the largest power of two below it, and 16 buffers cover 32 GiB. RADV gave 16 new 2 GiB sparse buffers consecutive device addresses (from 0xffffc00180a00000) while the test kept its 2 GiB measuring buffer alive, but not once it destroyed that buffer first (from 0xffffc00100200000, with a gap), and Vulkan doesn't promise it anyway. Capture-replay can't pick addresses either: `VkBufferOpaqueCaptureAddressCreateInfo` takes only an address captured from an identical buffer, and lavapipe lacks `bufferDeviceAddressCaptureReplay`. So the translator's single bias becomes a table of 16: device address = guest address + `bias[(guest address >> 31) & 15]`. The mask works because the window start (0x80_0000_0000) is a multiple of 32 GiB. The table doesn't change during a run (the buffers are created once), so it lives in a 128-byte buffer of its own, and the draw block's `address_bias` field (offset 64) holds the table's device address instead. The draw block stays 80 bytes and costs nothing more per draw. Each access takes its entry from its own address, not from the V# base. A naturally aligned access never crosses a 2 GiB boundary; one that did would read its second part through the wrong entry. An address past the mirror takes the entry of a buffer it doesn't lie in, so its device address lies past that buffer: the access is out of bounds (undefined, with `robustBufferAccess` off), not aliased into the mirror as this note first said. That is acceptable while the game's GPU memory sits in the first GiBs of the window. When the addresses happen to be consecutive, all entries hold the same bias. The mirror size option therefore only shrinks the mirror: at most 32 GiB, in whole 2 GiB buffers, with the table's size and mask unchanged. A larger mirror would need a bigger table and mask and a window start aligned to the mirror size, which is a design change.
  - **Binding blocks of 64 KiB.** A sparse buffer's binding granularity (`VkMemoryRequirements::alignment`) is 64 KiB on RADV and 4 KiB on lavapipe. Guest mappings are aligned to 16 KiB, so the mirror binds blocks of max(granularity, 16 KiB): the block-rounded memfd range at the block-rounded window range. That needs **window offset ≡ direct-memory offset (mod block)**. The window places direct memory to keep it: `map_direct` asks `vmem::map` for an address ≡ its offset (mod `dmem::mirror_block`, 64 KiB, RADV's granularity, so it holds for every block size seen), within the requested alignment. The alignment rules it out when the offset isn't a multiple of min(alignment, 64 KiB), for example a 32 KiB alignment at an offset that is an odd multiple of 16 KiB; the window then places the map at the alignment alone. No other GPU-visible mapping shares a block unless it views the same memfd block (adjacent views of contiguous direct memory); bound blocks then carry a reference count. The test binds a 16 KiB mapping in the middle of a 64 KiB block this way. A map that ends up breaking the congruence can't be mirrored exactly and is logged (`vmem`'s `map_locked`, since #276): one whose alignment ruled it out, a fixed map, and a batch map into a reservation, at an address the game picks. Unmap binds `VK_NULL_HANDLE` over the blocks (the test does), then frees the import.
  - **Limits.** RADV: a sparse address space of 128 TiB (0x800000000000), `minImportedHostPointerAlignment` 4 KiB, capture-replay supported. Lavapipe: 2 GiB of sparse address space in all, so its mirror is a single 2 GiB buffer, enough for tests (the spike's two-buffer test uses 1 GiB buffers there); `minImportedHostPointerAlignment` 4 KiB.
  - **No fallback needed** on RADV or lavapipe. Host pointer imports would need direct memory to be private anonymous memory, which loses the second views (map flag 0x80) and hole punching. The page table of the earlier plan (one device address per block, shadPS4's `bda_pagetable_buffer`) would only help a driver without sparse buffers.
  - **Not checked:** validation layers (none installed on the reference machine); whether one host pointer import may span several mappings (moot with dma-bufs); which GPU-visible mappings the game makes (the protection bits 0x10/0x20 on direct memory, flexible memory with GPU access, which would need a memfd too, and fixed maps into reservations), which item 21 logs.
  - **Item 21 (#276) lands in parts.** Part 1: the translator's bias table (above and "Per-draw data"), the sealed memfd, the congruent placement with the log of maps that break it, and the kernel's hook. The hook is `vmem::DirectObserver`, set once with `vmem::set_direct_observer` before the first guest mapping: `mapped` after each map of a direct region (`map_direct` and the batch map), `unmapped` for each part of a direct region, with its own offset, before an unmap, a batch unmap or the harness's restore gives it back, and `released` before `release_direct` punches its hole, also for a range still mapped (0x26d3f70). The calls run under the region table's lock (and `released` under the allocation table's), so no other map or unmap of the range comes between; the lock order is allocations, regions, mirror. Every direct mapping is reported, whatever its protection, since which ones the GPU reads is not checked. Still to come: bbvk's `MemoryMirror` (the 2 GiB sparse buffers, the bias table, udmabuf imports in runs of at most 64 MiB, blocks that count their bound guest pages, a release that imports the rest of a hit import again; tests on lavapipe with a 2 GiB mirror and 64 KiB blocks), then the observer that binds through it, the logging of flexible memory with GPU protection bits, and the mirror size option of `bb-run`.

  Performance on a discrete GPU (every read crosses PCIe) is a later concern: a device-local cache with write tracking (shadPS4's `page_manager` and `buffer_cache`) replaces the mirror for hot ranges then.
- **Mirror wiring (part 3 of #276, #343).** `bb-run` makes the mirror after the display is open (on the display's device, else on a device of its own, also with `--headless`) and sets `tools::MirrorObserver` (`src/tools/mirror_observer.hpp`) as the `vmem::DirectObserver`. Every direct mapping is mirrored whatever its protection bits, until a run shows which mappings the game makes with them. The observer records what `bind()` bound and unbinds only that (the contract of `unbind()`), so a mapping outside the mirror, one that threw, or a part that `released()` took is never unbound; `MemoryMirror::release(offset, length)` unbinds the blocks that view the range and frees the imports that pin it, and rebinds the other blocks of those imports. `--mirror-size GIB` takes 2 to 32 in steps of 2 (default 32). A flexible map with protection 0x30 logs one line at info on `hle.libkernel`. The dispatcher reads `MemoryMirror::bias_table()` for the draw block of each dispatch. The run ends with a `mirror: N binds, N unbinds, N releases` line.
- **Images** (render targets, depth, textures, display buffers) are `VkImage`s cached by guest address and descriptor. Tiled ↔ linear conversion runs as compute shaders adapted from shadPS4's `host_shaders/tiling.comp` and `texture_cache/tile.h`, which replaces the earlier plan of AMD's addrlib. Render targets are written back to guest memory only where the CPU or a later linear read needs them; the presenter reads the render target image of a display buffer directly. Without write tracking, a texture is checked once per submission: its guest memory is hashed on first use in that submission and re-uploaded when the hash changed. Write tracking replaces the hash with the device-local cache.
- **Draws** take a snapshot from the register mirror: ShaderKey per stage, fetch code from the vertex stage's user data dwords 0–1, render targets, blend, depth, stencil, raster and primitive state. Pipelines are cached by that key and use dynamic rendering. The format, blend, compare, cull and topology tables may be adapted from shadPS4's `renderer_vulkan/liverpool_to_vk.cpp`.
- **Presentation.** A window and Vulkan surface from SDL3 (zlib, the system package `SDL3-devel`; CI builds in a Fedora 44 container). The existing video-out flip thread completes flips per tick; on each flip the presenter blits the display buffer's image to the swapchain. Submit-and-flip queues the flip behind the submission's work, as shadPS4's `PatchFlipRequest` does with the 64-dword `0x68750777` NOP.
- **Unknown packets** are logged once per opcode, among them 0x8C and 0x8D, which have no name yet. "Unknown" means outside the opcodes the game writes ([gnm.md](../formats/gnm.md#pm4-packets)); those the parser doesn't run yet are skipped without a log line until their item runs them. `NOP` payloads tagged `0x6875xxxx` are skipped; the parser records the tag for the trace.
- **Parser core (item 15, #270).** Item 15 landed in parts: the register mirror (`registers.hpp`) and the packet headers (`packet.hpp`) with #270, the parser described here (`parser.hpp`) as the first part of #273. `bb::pm4::Parser` runs a `Stream` against one `RegisterMirror` and returns `done`, `waiting` or `error`. A `Stream` is a stack of up to four buffer positions (the submitted buffer and three nested `INDIRECT_BUFFER`s); a waiting or failing stream keeps its position at that packet, so the next run starts there. A chained `INDIRECT_BUFFER` (bit 20 of its size dword) replaces the current buffer, as in shadPS4. The size of a packet is taken before it runs. An optional `readable` check (the GPU thread passes the guest mapping table) rejects an `INDIRECT_BUFFER` into unmapped memory with `error` instead of a fault. A type-3 count of 0x3FFF means an empty body (a one-dword `NOP`). Type-2 dwords are filler; type-0 packets are skipped and logged once like unknown opcodes; a type-1 header, a truncated packet or a body too short for its opcode stops the stream with `error`. The four `SET_*_REG` packets fill the mirror (offset in bits 0-15, CI's index bits ignored); values past the end of a space are dropped and logged once per space. The spaces are config 0x2000-0x2BFF, SH 0x2C00-0x2FFF, context 0xA000-0xA3FF and uconfig 0xC000-0xFFFF, which hold every register of their kind in AMD's offset header. `REWIND` waits until bit 31 of its body (read with acquire) is set. `CONTEXT_CONTROL` is recorded only (we never load or shadow registers). `CLEAR_STATE` writes the context defaults, which the GPU thread installs at its start (parts 3 and 4 of #273, below). The predicate bit is decoded, and predicated packets run until `SET_PREDICATION` exists. Instead of storing `NOP` tags, the parser hands every packet that ran to an optional trace callback, and `nop_tag` decodes a `0x6875xxxx` tag from it.
- **GPU thread and submits (part 2 of #273).** `bb::pm4::GpuThread` (`gpu_thread.hpp`) owns one `Parser` and one `RegisterMirror` and a queue of `Stream`s per hardware queue; the graphics queue, the constant queue (#272, below) and one queue per compute ring (#275, below). The thread visits the queues round-robin and runs each front stream until it ends, fails or waits. A failed stream is logged at warn on `gpu.pm4` and dropped; a waiting one stays at the front of its queue and is retried on the next round. With nothing runnable the thread sleeps until a submission, or polls every 100 µs while a stream waits. `wait_idle(timeout)` waits until every queue is empty, and `stats()` counts queued, finished and failed streams and the packets that ran. The register mirror is read only while the thread is idle, as the tests do; the backend will read its state on the GPU thread itself. The HLE side (`src/hle/video/gnm_driver.cpp`) starts the thread on the first submit (`gpu_thread()`), with `vmem::mapped` as the parser's `readable` check, `gpu_interrupt` as its interrupt callback (#336) and the `--gpu-trace` trace, if any (#285). `sceGnmSubmitCommandBuffers` and `sceGnmSubmitAndFlipCommandBuffers` queue each draw command buffer as one stream after checking that it lies in guest mappings and is whole dwords long (else it is logged and left out); they return before the buffers run. Constant command buffers go to the constant queue (#272, below). The flip of the submit-and-flip doesn't wait for the GPU thread yet, since the presenter (#277) shows only test images, not what the submission drew. `sceGnmValidateCommandBuffers` queues nothing and returns `0x80d13fff` (item 18). `sceGnmSubmitDone` returns 0 and does nothing else.
- **Default state, markers and queries (parts 3 and 4 of #273).** `src/gpu/pm4/default_state.*` holds the two default state blocks, adapted from shadPS4 (`gnmdriver.cpp`, `gnmdriver_init.h`; base PS4 sequences only, the HLE never reports Neo mode), and `src/gpu/pm4/clear_state.cpp` the `CLEAR_STATE` values, adapted from fpPS4 (`chip/pm4_pfp.pas`, `t_pfp_ctx.clear_state`) under LGPL-2.1-only. `sceGnmDrawInitDefaultHardwareState200` writes `CONTEXT_CONTROL`, `CLEAR_STATE` and an `ACQUIRE_MEM` (12 dwords), then the SDK 2.00 register writes (118 dwords, ending with `GRBM_GFX_INDEX` = broadcast), and pads to the 256 dwords the caller reserved with one `NOP` whose first payload dword is 0; `sceGnmDispatchInitDefaultHardwareState` writes `COMPUTE_STATIC_THREAD_MGMT_SE0/SE1` and `COMPUTE_RESOURCE_LIMITS` (`SET_SH_REG` with the shader-type bit) and an `ACQUIRE_MEM`, padded the same way. Both return 256, or 0 without writing when fewer dwords are free. The `CLEAR_STATE` values are those fpPS4 writes, for the context space only: a `CLEAR_STATE` leaves the SH, config and uconfig registers alone. fpPS4 writes 509 of the 1,024 context registers and leaves the others unchanged; we set those others to 0 instead (a deviation from fpPS4), so no state from before a `CLEAR_STATE` survives it. `PA_SC_CLIPRECT_RULE` (0x083), `CB_TARGET_MASK` (0x08E) and `CB_SHADER_MASK` (0x08F) are among them; shadPS4 sets them to `0xDEADBEEF` placeholders. `GpuThread` installs them and starts with them in the context registers. The push and set markers write one `NOP` of exactly the size the game's writer computed (2 + (len+8)/4 + 2·((len+12)/8) dwords): tag `0x68750001` or `0x68750003`, the string with its terminator, zeros; another size fails with -1 and writes nothing. The pop marker is a 6-dword `NOP` with tag `0x68750002`. The compute twins of the markers call the same imports, and their `NOP`s carry no shader-type bit, which a `NOP` doesn't need. `sceGnmIsUserPaEnabled` and `sceGnmDriverCaptureInProgress` return 0. The unreachable imports of [gnm.md](../formats/gnm.md#unreachable) have no implementation and resolve to logging stubs; so do the reachable ones that wait for their items or are only called when profiling is on. **Acceptance run** (2026-11-07, debug build, `bb-run --headless --timeout 60`, 8 GiB memory cap): the game reaches the same point as before and runs until the timeout; the GPU thread finished 7,990 streams with 949,903 packets, none failed, and no unknown opcode was logged (0x8C and 0x8D didn't occur). In a 30 s run the draw default state was written 1,745 times, with no import failing for lack of room.
- **Constant engine (item 17, #272).** Each `Stream` belongs to an engine: the draw engine (DE) for the graphics queue's DCBs, the constant engine (CE) for the constant queue's CCBs. The `Parser` holds the CE state both engines share: CE RAM and the CE and DE counters. CE RAM is 48 KiB, the limit the game's CCB writers (0x11fd190–0x11fd911) enforce (offset ≤ 0xBFFF, offset + 4 × count ≤ 0xC000) and shadPS4's size. The CE runs `WRITE_CONST_RAM` (byte offset in bits 0-15, then the dwords), `DUMP_CONST_RAM` (byte offset, dword count in bits 0-14, destination low and high; the destination is checked with `readable`, the guest mappings), `INCREMENT_CE_COUNTER` (bit 0 of its select; bit 1, the CS partition counter, is not modelled), `WAIT_ON_DE_COUNTER_DIFF` (waits while the CE counter is `diff` or more ahead of the DE counter) and `INDIRECT_BUFFER_CONST` (the `INDIRECT_BUFFER` body; the game's writer sets bits 20, 23 and 24 like its DCB writer, so it chains), plus `NOP` and `REWIND` as the DE does. The DE runs `INCREMENT_DE_COUNTER` and `WAIT_ON_CE_COUNTER` (waits until the CE counter is ahead of the DE counter). The counters wrap at 2^32 and the waits compare their signed difference. Bits 0-1 of the CE RAM offsets are ignored. A CE RAM access past 48 KiB, a dump into unmapped memory or a body too short fails the stream. As on the hardware, each engine skips the other's packets: the DE skips the CE packets, and the CE skips the other packets of the game, logging each opcode once, except `WRITE_DATA`, which the game also writes into CCBs (0x11fd520, engine select 2 = CE in bits 30-31 of its control dword): each engine runs the `WRITE_DATA`s whose engine select names it (#274, below). The submits queue CCB *i* on the constant queue and DCB *i* on the graphics queue; when either buffer of a pair isn't readable guest memory, both are left out, since the other one's counters would wait for packets that never run. The round-robin GPU thread then runs the CE ahead of the DE until a counter stops one of them. A DE that waits on a CE counter no queued CCB will raise waits for ever (polled), as on the hardware. The `DUMP_CONST_RAM` write calls the parser's `before_write` sync point like the memory packets (below).
- **Memory packets (item 19, #274).** `src/gpu/pm4/memory_packets.cpp`, tests in `tests/gpu/pm4/memory_packets_test.cpp`. Field layouts adapted from shadPS4 (`pm4_cmds.h`), checked against the game's writers (0x1073b80, 0x10778f0, 0x1077b30, 0x1078320, 0x108b0f0).
  - Instead of waiting on a timeline semaphore itself, the parser calls a `Sync` callback at two points: `before_write`, before every memory write of `WRITE_DATA`, `DUMP_CONST_RAM` and the label packets and before an interrupt (the backend will wait there for the work recorded so far), and `before_wait`, each time a `WAIT_REG_MEM` doesn't pass (the backend will submit what it recorded; with nothing recorded that is free, so being called on every poll is fine). Without a callback the parser goes on at once. The GPU thread doesn't set one yet: no backend records work on it so far.
  - `WRITE_DATA` (control: `DST_SEL` bits 8-11, one address bit 16, `ENGINE_SEL` bits 30-31; address; data) writes memory for `DST_SEL` 1, 2 and 5 (the game uses 5), dword by dword with release stores, or every dword to one address. The CE runs those with engine select 2, the DE the others. Register destinations and other selects are logged once and skipped.
  - `EVENT_WRITE_EOP` (address high bits 0-15, `INT_SEL` 24-25, `DATA_SEL` 29-31), `EVENT_WRITE_EOS` (command 2 writes the data dword; command 1, a GDS store, is logged once and skipped) and `RELEASE_MEM` (`INT_SEL` 24-26, `DATA_SEL` 29-31, full high address dword) share the label write: `DATA_SEL` 1 writes the low data dword, 2 the qword, 3 and 4 the GPU clock (nanoseconds of the steady clock for both; shadPS4 uses the TSC for 4, which nothing in the game needs yet), 5 (GDS) is logged and skipped. A qword at an 8-byte aligned address is one atomic store, otherwise two dwords. A non-zero `INT_SEL` calls the parser's `Interrupt` callback with `gfx_eop_interrupt` (0x40, shadPS4's `GfxEop`) after the write; `GpuThread` takes the callback as its second constructor argument. A stream carries its interrupt source: the compute rings (#275) report their pipe. The game's compute `RELEASE_MEM` writer always sets `INT_SEL` 3.
  - `WAIT_REG_MEM` (function bits 0-2, memory space bit 4; poll address or register offset; reference; mask; poll interval) compares `(value & mask)` with the reference as shadPS4 does; memory is read with an acquire load, registers from the mirror at their absolute offset. Function 7 (reserved) fails the stream. A failed compare returns `waiting`, and the GPU thread polls it every 100 µs (test: a label written by the CPU releases a waiting DCB).
  - Every address is checked with `readable` (the guest mappings); an access outside fails the stream, as a body too short for the packet does.
  - `WRITE_DATA` and `COPY_DATA` write registers (any of the config, SH, context and UCONFIG spaces; other offsets are dropped with one log line each). `COPY_DATA` reads a register, memory, the immediate dwords or the GPU clock, 32 or 64 bits. `DMA_DATA` copies memory or fills dwords; GDS and register addressing are logged once and skipped. `MEM_SEMAPHORE` signals (increment, or write 1) or waits for a non-zero value and decrements it, waiting like `WAIT_REG_MEM`. The equeue imports (`sceGnmAddEqEvent`, `sceGnmDeleteEqEvent`, `sceGnmGetEqEventType`, #336) register (queue, source) pairs with user data; the GPU thread's interrupt callback triggers a `gnm_event_kind` event on each queue registered for the source. `ACQUIRE_MEM`, `PFP_SYNC_ME` and `EVENT_WRITE` stay no-ops.
- **Compute queues (item 20, #275).** `GpuThread` (`gpu_thread.hpp`) holds 56 compute rings (7 pipes of 8 queues, shadPS4's limit; pipe 7 belongs to the system), each a further queue in the round-robin after the graphics and constant queues. Tests in `tests/gpu/pm4/compute_ring_test.cpp` and `tests/hle/video_test.cpp`.
  - `29oKvKXzEZo` (`sceGnmMapComputeQueue`, `src/hle/video/gnm_driver.cpp`) checks its arguments as shadPS4 does, in its order (pipe below 7, queue below 8, a 256-byte aligned ring, a power-of-two ring size, a dword-aligned read pointer, with shadPS4's error values), and also that ring and read pointer lie in guest mappings (else the ring or read-pointer error; the ring's mapping is checked after its size, which it needs). `GpuThread::map_ring` takes a free ring, writes 0 to the read pointer (the game's wrapper 0x1089a80 clears it as well) and the import returns the ring index + 1, so the first id is 1 as the game needs. A slot whose streams an unmap left queued is reused only once the thread dropped them.
  - `bX5IbRvECXk` (`sceGnmDingDong`) gives the write offset in dwords. `ring_doorbell` queues the dwords from the previous write offset to the new one as one compute-engine stream, or as two when the offset went back (wrapped): to the ring's end, then from its start. The game's writer 0x108c830 writes only 4-dword `INDIRECT_BUFFER`s (0x108b330: header 0xc0023f02, size with bits 23 and 24, no chain bit) and wraps to the ring's start before one would cross the end; when its packets end exactly at the end it reports offset 0. So no packet straddles the end, and the parser fails a stream that does instead of joining the two parts (shadPS4 buffers such a packet). An offset equal to the previous one queues nothing; an offset past the ring or an unknown id is logged and ignored.
  - After each run of a ring stream (finished or waiting) the thread writes the read offset back with a release store: the stream's top-level position in the ring, modulo its size. A stream that fails is dropped, and the offset goes to its end as for a finished one, so the game's free space doesn't shrink. The position is past an `INDIRECT_BUFFER` that still runs, as the CP's fetch is; the game uses the read pointer only for the free space in the ring (0x108c830 computes `(read - write - 1) mod size`, so the ring never fills completely).
  - Compute streams run on `Engine::compute`: the draw engine's packets except `INCREMENT_DE_COUNTER` and `WAIT_ON_CE_COUNTER`, which it skips. An `INDIRECT_BUFFER` in the ring itself always nests, also with the chain bit, so the stream's position stays in the ring (shadPS4 chains only below the ring level). Its `EVENT_WRITE_EOP` and `RELEASE_MEM` interrupts report the pipe (shadPS4's `Compute0RelMem` + pipe); the HLE passes no interrupt callback yet.
  - `ArSg-TGinhk` (`sceGnmUnmapComputeQueue`) unmaps the ring: the thread drops its queued streams (counted as finished, not failed) and writes its read pointer no more. A run under way finishes first: the call waits until the thread has returned from it, so the guest may free the ring afterwards. It returns 0, also for an unknown id (logged), as shadPS4 does.
  - Game run (60 s, headless, 2026-11-07): the render thread maps one ring of 1,024 dwords on pipe 0, queue 0, and the main thread rings the doorbell 53 times in steps of 4 dwords; every stream parses without an error or unknown packet. The ring doesn't wrap within that run, so the wrap path is covered by the synthetic tests only.

### GPU trace (item 30, as built)

`bb-run --gpu-trace` writes `<UTC time>-<pid>-gpu-trace.txt` (mode 0600, never overwritten) in the logs directory of the state directory. `pm4::GpuTrace` (`src/gpu/pm4/gpu_trace.cpp`) is written by the GPU thread only, from the parser's per-packet trace hook, so the register mirror is as it is after the packet. Without the option the hook costs one pointer test per packet (`trace_ != nullptr`), on top of the counter and the trace-level log call that were already there.

- A draw (`DRAW_*`) or dispatch packet gives one line: `frame <n>: draw op=<opcode> body=<dwords> <first four dwords> vs=<address> ps=<address> rt0=<CB_COLOR0_BASE address> prim=<VGT_PRIMITIVE_TYPE>`, or `frame <n>: dispatch op=<opcode> body=<dwords> <first four dwords> cs=<address> threads=<x>x<y>x<z>`.

Part 2 of #269: `src/gpu/vk/scheduler.*`, tests in `tests/gpu/vk/scheduler_test.cpp`.

- `Scheduler` over the graphics queue, one per device, used by one thread. One timeline semaphore starting at 0. `commands()` begins a command buffer (`ONE_TIME_SUBMIT`) on the first call after a flush and returns the same one until the next flush; `recording()` says whether one is begun. `flush()` ends it with a `vkCmdPipelineBarrier2` from all commands' memory writes to host reads, submits it with `vkQueueSubmit2` (holding the queue's mutex) signalling `submitted() + 1` at all commands, and returns that value; with nothing recorded it submits nothing and returns `submitted()`. `completed()` reads the semaphore; `wait(value, timeout_ns)` returns whether the value was reached and throws `std::logic_error` for a value above `submitted()` (including the value of work still being recorded); `finish()` is `wait(flush())`. Other threads may wait on `semaphore()` (tested).
- Command buffers come from one pool with `RESET_COMMAND_BUFFER`, so beginning one again resets it. `commands()` takes the first command buffer whose last submission's value the semaphore has reached, or allocates one. The test holds a submission back with a `VkEvent` the host sets (`vkCmdWaitEvents` from the host stage), which makes the "still in use" case deterministic on lavapipe.
- `defer(function)` queues a function for the value of the work being recorded, or for `submitted()` with nothing recorded. `flush()`, `wait()` and the destructor run the due ones in order on the scheduler's thread; a function deferred after its work completed runs in the next `flush()`, even one that submits nothing. The destructor drops the work being recorded, waits for `submitted()` and runs every function left.

Part 1 of #279: `src/gpu/pm4/targets.*`, tests in `tests/gpu/pm4/targets_test.cpp`.

- `color_target(regs, hints, slot)` and `depth_target(regs, hints)` read the `CB_COLOR<n>_*` and `DB_*` registers of the mirror into plain structs: addresses (register << 8), pitch and height in pixels (`PITCH.TILE_MAX`, `SLICE.TILE_MAX` and `DB_DEPTH_SIZE`, so rounded up to whole tiles), the view's first slice (`SLICE_START`) and `slices` = `SLICE_MAX` + 1 (`SLICE_MAX` is the absolute index of the view's last slice, so `slices` is the image's layer count up to the end of the view, and the view covers slices `base_slice` to `slices` - 1, that is `slices` - `base_slice` layers; the image cache and the rendering's `layerCount` must not add `base_slice` again), `FORMAT`, `NUMBER_TYPE` (6 is SRGB in the CB, not `SNORM_NZ` as in a T#), `COMP_SWAP`, the tile mode index, the sample count (`NUM_FRAGMENTS` for colour, as shadPS4), the CMASK and HTILE addresses, `FAST_CLEAR` with `CB_COLOR<n>_CLEAR_WORD0/1` (one pixel as stored in memory), and the depth and stencil clears of `DB_RENDER_CONTROL`, `DB_DEPTH_CLEAR` and `DB_STENCIL_CLEAR`. A colour target exists when its base and format are non-zero; the depth target when depth (format and read base) or stencil (format and read base) is present, and a missing part is left out. `LINEAR_GENERAL` is decoded but its address offset (shadPS4 adds the low byte of `SLICE_START`) is not applied.
- **The game writes the extent hint.** The registers give the size only in whole tiles, so the exact size comes from the `NOP` after the setup, as in shadPS4. Found statically in the eboot's GNM code (no Ghidra):
  - The colour target setter (0x10738b0) writes one `SET_CONTEXT_REG` (header 0xc00b6900) of the 11 registers `CB_COLOR<n>_BASE` to `CB_COLOR<n>_FMASK_SLICE` from dwords 0-10 of the render target object, then the one-dword `NOP` 0xc0001000 with dword 6 (+0x18). Dword 6 also goes to register 0xA31E + 15n, which is `CB_COLOR<n>_DCC_CONTROL` on VI and unused on CI, so the mirror holds the colour hint as well. For a NULL target it writes only `CB_COLOR<n>_INFO` = 0.
  - The depth target setter (0x10739b0) writes `DB_Z_INFO` to `DB_DEPTH_SLICE` (header 0xc0086900, object dwords 0-7), then four single registers, `DB_DEPTH_INFO` (+0x2c), `DB_DEPTH_VIEW` (+0x20), `DB_HTILE_DATA_BASE` (+0x24) and `DB_HTILE_SURFACE` (+0x28), then the hint `NOP` with +0x30. For a NULL target it writes `DB_Z_INFO` = 0 and `DB_STENCIL_INFO` = 0.
  - A byte search of the code finds the headers 0xc00b6900 and 0xc0086900 once each (in these setters) and none of the other colour counts shadPS4 accepts (0xc00d6900, 0xc00e6900). Its third case, a hint after four registers from `CB_COLOR<n>_CMASK`, doesn't occur either: the three 0xc0046900 headers write float registers. The other 0xc0001000 immediates in the GNM code are one-dword `NOP`s with 0 or a 0x6875xxxx tag, or variable-length `NOP` headers.
  - The hint holds the width in bits 0-15 and the height in bits 16-31 (shadPS4's reading; the code that fills the object was not traced, so this is checked at run time).
- `ExtentHints` sees every packet that ran (the parser's trace callback; the GPU thread connects it, item 18). A `SET_CONTEXT_REG` starting at `CB_COLOR<n>_BASE` or `DB_Z_INFO` drops that target's hint and waits for a new one; other `SET_CONTEXT_REG`s keep the wait (the depth setter's four registers); a following `NOP` with header 0xc0001000 and a body that is no 0x6875 tag sets it; any other packet ends the wait. A zero width or height is no hint. Without a hint the target's extent is its pitch by its height.

Part 2a (as built): `src/gpu/vk/formats.*`, tests in `tests/gpu/vk/formats_test.cpp`.

### Tiling (item 23, as built)

Part 1 of #278: `src/gpu/tile/tiling.*` (`bbtile`, namespace `bb::tile`, only `bbcommon`, so it builds and tests without Vulkan), tests in `tests/gpu/tile/tiling_test.cpp`. Adapted with notices from shadPS4 (ff1b7a2e) `amdgpu/tiling.*` (the tile mode tables), `texture_cache/tile.h` (the level sizes) and `host_shaders/tiling.comp` (the address computation), on the CPU.

- **Supported tile modes** (`mode_info`): the thin non-PRT ones with eight pipes (P8_32x32_16x16) and the linear ones: 0-4 (`Depth2DThin64` to `1K`, split 64 to 1024 bytes), 5 (`Depth1DThin`), 8 (`DisplayLinearAligned`), 9 (`Display1DThin`), 10 (`Display2DThin`), 13 (`Thin1DThin`), 14 (`Thin2DThin`) and 31 (`DisplayLinearGeneral`). PRT, thick and 3D modes (6, 7, 11, 12, 15-30) give nothing; the game's display buffers and textures don't use them (below), and render and depth targets with other modes are found by the targets item at run time.
- **One fragment only.** With one fragment the bank width is always 1, a colour tile is never split (the colour tile split is at least the tile's own bytes, so it is taken as 1024 and shadPS4's sample split drops out), and the macro tile mode is log2(min(split, 64 × bytes) / 64), one of 0-4 (`1x4_16`, `1x2_16`, `1x1_16`, `1x1_16_Dup`, `1x1_8`). The macro tile is 64 × aspect by 8 × bank height × banks / aspect elements, which reproduces shadPS4's `macro_tile_extents_x1` rows for these modes (checked once against the table; the table itself is not copied).
- **Layouts** (`layout`): level i starts from max(pitch >> i, 1) by max(height >> i, 1) pixels (the T#'s or the target's pitch, as shadPS4), divided into 4x4 blocks for BC formats (`blocks`), then padded: linear aligned to a pitch multiple of max(8, 64 / bytes) and a layer of a multiple of max(64, 256 / bytes) elements; 1D to 8x8 and a layer of a multiple of 256 bytes; 2D to whole macro tiles, except levels after the first that are smaller than one macro tile, which fall back to 1D (`Level::macro`); linear general not at all. Levels follow each other, each layer after layer. Pow2 padding and the depth of volume textures are left to the textures item. A surface of 4 GiB or more gives nothing (the shader will use 32-bit offsets).
- **Addresses** (`tiled_offset`): linear row-major; 1D the micro tile in rows of pitch / 8, then the element's index in the 8x8 micro tile (display order by element size, thin and depth x0 y0 x1 y1 x2 y2); 2D as `ComputeSurfaceAddrFromCoordMacroTiled` with the tile split, the P8_32x32_16x16 pipe bits, the 16- or 8-bank bits, the 2D slice rotation, the split rotation and the T#'s `BANK_SWIZZLE`. The linear copy (`detile`, `tile`) keeps the padded rows, so it has the same size and level offsets as the tiled surface.
- **Tests:** every supported mode at 8 to 128 bits with three levels and two layers maps every element to its own element of the surface (a bijection onto the whole size), offsets worked out by hand for `Display2DThin` and `Thin1DThin`, the display buffer layout, three game texture sizes from the TPF headers (below), padding rules, unsupported input, and a CPU round trip.

**Tile modes the game uses** (read statically, objdump and the game's archives):

**Part 2: the compute detiler and tiler on `bbvk`.** No GLSL compiler is a build dependency (glslang isn't installed), so instead of porting `tiling.comp` instruction by instruction through the SPIR-V builder, the CPU splits one level's offsets into tables per column, row and layer, and a small shader recombines them; this deviates from "Images" above, which planned the shader as an adaptation of `tiling.comp`. In every supported mode the micro tile index has the x and the y bits in separate places, so the element offset, its tile split index and the macro and micro tile offsets each split into an x part plus a y part, the pipe and bank bits into an x part XOR a y part, and the slice rotation and swizzle into a per-layer part. Each table entry is {offset, pipe_bank | split << 16}; with per-level constants `split_bytes` (the bytes of one split slice), `split_rotation` ((banks / 2 + 1) << 3), `pipe_bank_bits` (3 + log2 banks, 0 for linear and 1D levels) and its mask:

```
split     = (col[1] >> 16) + (row[1] >> 16)
total     = col[0] + row[0] + layer[0] + split * split_bytes
pipe_bank = (col[1] ^ row[1] ^ layer[1] ^ split * split_rotation) & pipe_bank_mask
offset    = level.offset + (total & 255 | pipe_bank << 8 | total >> 8 << (8 + pipe_bank_bits))
```

The column part of a 2D level is (x / macro width) × macro bytes + the x bits' element offset (mod the split), pipe (tx0 ^ tx1, tx1, tx2) and bank x / 64; the row part (y / macro height) × macro tiles per row × macro bytes + the y bits' element offset + (y / 8 mod bank height) × tile bytes, pipe y / 8 & 7 and the bank bits of y / 8 / bank height; the layer part layer × splits × `split_bytes` with bank (swizzle + (banks / 2 - 1) × layer). A test compares this recombination with `tiled_offset` for every element of every mode before the shader is built on it. The 500-line limit splits it in two:

- **Part 2a (as built): the tables and the shader.** `address_tables` and `combine` in `bbtile` (the test above); `src/gpu/vk/tiler.*` in `bbvk`, which now links `bbgcn` privately for its SPIR-V builder: `tiling_shader(bytes, to_linear)` builds the shader for elements of 1, 2, 4, 8 or 16 bytes (an 8- or 16-bit integer, or a vector of two or four words for 64 and 128 bits, BC blocks included), in one direction. One invocation per element of a level, workgroups 8x8x1 over pitch × height × layers, invocations past the pitch or the height do nothing (linear general and linear aligned levels aren't multiples of 8). Everything goes through device addresses (`PhysicalStorageBuffer64`, no descriptors): the 48-byte push constants (`TilingConstants`) hold the level's tiled and linear addresses (the level's offset already added), the address of its tables (the column, row and layer entries one after another, 8 bytes each), the padded pitch and height and the four constants above. The invocation loads the column entry x, the row entry pitch + y and the layer entry pitch + height + z, recombines them as above without the level's offset, and copies one element from the tiled offset to the linear offset ((z × height + y) × pitch + x) × bytes, or back, with 32-bit offsets (layouts stay below 4 GiB). 8- and 16-bit elements need `storageBuffer8BitAccess` and `storageBuffer16BitAccess`, which `bbvk`'s device now requires ("bbvk device core"). Test: the ten shaders pass `spirv-val`.
- **Part 2b (as built): pipelines and the round trip.** `Tiler` in `src/gpu/vk/tiler.*` (`bbvk` now links `bbtile` publicly) holds one pipeline layout (the push constants, no descriptor sets) and the ten pipelines, made on first use. `record(commands, layout, level, tables, addresses, to_linear)` adds the level's offset to the surface's tiled and linear base addresses, pushes the constants and dispatches ceil(pitch / 8) × ceil(height / 8) × layers workgroups; the caller orders it against other work with barriers (the levels of one surface write disjoint bytes, so they need none between them) and keeps the tiler alive until its work is done. `table_words(tables)` flattens one level's tables for the table buffer. Test (`tests/gpu/vk/tiler_test.cpp`, skips without lavapipe): tiles our own data with `tile` on the CPU, detiles it on the GPU, tiles that linear copy back on the GPU and compares both with the CPU copies byte for byte, for every supported mode at every element size with three levels and two layers, and a 2D surface with a bank swizzle. This closes #278.

### Pipeline state (item 26, as built)

Part 1 of #281: `src/gpu/vk/pipeline_state.*`, tests in `tests/gpu/vk/pipeline_state_test.cpp` and, against the eboot, `tests/game/clip_space_test.cpp`. Part 1 covers the stages with their keys and the fetch address, the topology and the clip space. Raster, blend, depth, stencil and the remaining dynamic state didn't fit into the same 500 lines and are part 2.

- `draw_state(regs, quad_control, why)` takes the snapshot of a draw from the register mirror and returns a `DrawState`: the `PipelineKey` a pipeline is made and cached by (item 31), and the `DynamicState` a draw sets on the command buffer. The split follows Vulkan 1.3: what core dynamic state covers (the viewport, cull mode, front face and blend constants; depth, stencil, scissor, depth bias and primitive restart are still the draw's) is dynamic, the rest goes into the key. The topology stays in the key, as only its class could be dynamic without `dynamicPrimitiveTopologyUnrestricted`. The targets' formats are not in the key: they come from `RenderingInfo` (item 24), which item 31 adds to its cache key. Unsupported state gives nothing and a reason in `why`, never a fallback.
- **Stages.** `VGT_SHADER_STAGES_EN` must be 0 (VS and PS only; the other stages come with tessellation and geometry shaders). Each stage is a `StageState`: the program address (`SPI_SHADER_PGM_LO/HI_*`), the `ShaderKey` from the stage's registers (as listed under "Stage interfaces and ShaderKey"; the image classes come from the T#s with the textures item, 28), and for the VS the **fetch address** from user-data dwords 0-1 when `USER_SGPR` is at least 2. The snapshot can't know whether the program calls a fetch subroutine without decoding it, so item 31 compares the fetch address only for programs that do (it knows once it has decoded the program), or a VS whose dwords 0-1 hold a per-draw pointer would miss the cache on every draw. A zero PS address (the NULL PS of the stage import) means no pixel stage (depth only).
- **Topology** from `VGT_PRIMITIVE_TYPE`, adapted from shadPS4's `liverpool_to_vk.cpp`: lists, strips, fans and the adjacency types; polygon as a triangle fan, as shadPS4. Rect lists, quad lists and strips, line loops and patches have no Vulkan topology and are unsupported until a later part emulates them (shadPS4 draws rect and quad lists as patches with its own tessellation shaders).
- **Clip space.** On the hardware `DX_CLIP_SPACE_DEF` of `PA_CL_CLIP_CNTL` only chooses the clip volume (z from 0 to w, or from -w to w); the viewport transform is zscale · z + zoffset either way. The viewport therefore keeps the hardware's transform in both conventions: depth from zoffset to zoffset + zscale, or with `negativeOneToOne` (`VK_EXT_depth_clip_control`, which item 31 needs on the device) from zoffset - zscale to zoffset + zscale, as shadPS4's `UpdateViewportScissorState`. Without depth clipping (`CLIP_DISABLE`, or a `ZCLIP_NEAR_DISABLE` or `ZCLIP_FAR_DISABLE`, as shadPS4's `ZclipEnable` takes one alone as off) the key sets `depth_clamp`, and the clip space no longer matters: the transform is the same in both conventions, and only the clamp range differs. Vulkan's depth clamp clamps to the viewport's depth range, the hardware to `PA_SC_VPORT_ZMIN/ZMAX` (normally 0-1). So the key sets `negativeOneToOne` exactly when zoffset ± zscale lies within 0-1 (an OpenGL-style zscale = zoffset = 0.5 then clamps to 0-1, not to 0.5-1), and otherwise keeps z from 0 to w (the game's zscale 1, zoffset 0 then clamps to 0-1, where -w to w would have to clamp the range and change the transform). A range narrower than 0-1 (zscale 0.25, zoffset 0.5) still clamps to that range rather than to 0-1. The depth range is clamped to 0-1 (no `VK_EXT_depth_range_unrestricted`). x and y: x = xoffset - xscale, width = 2 · xscale, and the same for y, so the game's negative yscale gives a negative height (core since Vulkan 1.1) and NDC y = 1 lands at the top, as on the hardware. `PA_CL_VTE_CNTL` must have `VTX_W0_FMT` and neither `VTX_XY_FMT` nor `VTX_Z_FMT` (positions divided by w, as in Vulkan); a disabled scale is 1 and a disabled offset 0. A zero x or y scale draws nothing and gives no snapshot; a negative x scale gives none either (a Vulkan viewport may only have a negative height). Deviation from shadPS4: it treats `CLIP_DISABLE` as screen-space positions and sets a viewport over the whole 16K window with a patched VS; the hardware keeps the viewport transform under `CLIP_DISABLE` (that is `VTX_XY_FMT`'s job), and the game's full-screen pass below relies on it.

### Pipeline creation and cache (item 31, as built)

#287: `src/gpu/vk/pipeline_cache.*`, tests in `tests/gpu/vk/pipeline_cache_test.cpp`.

- `PipelineCache::get(key, targets, why)` returns the `GraphicsPipeline` for a `PipelineKey` (item 26) drawing into the formats and sample count of a `RenderingInfo` (item 24; its extent and layers don't count). It makes the pipeline on the first request and returns the same object for every equal request. The cache reads the stages' code through a `CodeReader` (guest address to the readable dwords from there on, empty when unreadable), which the draw item gives the guest mapping table; the tests give it their own programs.
- **Fetch address.** The translator now reports whether a VS program calls the fetch subroutine (`ShaderInterface::calls_fetch`). The first translation of a VS (code address and `ShaderKey`) without the call records it, and from then on its requests are looked up with the fetch address cleared, so a VS whose user-data dwords 0-1 hold a per-draw pointer doesn't miss on every draw. For a program with the call the fetch address is part of the key.
- **Pipeline.** The VS and, unless the key has none, the PS as translated modules (entry point `main`); no vertex input (the VS fetches through the mirror); the key's topology; one viewport and scissor; `depthClampEnable` and `negativeOneToOne` (`VkPipelineViewportDepthClipControlCreateInfoEXT`) from the key, which needs `VK_EXT_depth_clip_control`, `depthClipControl` and `depthClamp` on the device (added to item 14's requirements); fill mode, line width 1; the sample count of the targets; `VkPipelineRenderingCreateInfo` with the targets' colour, depth and stencil formats; per colour target the blend state and write mask of the key (part 2 of item 26) and the key's polygon mode. The layout has one push-constant range of 16 bytes for both stages ("Per-draw data").
- **Dynamic state** of every pipeline (`graphics_dynamic_states`): viewport, scissor, cull mode, front face, depth test, depth write and compare op, stencil test, op, compare mask, write mask and reference, depth bias and its enable, blend constants, primitive restart. Recording them is the draw item's (27): the snapshot has the viewport, cull mode, front face and blend constants so far. The draw must set every one of them before it draws.
- **Deviation: no descriptor sets yet.** The layout has no set layouts; a stage whose translation uses images or samplers gives an error instead. The set layouts for the translator's bindings (one set per hardware stage, `gcn::descriptor_set`) come with the textures item (28), which allocates the sets. `GraphicsPipeline` keeps both stages' `ShaderInterface` for the draw and textures items.
- **Errors.** A stage whose code isn't readable gives nothing and a reason, and nothing is kept, since the program may be mapped by the next request. A translation error or a stage with images is kept with the key, logged once at warn on `gpu.vk`, and given again for an equal request without translating again. A VS whose fetch subroutine is unmapped (it calls it) is unreadable code too. A VS error that doesn't depend on the fetch subroutine (the same error without it) is kept without the fetch address, so a per-draw pointer in the user data doesn't add an entry per draw. A failing Vulkan call throws; its entry and the objects made so far are dropped, so the next request tries again (as `ComputePipelineCache` does).
- **Not yet.** The cache is in memory only and keyed by guest addresses, so a program or fetch subroutine replaced at the same address was not noticed until #371 (see "Code hash of a cached pipeline"); a disk cache (a `VkPipelineCache` and a key by code hash) comes later. Stages aren't cached on their own: a VS is translated again for every new pipeline it is part of. Lavapipe creates the test pipelines; a draw with them comes with item 27.

### Code hash of a cached pipeline (#371)

A pipeline is looked up by guest address and register-derived key. Without a check, a game that puts other code at an address it used before (a streamed or recycled shader buffer) would get the old pipeline. Whether Bloodborne does this is not known (in a 40 s run its 6 compute programs sit at fixed addresses), so both caches check.

- **Choice: hash the code on every lookup.** The alternatives are a hash once per frame (a replacement between two draws of one frame would be missed) and tracking writes to the shader's pages (needs a write observer on the guest mapping and cannot tell a shader from the data around it that shares a page). The per-lookup hash needs nothing but the `CodeReader` and is exact. shadPS4 also keys its shader cache on a hash of the binary.
- **Extent.** The reader returns the mapping to its end, so the hash covers only what the translation used: `Translation::code_dwords` (the program up to its last instruction) and `fetch_dwords` (the fetch subroutine up to its `s_setpc_b64`). An entry that failed to translate has no known extent and stamps the first 64 KiB (`error_stamp_dwords`).
- **Entries.** `common::CodeStamp` (dword count and `common::hash_code`, four 64-bit lanes) is kept per piece of code an entry was made from: the CS; the VS, the PS and the fetch subroutine. A lookup reads the code, and an entry matches only when its key is equal and its stamps match (unreadable or shortened code does not match, so it gives "no readable code" as a first request does). Changed code makes a new entry; the old one stays, because the GPU may still use its pipeline, and matches again if its code returns. The set of versions per address is not bounded; it grows only as often as the game changes the code. The record of a VS that does not call the fetch subroutine carries the VS stamp, so a program that starts calling it is translated again with its fetch address.
- **Cost, measured offline** on the extracted shaders (about 20,300 programs; code sizes in dwords: VS median 184, p99 1461; PS median 445, p99 1450; CS median 80, max 5969), release-like build (`-O2`), one core of the development machine, hot cache: 193 dwords 0.11 us, 981 dwords 0.50 us, 1450 dwords 0.73 us, 5969 dwords 3.0 us (about 8 GB/s). A compute dispatch pays one hash of its program: typically 0.05 to 0.2 us, 3 us at worst. A draw pays VS plus PS plus, for a VS that calls it, the fetch subroutine (a few dozen dwords): about 0.4 us typical, 1.5 us for two of the largest. At the few thousand draws of a frame that is on the order of 1 ms or less of one core per frame, and the debug build with sanitizers is slower. If a profile shows it, the next step is a per-frame hash of a program that was already checked in the frame.

### Compute pipelines (item 25, as built in #280)

`compute_state(regs, why)` (`pipeline_state.hpp`) snapshots the CS registers into a `ComputeState`: the program address (`COMPUTE_PGM_LO/HI`) and a `ShaderKey` with `COMPUTE_PGM_RSRC1/2` and `COMPUTE_NUM_THREAD_X/Y/Z`, push offset 0. A zero program address gives nothing. `ComputePipelineCache` (`compute_pipeline.hpp`) translates the program read through a `CodeReader` and makes a pipeline whose layout has one 8-byte compute push constant (the draw block's address) and no descriptor sets yet (textures item, 28). The cache is keyed by the whole state, so an equal state returns the same pipeline; user data is not part of the key. Translation errors and shaders with images are kept as errors, unreadable code is not. Recording dispatches is #345 (parser and recording as built below).

### Dispatch packets in the parser (item 25, part 1 of #345)

`DISPATCH_DIRECT` (body: x, y, z, `COMPUTE_DISPATCH_INITIATOR`) and `DISPATCH_INDIRECT` become a `DispatchCall` (`groups`, or `indirect`, and `initiator`). On the draw engine `DISPATCH_INDIRECT` has the body offset, initiator and `indirect` is the `SET_BASE` address (base index 1) plus the offset; on a compute ring (`Engine::compute`) it has the body address lo, address hi (48 bits), initiator, with no `SET_BASE`. The call goes to the callback of `Parser::set_dispatch` together with the register mirror. `SET_BASE` with base index 1 is kept as the base address (48 bits) per stream, so one stream's base never reaches another; other base indexes are ignored. An indirect dispatch without a base, a packet that is too short, or counts outside readable guest memory fail the stream. A dispatch with `COMPUTE_SHADER_EN` (initiator bit 0) clear does nothing. Without a callback dispatches are skipped as before. `GpuThread::set_backend(dispatch, sync)` installs the callback and the parser's `Sync` callback; both run on the GPU thread, which knows nothing of Vulkan. Tests: `tests/gpu/pm4/parser_test.cpp`, `gpu_thread_test.cpp`.

### Dispatch recording and the game run (item 25, parts 2 and 3 of #345)

- **`vk::Dispatcher`** (`src/gpu/vk/dispatcher.*`) runs on the GPU thread over a `Scheduler`, a `ComputePipelineCache` and the `MemoryMirror`. A dispatch whose program is unreadable, doesn't translate or uses images is counted as `untranslated` (the reason is logged once per program) and the stream goes on. A Vulkan failure, indirect counts outside the mirror or unaligned, or group counts over the device limit count as `failed` and drop that dispatch only. `sync(before_wait)` submits the recorded work, `sync(before_write)` submits and waits for it, so memory packets see what the dispatches wrote. `stats()` can be read from another thread.
- **`bb-run`** makes the scheduler, the cache (its code reader returns the guest dwords up to the end of the mapping, at most 1 MiB) and the dispatcher right after the mirror, and installs them with `gpu_thread().set_backend` before the game starts, because `set_backend` asserts that no stream is queued. Without a mirror (no device, no direct memory) or when the dispatcher can't be made, dispatches are skipped as before and a warning says why. The objects are never destroyed: `bb-run` ends in `_exit`, so they outlive the GPU thread. The run ends with `dispatches: N recorded, N untranslated, N failed`.
- **Game run** (2026-11-09, debug build, `bb-run --headless --timeout 40`, 8 GiB cap): `dispatches: 0 recorded, 7961 untranslated, 0 failed`. The programs are rejected by the translator with `COMPUTE_PGM_RSRC2` 0x98 or 0xa0 (thread-group and thread id enables the translator doesn't support yet, #253), so no game dispatch runs through the mirror yet; they will once the translator handles those ids.

## Draw packets (item 27, #282, parser part)

`src/gpu/pm4/draw_packets.cpp`. `INDEX_BASE`, `INDEX_BUFFER_SIZE`, `INDEX_TYPE` and `NUM_INSTANCES` set the index state of the stream (like `SET_BASE`; `NUM_INSTANCES` starts at 1). `DRAW_INDEX_2`, `DRAW_INDEX_AUTO`, `DRAW_INDEX_OFFSET_2`, `DRAW_INDEX_INDIRECT` and `DRAW_INDIRECT` each call `Parser::set_draw`'s callback with the register mirror (the snapshot source: the backend builds it with `vk::draw_state`) and a `DrawCall` (kind, index buffer address and size, first index and count, instances, indirect argument address and the two user data registers, initiator). Without a callback, draws are skipped; a draw with no vertices or no instances is not reported and is not checked further (it needs no index buffer). A packet that is too short, an indexed draw without a buffer address, unreadable indices or arguments, or an indexed draw with an `INDEX_TYPE` other than 16 or 32 bit (8-bit is not supported) stop the stream. The `*_MULTI` draws have no callers and stay unhandled. Recording into Vulkan is #346.

### Recording draws (#346, `src/gpu/vk/draw_recorder.*`, tests in `tests/gpu/vk/draw_recorder_test.cpp`)

`DrawRecorder::draw` is the parser's draw callback on the GPU thread, next to the `Dispatcher` and on the same `Scheduler`. For each draw it builds the `DrawState` (`draw_state`, with the device's `quad_control`), orders the draw after earlier shader writes (a memory barrier; the dispatcher's barrier now also covers vertex and fragment shader writes), begins a dynamic rendering into the register mirror's targets (`TargetRenderer::begin`: one rendering per draw, so a dispatch between two draws never sits inside one), gets the pipeline from the `PipelineCache`, takes one draw block per stage from the dispatcher (`Dispatcher::draw_block`: the stage's user data, the bias table, the code address), pushes the two block addresses (VS at `vertex_push_offset`, PS at `pixel_push_offset`), sets the whole `graphics_dynamic_states` list from `DynamicState` (the scissor clipped to the rendering's extent) and records `vkCmdDraw` or, with the index buffer bound at its mirror offset (`VK_BUFFER_USAGE_INDEX_BUFFER_BIT` is now one of the mirror's buffer usages; an offset that isn't a multiple of the index size or a buffer outside the mirror fails the draw), `vkCmdDrawIndexed` with the first index of `DRAW_INDEX_OFFSET_2`. A draw whose state, shaders or targets aren't supported is counted as `unsupported` and logged once per reason; a Vulkan error or a bad index buffer is counted as `failed`; the stream goes on either way. Indirect draws are not recorded yet (they are `unsupported`). The recorder has no sync callback of its own: `Dispatcher::sync` serves both, and its `before_wait` is idempotent (`Scheduler::flush` submits nothing when nothing was recorded), so the parser's retry of a waiting packet every 100 microseconds doesn't submit. `PipelineCache::create` clears `blendEnable` of a target whose format lacks `COLOR_ATTACHMENT_BLEND`. The test renders the render test's `vs_attrs`/`ps_discard` pair through the parser (`DRAW_INDEX_AUTO`, `DRAW_INDEX_2` with 16-bit and `DRAW_INDEX_OFFSET_2` with 32-bit indices from the mirror) into an 8_8_8_8 target on lavapipe and checks every texel by read-back, with and without a scissor. Not wired into `bb-run` yet.
