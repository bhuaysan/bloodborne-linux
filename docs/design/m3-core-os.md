# Core OS design (M3)

How the runtime carries the game from its entry point to its main loop: loading the bundled PRXs, TLS, threads, sync, memory, time, files, runtime directories and logging. It builds on [runtime.md](runtime.md) (loader, stubs, hooks, harness). Issues of milestone M3 build on this note. Change it in the same PR when an implementation has to deviate.

Facts marked *(survey)* come from our static analysis of the pinned build; addresses are link addresses of the eboot unless a PRX is named.

## Goal: "main loop reached"

`main` (0x1e4a6c0) runs its init and then loops `while (tick()) {}` at 0x1e4a6f0. The tick (0x2018d20) has that loop as its only direct caller. Each tick calls the frame pacer (0x2034770, 0x820 bytes, only caller the tick), which reads the wall clock through `gettimeofday` (libScePosix) and sleeps through `sceKernelUsleep` until 1/30 s has passed *(survey)*.

**Criterion.** The main loop is reached when `gettimeofday` has been called 60 times from a return address inside 0x2034770–0x2034f90, while `main` has not returned. The HLE `gettimeofday` checks its return address against that range, so the check needs no hooks and no graphics. `bb-run --stop-at-main-loop` logs `main loop reached after <n> s` and exits with status 0 at that point, through the `_exit` path (flush the log, then `_exit(0)`), never `std::exit`: worker threads are still running, and host `atexit` handlers, static destructors and LeakSanitizer must not run under them. The game test runs exactly that with a timeout.

What must work before that point: PRX init, TLS, threads, mutexes, rwlocks and condition variables (the task system starts worker threads), kernel memory mapping (the eboot maps a 116 MiB block itself), an advancing wall clock and sleeps, and success results from `sceSysmoduleLoadModule(0xb4)`, `sceAppContentInitialize` and `sceUserServiceInitialize`. Network and PSN initialisation (`sceNetInit`, `sceHttpInit`, …) sit on the init path too *(survey)*.

## System services

libSceSysmodule, libSceUserService, libSceSystemService, libSceAppContent, libScePlayGo and libSceDiscMap live in `src/hle/system/` (`bbhlesystem`, an `OBJECT` library that `bb-run` links next to `bbhle`). Every module load succeeds and is tracked. One user (id 1) is logged in from the start, named after the profile (a setter, default `default`, until the runtime directories pass `--profile` on). No system events, no add-on content, the game fully installed as one PlayGo chunk, no libSceDiscMap remapping. Each value chosen for the game is documented in `system.hpp` with its call-site address. Error results that the game compares (`0x805a1001`, `0x80960002`, `0x80960003`) are the game's; the others are ours, since their callers only test for non-zero.

## Loading the bundled PRXs

- **Load set.** eboot, `libSceFios2.prx` and `libc.prx`, each checked against the hashes in `docs/clean-room.md`. The PRXs are mapped one after the other above the eboot, each at the next address aligned to its largest `p_align`. The other five bundled PRXs are not loaded.
- **Binding.** An import resolves, in this order, to: an export of a loaded module with the same library name and NID, an HLE implementation, a stub. `libSceLibcInternal` imports of libSceFios2 resolve to the libc.prx export with the same NID when one exists (15 of 16 do; a NID is the hash of the name alone). One HLE layer less, and the two libraries share one heap. All 216 libc imports of the eboot (202 of them referenced) and the 21 distinct libSceFios2 NIDs of the eboot (17) and libc.prx (8) bind to bundled exports; `bb-load` prints the bindings per module and library.
- **Exports go through `bb::hle`.** The load set maps all three modules first. It then registers every export of the PRXs with the HLE layer (`bb::hle::register_export(library, nid, address)`; libc.prx's exports a second time under `libSceLibcInternal`, unless that library exports the NID itself; `STT_TLS` exports are skipped, since base + `st_value` is no address for them), and only then relocates the three images with `bb::hle::resolve`. `resolve` applies the order above. So runtime.md's numbered steps stay as they are (only its game-runtime row grows), and `import_address` still returns exactly what the loader wrote into the GOT. Registering an export for an import that was already resolved, or registering it twice, is a `std::logic_error`, per (library, NID) as for implementations. An HLE implementation that an export shadows is logged once at start.
- **Module ids.** Loading order defines the TLS module id: eboot 1, libSceFios2 2, libc 3. All `R_X86_64_DTPMOD64` relocations of the PRXs (14 in libc, 3 in libSceFios2) name symbol 1, a local section symbol with an empty name and `st_shndx` 0 *(survey)*. `relocate` accepts `R_X86_64_DTPMOD64`, ignores its symbol and writes the id of the module being relocated, which it takes as a parameter. The offset cell next to each one is a link-time constant: there are no `R_X86_64_DTPOFF64` relocations.
- **Init.** In both PRXs `DT_INIT` is a real function at link address 0 (also `e_entry`) with the signature `(rdi, rsi, fn)`. It runs the preinit array and the constructor list, and then tail-calls `fn(rdi, rsi)` if `fn` is non-null, otherwise `module_start` *(survey)*. The runtime calls it as `init(0, nullptr, nullptr)`, on the game's main thread before the entry call (see Entry), libSceFios2 first, then libc. The two modules import from each other, so the order is not a dependency order. It is harmless because libSceFios2's init does nothing: its preinit array and constructor list are empty and its `module_start` cell is 0 *(survey)*. A non-zero return aborts the start.
- **libc runs the game's allocator.** libc's preinit entry asks libkernel for the process parameters (NID `959qrazPIrg`) and gets the runtime address of the eboot's `PT_SCE_PROCPARAM` block. Its +0x38 points to a 0x78-byte block (version 9 at +8, 1 at +0xc). The block's +0x30 points to a table of 12 functions in the eboot (0x20809d0–0x2081490), and its +0x60 to a second table of 5 (0x20814a0, 0x20814b0, 0x20814c0, 0x20817a0, 0x2081640). libc copies them into its dispatch cells, so its `malloc` family calls the game's own allocator *(survey)*. During preinit libc calls only the first entry of each table, both no-ops. The game's heap, a 116 MiB direct-memory block (allocate and map), is set up lazily on the allocator's first allocation *(survey)*, on whichever thread allocates first. Whether a libc constructor allocates during init is not known. PRX init runs on the game's main thread anyway, so all game code, the allocator included, runs on threads that have the eboot's TLS block and go through the same start-up path.
- **Eboot init.** The eboot's entry calls its own `DT_INIT`, so the runtime never does.
- **Fini.** PRX `DT_FINI` is not run at process exit in M3. libc's exit handler already flushes stdio, and the process ends anyway.

## Entry

The game's main thread is a pthread created by the runtime with a 16 MiB stack, not the process's initial thread, so the stack size is ours to choose and the initial thread can watch the timeout. It first runs the PRX initialisers (see Init), then calls the entry 0xa0 as `entry(args, exit_handler)`: `rdi` points to `{int argc; char* argv[]}` with `argv[0] = "/app0/eboot.bin"`, and `rsi` is a function the entry registers with `atexit` *(survey)*. libc's `exit` calls it, so it must be valid: the runtime passes a function that does nothing (PRX `DT_FINI` is not run in M3). `exit` ends in our `_exit`, which flushes the log and calls `_exit(2)`.

## TLS: one thread pointer for game and runtime

The eboot uses initial-exec TLS only: `mov rax, fs:0` followed by adding a constant from one of 15 GOT cells, all in [-0x750, -0xb]. That is its 0x750-byte, 16-aligned `PT_TLS` block directly below the thread pointer, variant II [Drepper]. It never reads `fs:0x28`. Its stack guard is the libkernel data import `f7uOxY9mM1U`. The PRXs contain no `fs` accesses. They reach their TLS through the libkernel helper `vNe1w4diLCs` with a `{module, offset}` pair (general dynamic), which the eboot imports but never calls *(survey)*.

**Decision.** Game code runs with glibc's thread pointer. `fs:0` is the self pointer in glibc too.
- The eboot's block is reserved as one 0x750-byte, 16-aligned block at the top of the executable's TLS segment: not a `thread_local` but an assembly-defined block in the input section `.tcommon` (see open question 1). It lives in an `OBJECT` library linked into `bb-run` and into every test executable that runs game code (the game tests, and the harness executables once they run PRX init or fs-using eboot functions; for those, this lifts runtime.md's M2 "no TLS" limit). At start, and in every new thread, each of them checks that the block ends exactly at the thread pointer. Otherwise it aborts with an error that names both addresses. glibc zero-fills it per thread, which matches the eboot's template (file size 0).
- The TLS helper hands out per-thread, per-module blocks initialised from the module's `PT_TLS` template. It creates them on first use and frees them at thread exit. Its `{module, offset}` argument is not always 8-byte aligned (libSceFios2 passes 0x4c084, for example *(survey)*), so the helper reads it with `memcpy`, never through a struct pointer. `bb::hle::link` registers the PRXs' templates last (`bb::hle::kernel::register_tls_modules`). A block starts at an address congruent to its template's link address modulo `p_align`, so the link-time offsets keep their alignment: libc.prx's template lies at 0xb8018 with `p_align` 0x10. The helper (`src/hle/kernel/tls.cpp`) aborts for a module without a registered template and for an offset outside the module's block.
- The helper keeps each thread's blocks in a `thread_local` list whose destructor frees them, so they go when glibc runs the thread's `thread_local` destructors. Thread exit (#94) must therefore run the game's own exit hooks (whatever the eboot and libc.prx register to run at thread exit) before glibc's `thread_local` destructors: such a hook may still reach its TLS through the helper, and a call after the list's destructor uses a destroyed object.
- **Why:** there is no `fs` switching anywhere, so HLE calls, hooks, callbacks and signal handlers need no glue (this closes the TLS point that runtime.md left open). The other option, a PS4-layout thread block per thread with `wrfsbase` on every transition, needs glue at every boundary and breaks signal handlers that run on the wrong `fs`.

## Threads

- The thread handle of the scePthread functions and the POSIX `pthread_t` of libScePosix are pointers to our `Thread` object (host `pthread_t`, name, attributes, return value). The sce and POSIX entry points share one implementation and differ only in how they report errors.
- Stack size and detach state are applied. Priority, scheduling policy and affinity are recorded and logged, not applied. Names go to `pthread_setname_np` (cut to 15 bytes) and into the log.

## Sync

- Mutexes, rwlocks and condition variables: the game's object holds a pointer to our object. For mutexes and rwlocks it wraps the glibc primitive of the matching type. A condition variable is our own waiter queue instead: each waiter sleeps on its own host condition variable, so destroy knows which waiters are still blocked (see [kernel-abi.md](../formats/kernel-abi.md#condition-variables)). An object still holding its static-initialiser value is created on first use, under a global lock. The issues confirm the guest object size and initialiser values from the game and libc.prx code.
- Mutex attributes hold their values in the guest's 8-byte cell itself (tagged), not a pointer, so they need no object of ours. Mutexes, rwlocks and condition variables are in `src/hle/kernel/sync.cpp`; `sync.hpp` hands the host mutex behind a guest mutex to other modules. Sizes, initialiser, types and timeouts: [kernel-abi.md](../formats/kernel-abi.md#mutexes-and-rwlocks) and [condition variables](../formats/kernel-abi.md#condition-variables).
- The counted sync object (create/destroy/wait/try-wait/post, `src/hle/kernel/counted_sync.cpp`, [kernel-abi.md](../formats/kernel-abi.md#counted-sync-object)) and the event queue (create/destroy/wait, triggered from our own code, e.g. a flip) are our own objects on a mutex and a condition variable. Other HLE modules raise events through `bb::hle::EventQueue::trigger(handle, event)`; the event record, the wait's timeout and the results are in [kernel-abi.md](../formats/kernel-abi.md#event-queue).
- Error results: see [Errors](#errors).

## Errors

Every POSIX entry point (threads, sync, files, memory, time) reports FreeBSD `errno` values, in the convention of its family: calls in the style of `open`, `read`, `mmap` and `clock_gettime` return -1 and set the guest `errno`; `pthread_*` calls return the error number and leave `errno` alone. Every sce entry point returns the sce error encoding and leaves `errno` alone, unless the ABI issue finds a caller in the game or libc.prx that reads `errno` after one; it then writes that down. It found two eboot callers, and in both the value makes no difference ([kernel-abi.md](../formats/kernel-abi.md#sce-error-codes)), so the rule stands. Host `errno` values are translated through one table in `src/hle/kernel/`. A POSIX call that fails sets the guest `errno`: the per-thread `int` whose address the libkernel errno-location import hands to libc.prx and the eboot, never glibc's `errno`. The `errno` values, the flag values, clock ids and struct layouts, each with its source, are in `docs/formats/kernel-abi.md`, taken from FreeBSD's errno(2), FreeBSD's public system headers (allowed by `docs/clean-room.md` since #77, under the limits written there: each value confirmed against the game's or libc.prx's use, release and header files logged in `docs/references.md`) and how libc.prx converts results.

## Process

The process basics live in `src/hle/kernel/process.cpp`. Call sites are in libc.prx unless named otherwise.
- `__error` returns `guest_errno_location()`. The stack guard `__stack_chk_guard` and `__progname` are data imports whose blocks are filled when they are resolved ([runtime.md](runtime.md#data-imports)): the guard with a random non-zero 64-bit value from `getrandom`, `__progname` with a pointer to `"eboot.bin"` in the same block. `__stack_chk_fail` logs its caller and aborts.
- `getpid` returns the host pid. `sysctl` answers only the MIB libc.prx passes, `{1, 14, 32, pid}` (0x52f50, 0x52fe1), `kern.proc.vmmap` ([kernel-abi.md](../formats/kernel-abi.md#sysctl-mib)), a map of the process's memory that libc walks to find the file holding an address. We report it empty (length 0), so libc finds nothing and fails as for a failed `sysctl`. Other MIBs are logged and refused with `ENOENT`.
- `signal`, `sigprocmask`, `sigreturn` and `6xVpy0Fdq+I` (the mask call of libc's `setjmp` and `longjmp`, `sigprocmask` arguments) log and succeed without touching host signal state; an old mask they return is empty. `sigfillset` fills the 16-byte guest set. The calls on the `setjmp` path log like stubs (1 to 10, then every 1000th). libc's `longjmp` pushes two registers before it calls `6xVpy0Fdq+I` (0x2fd17), so that call arrives with the stack 8 bytes off the SysV alignment; our function realigns it (`force_align_arg_pointer`). `setjmp` (0x2fcc6) pushes one and is aligned.
- `zE-wXIZjLoM` logs the code and returns: libc's exit path calls it right before `_exit`. `OMDRKKAZ8I4` logs the code and aborts: libc's wrapper at 0x1f560 has no code after the call, so libc does not expect it to return there (a deviation from the issue's "log the code", which assumed both return).
- `_exit` flushes the log and calls host `_exit` with the status.

## Memory

- Kernel map calls (`mmap`, the anonymous and named variants the allocator uses) become host `mmap` calls with translated flags. The host picks addresses: every observed call site passes flags 0, no fixed address *(survey)*.
- **Guest pages are 16 KiB.** `getpagesize` returns 0x4000, every mapping the host picks starts at a multiple of it (the runtime reserves 12 KiB more and trims), and lengths are multiples of it: `mmap` rounds up, the sce map calls refuse other lengths. The eboot rounds its own map lengths to 0x4000 (0x2081d8c) and passes it as an alignment (0x29032a9).
- **Region table** (`src/hle/kernel/vmem.hpp`, internal to the kernel module): start, end, guest protection, flags, direct-memory offset and name of every guest mapping. The queries read it, and every map and unmap is logged with it. A partial unmap or protect splits a region. Unmap, protect and mlock refuse (`EINVAL`, sce `ENOMEM` for mlock) a range that isn't covered by guest mappings, so the game can never unmap the runtime's memory; libc.prx's call of the release with address 0 after a failed map (0x23ee9) gets that error and ignores it. A guest `MAP_FIXED` never replaces a mapping (`MAP_FIXED_NOREPLACE`); no call site passes it. `mmap` refuses flags without a host counterpart and `MAP_SHARED` together with `MAP_PRIVATE` (`EINVAL`). The direct memory issue adds its mappings through the same table, with flag bit 1 and their offsets.
- **File mappings.** A file mapping (no `MAP_ANON`) looks its guest descriptor up in `fd_table()` (`EBADF` if it isn't open) and maps the host descriptor through `vmem::map`, so it is in the region table (flags 0, named `fd N`) and the log. Its offset must be a multiple of the guest page size (`EINVAL` otherwise); no call site passes one other than 0. A mapping without `MAP_SHARED` or `MAP_PRIVATE` is private, as for anonymous maps. The host enforces the descriptor's access mode, so a shared writable mapping of a read-only descriptor fails with `EACCES` as on FreeBSD, and nothing under `/app0` can be written through a mapping. libc.prx's only file mapping is `mmap(0, st_size, PROT_READ, MAP_PRIVATE, fd, 0)` (0x530e1).
- **Not applied:** `sceKernelMlock` only checks the range: the host's `RLIMIT_MEMLOCK` would make libc.prx's arena growth fail, which releases the arena when mlock fails (0x23ed9). `msync` goes to the host for any address, because libc.prx's only call (0x541a5) probes whether a 4 KiB page is mapped.
- **Direct memory** (allocate a range of "physical" memory, map it, release it, query the total size): backed by one `memfd` of fixed size, with the allocations as offset ranges in it. Mapping maps the memfd at that offset. Mapping the same range twice aliases, as it must. The protection bits above `PROT_EXEC` (0x30, used together with read/write) are accepted and dropped for the host, but kept in the region table, since the protection query reports them (the eboot tests bit 4 at 0x26bae04). The first use is logged once. The eboot's anonymous map call can pass them as well (prot 3 or 0x33 at 0x2081da6).
- **Total size: 8 GiB.** The memfd is created sparse (`ftruncate`, no pages until touched) with the size that the total-size query returns, at the first allocation. Every caller uses the size only as the end of an allocation's search range (0x33eacc, 0x2081a9b, 0x2081eaf, 0x26d3edd), so it only has to be larger than what the game holds at once. Since the file is sparse, a larger size costs nothing.
- **Allocation** (`src/hle/kernel/dmem.cpp`): the allocations are offset ranges `[start, end)` with a type, kept apart even when adjacent so that the type query `BC+OG5m9+bw` can report each. An allocation takes the lowest offset that is a multiple of the alignment and leaves the whole allocation inside `[search start, search end)`; a search end past the total size is clamped to it. No such offset: the sce code of `ENOMEM` (callers only test for non-zero). The alignment is a power of two: 0 means the guest page, smaller ones are raised to it, others are refused (`EINVAL`), as are lengths that aren't a multiple of the guest page. Every call site searches the whole of direct memory from 0, with alignments 0x4000, 0x10000 and 0x200000 (the 116 MiB heap at 0x2081a9e). Most round the length up to the alignment; 0x33ead5 rounds it only to 0x4000 (0x33ea91) while its alignment is the larger of its argument and 0x4000 (0x33eaa4), so a length need only be a multiple of the guest page.
- **Map** puts a `MAP_SHARED` view of the memfd at an address aligned to the call's alignment, through `vmem::map` (whose `Mapping::alignment` does the reservation and trim), with flag bit 1 and the offset in the region table. The range must lie in allocations. Map flag 0x80 (0x29032a4, a second view of mapped memory) is accepted and ignored, others are refused.
- **Release** rounds the length up to the guest page (0x33eb1d passes it unrounded), refuses a range that isn't all allocated, splits allocations at its ends and punches a hole into the memfd. Mappings that are left (0x26d3f70 drops one) stay mapped and read zeros; they are not unmapped for the game.
- **Not yet (#177):** the type query `BC+OG5m9+bw`, the address range reservation `7oxv3PPCumo` and the batch map `2SKEx6bSq-4`. They belong to direct memory: 0x2901eb0 reserves a range with `7oxv3PPCumo` and maps blocks of direct memory into it with `2SKEx6bSq-4` (see kernel-imports.md), and the type query reads the type that the allocations of 0x26d3ee0 and 0x33ead5 record. The query still fails for every offset, so the eboot's type-3 test (0x26bae30, called at 0x26bae74) answers "not type 3" even for those type-3 allocations; the two map calls are logging stubs. A reserved range needs a region kind of its own that a fixed direct map may replace, which is design work of its own, and the three together don't fit this issue's PR. Running the game to its main loop (#106) waits for them.
- **Harness.** The harness doesn't load the PRXs by default, so eboot imports of libc go to stubs as in M2. Testing a function that allocates needs libc's `malloc` family, which needs libc.prx loaded and initialised, and with it the game's allocator. The issue that adds this loads the load set and runs the PRX init once in the fixture setup, then forces the game's heap into existence with one allocation and its release, and creates the test thread's TLS blocks for both PRX modules through the TLS helper, all before the baseline snapshot. Otherwise the first test would map the heap or create a TLS block after the baseline, the restore would reset the allocator's state, and the next call would map it again. The 116 MiB heap doesn't fit runtime.md's 16 MiB arena. It becomes a snapshot region of its own. So do the other state the PRXs and TLS add, which `Harness(Image&)` doesn't cover today: the writable segments of libc.prx and libSceFios2 (libc's dispatch cells, its stdio state, and the libc data exports that eboot data imports now bind to instead of data blocks), the test thread's eboot TLS block, the PRX TLS blocks and the guest `errno`. The issue decides how to keep the per-test cost of these regions low and updates runtime.md's harness section.

## Time

Wall clock from `CLOCK_REALTIME`, every counter from `CLOCK_MONOTONIC`, sleeps through `clock_nanosleep`. Clock ids and the counter frequency are confirmed from the game's use. libSceRtc is implemented from the game's call sites only (see Naming). Its dates and microsecond ticks are in [rtc.md](../formats/rtc.md) and `src/hle/system/date_time.cpp` (in `bbhlesystem`); the tick epoch and the time zone are our choices there, since the code shows neither.

- `src/hle/kernel/time.cpp`. Sleeps are relative `clock_nanosleep` calls on `CLOCK_MONOTONIC`. An interrupted sleep is not restarted: `nanosleep` and `usleep` fail with `EINTR` (`nanosleep` fills the remainder, libc's `sleep` loops on it, libc.prx 0x61f5), `sceKernelUsleep` returns the sce code of `EINTR` (its callers ignore the result and read the clock again), libScePosix `sleep` returns the unslept seconds rounded up.
- No call site reads a counter frequency. The two unnamed counters count from the runtime's start: `4J2sUJmuHZQ` in microseconds (libc's `clock` returns it), `-2IRUCO--PM` in nanoseconds (its callers use it only modulo a ring size). Units and call sites are in [kernel-imports.md](../formats/kernel-imports.md#time).
- The time zone of `gettimeofday` and of `kOcnerypnQA` is the host's, with a daylight saving shift of 60 minutes, as the game assumes (eboot 0x1a386d).
- **Main-loop probe.** The libScePosix `gettimeofday` (the frame pacer's) passes its return address to an optional observer: `bb::hle::kernel::set_gettimeofday_observer(void (*)(std::uintptr_t))` in `time.hpp`, nullptr to remove it. It runs on the calling thread before the clock is read. libkernel's `gettimeofday` (libc.prx's) doesn't report.

## Files and paths

Guest paths are mapped through a mount table. Everything else is refused with `ENOENT` and logged once per prefix.

| Guest | Host | Access |
|---|---|---|
| `/app0/…` | `$BB_GAME_DIR/…` | read-only; writes fail with `EROFS` |
| save data mount points handed out by our libSceSaveData | `$XDG_DATA_HOME/bloodborne-linux/profiles/<profile>/savedata/<n>/` | read-write |
| temporary mount | `$XDG_CACHE_HOME/bloodborne-linux/profiles/<profile>/temp/` | read-write |
| `/hostapp/…` (debug output) | refused | logged |

Paths are normalised, and `..` cannot leave a mount. The resolver (`src/hle/kernel/paths.hpp`) takes a guest path and an access mode (`read`, or `write` for anything that may create, change or remove) and returns a host path or a guest errno: `ENOENT` for no mount, a relative path, `..` above the mount point or a junk file name, `EROFS` for a write under `/app0`, `ENAMETOOLONG` past the guest limits. A path that doesn't exist still resolves, so the host call reports the error or creates the file. Mount points are single components (`/savedata0`); the save data issue registers and removes them. The eboot imports no call that hands out a temporary mount point, so none is mounted by default; `temp_dir()` gives its host directory should one turn up. When an exact lookup under `/app0` fails, a case-insensitive lookup runs and its hits are cached and logged. macOS junk files (`._*`, `.DS_Store`) are hidden from directory listings. File descriptors are guest numbers in our own table that maps them to host descriptors, so the game can never close or reuse the runtime's own descriptors. Guest 0, 1 and 2 start out mapped to duplicates (`dup`) of the host's stdin, stdout and stderr (libc.prx's stdio writes to them), so a guest `close(2)` closes only the duplicate and the log keeps its stderr. A new descriptor gets the lowest free guest number, as in POSIX.

- The descriptor table (`FdTable`, `fd_table()`) is in `src/hle/kernel/file.hpp`, for the other modules that take descriptors (mmap, directories). A guest descriptor holds a shared reference to its host descriptor, which closes when the last call using it returns, so a `close` on one thread never pulls the host descriptor from under a `read` on another. The duplicates of the host streams get numbers of 3 or more, and a closed host stream is replaced by `/dev/null` at such a number, so a guest `close` never reaches a host descriptor the runtime reuses.
- `src/hle/kernel/file.cpp` holds the file functions. Host descriptors are opened `O_CLOEXEC`. `O_DIRECT` is dropped ([kernel-abi.md](../formats/kernel-abi.md#open-flags)), unknown open flags are refused with `EINVAL`. An open counts as a write for the resolver when its access mode isn't `O_RDONLY` or it has `O_CREAT` or `O_TRUNC`.
- `src/hle/kernel/dir.cpp` holds the directory and metadata calls (mkdir, rmdir, unlink, rename, truncate, ftruncate, getdirentries). All of them resolve their paths for `write`, so anything under `/app0` fails with `EROFS`. `Resolved` names the mount of a path and whether the path is the mount point itself: a rename between two mounts fails with `EXDEV` even when both lie on one host file system, and rmdir, unlink or rename of a mount point (either side) fails with `EBUSY`, so the game can never remove or replace the host directory behind it. `getdirentries` keeps no state of its own: the read position is the host directory offset of the descriptor. It reads host records with `getdents64`, skips junk files, writes guest records until the next one doesn't fit, then seeks the host descriptor back to the first record it didn't write. `*base` gets the offset before the call, and a guest `lseek` to it lists the same records again, which the eboot relies on (0x20725eb seeks back to the base, then resumes in the same block). A buffer too small for the next record fails with `EINVAL`, as does a descriptor that isn't a directory. A host inode that truncates to file number 0 becomes 0xffffffff, since libSceFios2 skips records with 0 (0x2d453). The eboot decides directory or not from the record type alone (0x207272e), so a host `DT_UNKNOWN` (XFS without ftype, some FUSE and NFS mounts) is replaced by the type `fstatat` reports, and a symbolic link by the type of its target, since the resolver follows links. A dangling link keeps `DT_LNK`.

## Network and PSN

Offline, with no host networking. The init calls on the start-up path (`sceNetInit`, `sceNetPoolCreate`, `sceSslInit`, `sceHttpInit`, `sceHttpCreateTemplate`, `sceHttpCreateEpoll`, the unnamed libSceHttp `s2-NPIvz+iA` and `EY28T2bkN7k`, the unnamed libSceNpManager `A2CQ3kgSopQ`) succeed. `sceNetInit` returns 0 on every call, since several call sites initialise independently. Ids are per-kind counters from 1 (a template id of 0 would be skipped by its destructor at 0xfd1dfa), and the HTTP epoll handle is a 64-bit counter value. The state queries report offline: `sceNetCtlGetState` state 0, `sceNpGetState` state 1 (not the signed-in 2), `sceNetCtlGetInfo` a negative result of our own without touching its output, because its callers print the output on success. Each value is documented in `src/hle/net/net.hpp` with the call sites that check it. Every other network and PSN import stays a stub. The module is the OBJECT library `bbhlenet`; executables that run the game link it next to `bbhle`.

## Video out without a GPU

Two code paths drive video out *(survey)*. One opens a port, creates the queue `"Initialize"`, registers it for flip events and registers two 1920x1080 buffers (0x11e488e..0x11e4915); its flips come from `sceVideoOutSubmitFlip` (0x11e419a, 0x11e420a, 0x11e4560, 0x11e4ae0), each followed by a wait on that queue without a timeout. The other (0x26d61d4..0x26d65f3, queue `"FlipEventQueue"`) flips through the unnamed GPU submit-and-flip call `xbxNatawohc` (0x26b0dff, 0x26b0ee2, followed by `sceGnmSubmitDone`) and waits at 0x26d6ee0..0x26d6f2d until the 64-bit flip count at +0x18 of the flip status has caught up with its own count of submitted frames, one queue wait per round. Both block forever unless flips complete, so flips do complete without a GPU. Both paths are implemented: buffers are registered and kept, and GPU submissions complete at once without running their command buffers.

- **Ports.** `sceVideoOutOpen` hands out handles from 1, distinct for every open, never reused. Calls on a handle that is not open return `0x80290001`, the value the game stores as "no port" before it opens one (0x26d619e); callers check only the sign.
- **Flips.** A flip submitted with `sceVideoOutSubmitFlip` completes at the first 1/60 s tick of `CLOCK_MONOTONIC` after the port's previous flip, so at most one completes per tick. One flip thread, started at the first submission, completes them: it raises the port's flip count and then triggers a flip event on every queue registered for the port (`EventQueue::trigger`; id the port handle, kind 1, detail the buffer index, data the flip argument, user data the value given at registration). Closing a port drops its pending flips.
- **Buffers.** `sceVideoOutSetBufferAttribute` fills the caller's attribute block with our own 28-byte layout (`BufferAttribute`: format, tiling, aspect, width, height, pitch, a reserved word), since the game never reads it back. `sceVideoOutRegisterBuffers` records the addresses for indices `start..start+count-1`, at most 16 per port, and keeps a copy of the attribute. A count of 0 succeeds and registers nothing: 0x26d65d6 calls with count 0 when its configured buffer count is 0 and fails on a negative result. The unnamed `CBiu4mCE1DA`, called as `(handle, 0)` right after the open (0x26d61ee), returns 0 for an open port.
- **GPU submits.** `gnm_driver.cpp` implements the unnamed submit calls without a GPU: `zwY0YV91TTI` and `iCO804ZgzdA` (count, draw command buffers and their sizes, second command buffers and their sizes) return 0 at once. `xbxNatawohc` does the same submit and then `sceVideoOutSubmitFlip`, with the port handle in `r9` and buffer index, mode and flip argument on the stack, and returns the flip's result, so its flips complete like any other. `sceGnmSubmitDone`, called after the submit-and-flip at 0x26b0dff and 0x26b0ee2, returns 0. The first three submissions, of any of the three calls, are logged at `info` (number, call, buffer count, size of the first draw buffer), the rest at `debug`. Command buffers are parsed from M4 on.
- The first three flips are logged at `info`, the rest at `debug`. The module is the OBJECT library `bbhlevideo` (`src/hle/video/`); executables that run the game link it next to `bbhle`.

## Runtime directories

`$XDG_DATA_HOME` (profiles, save data), `$XDG_CACHE_HOME` (temp, later the shader cache), `$XDG_CONFIG_HOME` (config, later) and `$XDG_STATE_HOME` (logs), each with the XDG default when unset, each under `bloodborne-linux/`. `--profile <name>` (`[A-Za-z0-9_-]{1,32}`, default `default`) selects the profile directories. A variable that is empty or relative counts as unset, as the XDG spec says; the defaults need `HOME`. Directories are created with mode 0700 when first used, missing parents included (existing ones keep their mode). Nothing is ever written to the game or repository directory: `bb::common::RuntimeDirs` (`src/common/runtime_dirs.hpp`) refuses to start when one of its four directories and the game directory or the source checkout the binary was built from lie inside one another, and it creates directories only inside its own four.

## Logging

One logger in `bbcommon` (`src/common/log.hpp`): levels, channels (`loader`, `hle.<library>`, `game`), the thread name on every line, output to stderr and to `$XDG_STATE_HOME/bloodborne-linux/logs/<UTC time>-<pid>.log`. `BB_LOG=<channel>=<level>,…` filters. Stubs log their calls as runtime.md describes; in the `debug` preset, calls to HLE implementations can be traced as well (below).

- **Lines.** `<UTC hh:mm:ss.mmm> <level> [<thread>] <channel>: <message>`. Levels are `trace`, `debug`, `info`, `warn`, `error`, `fatal` (always shown) and `off`. The thread is the name `bb::common::set_thread_name` gave it (which also sets the host name, cut to 15 bytes), else its host thread id. Each line is one `write(2)` per output under one lock, so lines never interleave and nothing is buffered in the process. That is what "flushed on `_exit` and on a fatal error" rests on: `log_flush()` only waits for a line in progress (and syncs the file). `log_fatal` logs, flushes and aborts. The logger is not async-signal-safe.
- **Filter.** `BB_LOG` entries are `<channel>=<level>` or a bare `<level>` for the default (`info`). An entry covers its channel and the channels below it (`hle` covers `hle.libkernel`), the longest match wins, and an unknown level or an empty channel is an error. The first runtime entry point, bb-run (#101), reads it with `set_log_filter_from_environment()` at start. Until then `BB_LOG` has no effect: bb-load runs no game code and keeps the default filter.
- **HLE call trace.** In builds without `NDEBUG` (the `debug` preset), `resolve` hands out a trace thunk instead of an HLE implementation itself if the filter shows `trace` for `hle.<library>` when that import is first resolved. The filter is read there, once per import, and never again for the choice: resolving is cached, so a later filter change can neither add nor remove a thunk. So bb-run (#101) must read `BB_LOG` before it links anything; then `BB_LOG` decides which libraries get thunks. With trace off for a library at that moment, and in every build with `NDEBUG`, the GOT slot holds the implementation itself and tracing costs nothing. The thunk is the 24-byte one of runtime.md with its own entry, `bb_hle_trace_entry` (`stub_entry.S`), and a `TraceInfo` (implementation, library, module, NID, name, channel) in place of a `StubInfo`. The entry saves `rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9`, `rax` (`al` counts the vector registers of a variadic call) and `xmm0`–`xmm7`, calls `on_traced_call` with the return address on top of the stack, restores them and jumps to the implementation with the stack as the caller left it. So stack arguments stay in place and the implementation returns straight to the caller with its own `rax`/`xmm0`. Only the low 128 bits of the vector registers are kept, which is all the System V ABI passes for `double`, `float` and 128-bit vectors. `on_traced_call` writes one line at `trace` on `hle.<library>`, `call <library> (<module>) <NID> <name> from <return address>: <rdi> … <r9>`, if the filter shows it at that call. Since `import_address` returns what `resolve` returned, a replacement calls through the same thunk as the original. Exports of the bundled PRXs (bound before implementations) and data blocks are never traced; stubs keep their own `warn` log.
- **File.** `open_log_file()` creates `<UTC yyyymmddThhmmssZ>-<pid>.log` (mode 0600, never an existing file) in the logs directory of `RuntimeDirs`. bb-run (#101) calls it once at start, so each run of the game writes one file. bb-load writes none.

## Naming

NIDs without a matched name are implemented under a descriptive C++ name and registered by NID, with a comment that the name is unknown. They get no row in `symbols/nids.csv`, which holds matched names only. For libSceRtc, libSceSaveData and libSceSaveDataDialog (exposure log in `docs/clean-room.md`, which treats libSceSaveDataDialog like libSceSaveData) semantics come from the game's call sites only, and no Sony-style names are written down, not even in comments.

## Open questions

1. Whether the eboot TLS reservation ends exactly at the thread pointer with the sanitizer runtimes linked in (clang links ASan statically). glibc puts the executable's block at the thread pointer minus `p_memsz` rounded up to `p_align`. So the reservation must be the last thing in the executable's TLS segment, and that segment's `p_memsz` must be a multiple of its `p_align`. A `thread_local` with an alignment above 16 anywhere in the executable can break either. If one does, a linker script fragment will be needed. *Resolved by #83:* a plain `thread_local` would not do, since GNU ld fills `.tbss` in link order, so the TLS of a static library linked after the reservation (bbcommon, say) would sit above it, and an orphan TLS section lands between `.tdata` and `.tbss`. The reservation (`src/hle/eboot_tls/`, OBJECT library `bbeboottls`) is therefore defined in assembly in the input section `.tcommon`, which GNU ld's default script places after every `.tbss` input section (`*(.tbss .tbss.* …) *(.tcommon)`, `ld --verbose`), whatever the link order; no linker script fragment is needed. Nothing else uses `.tcommon` (TLS common symbols, which C++ and C with `-fno-common` never produce). With GCC 16 and GNU ld 2.46, in `debug`, `relwithdebinfo` and `release`, `kernel_tls_test`, `harness_eboot_test` and `game_eboot_test` each have a TLS segment with `p_memsz` 0x7a0 and `p_align` 0x10 and the reservation at 0x50–0x7a0 (below it: bbhle's guest `errno` cell, the TLS helper's per-thread list and the log's thread name), and the check passes on the main thread and on new threads. GCC links its sanitizer runtimes as shared libraries, whose TLS is a module of its own. Untested: lld, and clang with its static ASan runtime. A `thread_local` aligned above 16 would raise `p_align` past the reservation's alignment and can break the placement again. The check catches all of these: `bbeboottls` runs it at start-up and aborts with both addresses, and thread start (#94) runs `bb::hle::kernel::check_eboot_tls` in every new thread.
2. Whether worker threads or the tick block on GPU completion beyond flips. Flip waits exist on both video paths (see [Video out without a GPU](#video-out-without-a-gpu)); flips complete on both, since the GPU submit-and-flip call submits its flip with `sceVideoOutSubmitFlip`. A wait for a label or an end-of-pipe event that a command buffer would write is not, and would need M4's command buffer parsing.
3. Whether the game throws C++ exceptions. If so, libc.prx's unwinder needs module information from libkernel (possibly the unnamed info query `f7KBOafysXo`).
